## Pruébalo

Cambia los criterios y mira, a la vez, la URL que mandaría Angular, lo que valida Zod, la consulta de Prisma (o el SQL aproximado), qué filas de la tabla se descartan con el `where`, cuáles se saltan con `skip` y cuáles se devuelven con `take`, y el JSON de la respuesta. Prueba también a pedir más de 50 por página, la página 0 o a ordenar por `passwordHash`: Zod lo para con un `400`.

<SimuladorListado />

Lo que hay que ver en el simulador:

- **El `where` solo lleva los criterios que han llegado.** Sin búsqueda ni categoría, el `where` queda vacío y cuenta todos.
- **El total cuenta con el mismo `where`**: es el número de productos que cumplen el filtro, no el de la tabla.
- **`skip = (page - 1) * limit`**. Página 2 de 5 en 5: se saltan 5 y se cogen 5.
- Una página más allá del final no es un error: devuelve `items` vacío. En Angular sale el estado "vacío".
- La búsqueda es un `ILIKE` de Postgres: no distingue mayúsculas, pero **sí tildes**. "raton" no encuentra "Ratón".

## 1. El schema de Zod

```ts title="src/modules/productos/productos.schema.ts"
import { z } from 'zod';

export const listarProductosSchema = z.object({
  q: z.string().trim().optional(),
  categoriaId: z.coerce.number().int().positive().optional(),
  orden: z.enum(['nombre', 'precio', 'createdAt']).default('createdAt'),
  dir: z.enum(['asc', 'desc']).default('desc'),
  page: z.coerce.number().int().min(1).default(1),
  limit: z.coerce.number().int().min(1).max(50).default(10),
});

export type ListarProductosQuery = z.infer<typeof listarProductosSchema>;
```

- **Todo lo que llega en la URL es texto.** `z.coerce.number()` convierte `"2"` en `2` (y `"abc"` en `NaN`, que no pasa la validación).
- **`.default(...)`** pone un valor si no viene. Así el servicio nunca recibe `undefined` en `page`, `limit`, `orden` ni `dir`.
- **`z.enum` para el orden.** Si alguien manda `orden=passwordHash`, responde `400`. Nunca ordenes por un campo que venga sin comprobar.
- **`.max(50)`** para que nadie pida un millón de filas de golpe.
- **`z.infer`** saca el tipo de TypeScript del schema, igual que `RegisterInput` en el `users.schema.ts` de clase.

## 2. El servicio

<Recorrido
  titulo="src/modules/productos/productos.service.ts"
  lenguaje="ts"
  codigo={`import { Prisma } from '@prisma/client';
import { prisma } from '../../config/db.js';
import type { ListarProductosQuery } from './productos.schema.js';

export async function listarProductos(filtro: ListarProductosQuery) {
  const where: Prisma.ProductoWhereInput = {};
  if (filtro.q) {
    where.nombre = { contains: filtro.q, mode: 'insensitive' };
  }
  if (filtro.categoriaId) {
    where.categoriaId = filtro.categoriaId;
  }

  const orderBy: Prisma.ProductoOrderByWithRelationInput = { [filtro.orden]: filtro.dir };

  const [total, items] = await prisma.$transaction([
    prisma.producto.count({ where }),
    prisma.producto.findMany({
      where,
      orderBy,
      skip: (filtro.page - 1) * filtro.limit,
      take: filtro.limit,
      select: {
        id: true,
        nombre: true,
        precio: true,
        stock: true,
        categoria: { select: { id: true, nombre: true } },
      },
    }),
  ]);

  return {
    items,
    total,
    page: filtro.page,
    limit: filtro.limit,
    totalPages: Math.ceil(total / filtro.limit),
  };
}`}
>
  <Paso lineas="1-3" titulo="Imports">
    `Prisma` (con mayúscula) trae los **tipos** que genera Prisma para tu modelo. El `prisma` (minúscula) es el cliente único de `config/db.ts`, como en clase.
  </Paso>
  <Paso lineas="6" titulo="Un where vacío">
    `Prisma.ProductoWhereInput` es el tipo del `where` de `producto`. Empieza vacío: sin criterios, cuenta y devuelve todos.
  </Paso>
  <Paso lineas="7-9" titulo="Búsqueda">
    `contains` con `mode: 'insensitive'` es un `ILIKE '%teclado%'` de Postgres: encuentra "Teclado mecánico" aunque se escriba en minúsculas.
  </Paso>
  <Paso lineas="10-12" titulo="Filtro">
    Solo se añade si ha llegado. El `where` se construye poco a poco con los criterios que vengan.
  </Paso>
  <Paso lineas="14" titulo="Orden con clave calculada">
    `{ [filtro.orden]: filtro.dir }`: si `orden` vale `"precio"` y `dir` vale `"asc"`, queda `{ precio: 'asc' }`. Es seguro porque Zod solo deja pasar los tres campos del `enum`.
  </Paso>
  <Paso lineas="16-17" titulo="Dos consultas a la vez">
    `prisma.$transaction([...])` con un **array** lanza las dos consultas juntas, en una misma transacción, y devuelve los resultados en el mismo orden. Ojo: con el nivel de aislamiento por defecto de Postgres (`READ COMMITTED`), si alguien inserta un producto justo entre las dos, el total podría no cuadrar por uno. Para que vean exactamente los mismos datos se pasa `{ isolationLevel: 'RepeatableRead' }` como segundo argumento; en un listado, no suele merecer la pena.
  </Paso>
  <Paso lineas="17" titulo="El total, con el mismo where">
    `count({ where })` cuenta solo lo que cumple los filtros. Si contaras sin `where`, Angular calcularía páginas que no existen.
  </Paso>
  <Paso lineas="21-22" titulo="Paginación">
    `skip` es cuántas filas se saltan y `take` cuántas se cogen. Página 2 de 10 en 10: `skip = 10`, `take = 10`. Es el `OFFSET` y el `LIMIT` de SQL.
  </Paso>
  <Paso lineas="23-29" titulo="Selección de campos">
    `select` dice qué columnas vuelven. No se mandan `descripcion` ni `createdAt`, y de la categoría solo `id` y `nombre`. Cumple el requisito de "selección de campos".
  </Paso>
  <Paso lineas="33-39" titulo="La respuesta">
    La página (`items`) y lo que Angular necesita para los botones: `total`, `page`, `limit` y `totalPages`. Con 0 resultados, `totalPages` es 0.
  </Paso>
</Recorrido>

## 3. El controlador

```ts title="src/modules/productos/productos.controller.ts"
import type { Request, Response } from 'express';
import { z } from 'zod';
import { listarProductosSchema } from './productos.schema.js';
import { listarProductos } from './productos.service.js';

export async function listarProductosCtrl(req: Request, res: Response) {
  const resultado = listarProductosSchema.safeParse(req.query);
  if (!resultado.success) {
    return res.status(400).json({ error: z.treeifyError(resultado.error) });
  }
  res.json(await listarProductos(resultado.data));
}
```

- **`safeParse`** no lanza excepciones: devuelve `success` y `data` o `error`, igual que en el `validate` de clase.
- **`z.treeifyError`** es la forma de Zod 4 de ordenar los errores (sustituye al `.flatten()` obsoleto, como se vio el 27/10).
- **No hace falta `try/catch`**: en Express 5, si una función `async` lanza un error, llega solo al `errorHandler`.
- Las respuestas de error de clase usan la clave `message` (y `validate` usa `errors`); aquí se usa `error`. Elige una para toda tu API y úsala igual en Angular.

### ¿Por qué no se usa el middleware validate de clase?

<DeClase fecha="27/10" proyecto="node-server-26-27" nota="validate.ts, versión de clase para Zod 4" />

```ts title="src/middleware/validate.ts (de clase)"
export const validate = (schema: ZodType) => (req: Request, res: Response, next: NextFunction) => {
  const parsed = schema.safeParse(req.body);
  if (!parsed.success) {
    return res.status(400).json({ errors: z.treeifyError(parsed.error) });
  }
  req.body = parsed.data;
  next();
};
```

El de clase valida el **`body`** y lo sustituye por los datos validados (`req.body = parsed.data`). Con los *query params* no se puede hacer lo mismo: **en Express 5, `req.query` no se puede sobrescribir** (es de solo lectura, y `req.query = ...` da un error). Por eso se valida en el controlador y se pasa `resultado.data` al servicio.

<Callout title="La otra mitad está en Angular">
  En Angular, el servicio monta la URL con `HttpParams` (que es **inmutable**: `params = params.set(...)`), se salta los criterios vacíos, recibe una `Pagina<T>` con la misma forma que esta respuesta y, al buscar, **vuelve a la página 1**. Está en [Listado con filtros, paginación y token](/docs/2-dam/acceso-a-datos/angular-avanzado/listado-filtros-y-token), dentro de Angular avanzado.
</Callout>

## Ejercicios

<Ejercicio titulo="Filtro por precio máximo" dificultad="facil">
  Añade al listado un filtro `precioMax`: si llega, solo se devuelven los productos con precio menor o igual. Cambia el schema y el servicio.

  <Pista>En el schema, igual que `categoriaId` pero con `positive()` y sin `int()`, porque puede tener decimales.</Pista>
  <Pista>En el servicio, el operador es `lte`.</Pista>

  <Solucion>

```ts title="productos.schema.ts"
precioMax: z.coerce.number().positive().optional(),
```

```ts title="productos.service.ts"
if (filtro.precioMax !== undefined) {
  where.precio = { lte: filtro.precioMax };
}
```

Con `?precioMax=50` llega `50` (número) y el `where` queda `{ precio: { lte: 50 } }`. Se combina con los demás criterios: todos tienen que cumplirse.

</Solucion>
</Ejercicio>

<Ejercicio titulo="Solo los que tienen stock" dificultad="media">
  Añade un parámetro `disponibles`: con `?disponibles=true` solo salen los productos con `stock` mayor que 0, y con `false` o sin él, todos. Ojo con cómo conviertes el texto a booleano.

  <Pista>`z.coerce.boolean()` no sirve: convierte con `Boolean(valor)`, y `Boolean("false")` es `true` porque cualquier texto no vacío lo es.</Pista>
  <Pista>Acepta solo `"true"` o `"false"` con un `z.enum` y transfórmalo.</Pista>

  <Solucion>

```ts title="productos.schema.ts"
disponibles: z.enum(['true', 'false']).transform((v) => v === 'true').optional(),
```

```ts title="productos.service.ts"
if (filtro.disponibles) {
  where.stock = { gt: 0 };
}
```

- `?disponibles=true` → `true` → filtra.
- `?disponibles=false` → `false` → no filtra.
- `?disponibles=si` → `400`, porque no está en el `enum`.

Zod 4 también trae `z.stringbool()`, que hace esta conversión por ti (y acepta además `1`/`0`, `yes`/`no`, `on`/`off`…): `disponibles: z.stringbool().optional()`.

</Solucion>
</Ejercicio>
