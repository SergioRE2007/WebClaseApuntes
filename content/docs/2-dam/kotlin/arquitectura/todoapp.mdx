## Cómo creció la app

<Steps>


  </Step>
  <Step>

#### Repositorio en memoria y módulo de Hilt

  La interfaz `TaskRepository`, su implementación `TaskRepositoryInMemory` (con `@Inject constructor()` y dos tareas de prueba, "Dummy" y "Dummy2", creadas en el `init`) y el `ApplicationModule` con `@Binds @Singleton`. Ver [Capas](/docs/2-dam/kotlin/arquitectura/capas) y [Módulos de Hilt](/docs/2-dam/kotlin/arquitectura/hilt-modulos).

  </Step>
  <Step>

#### La lista, por capas

  `MainActivity` con `@AndroidEntryPoint` recibía el repositorio con `@Inject lateinit var` y se lo pasaba a `TaskListScreen`. La pantalla se construyó capa a capa: `Scaffold` vacío, `LazyColumn` con `items(key = { it.id })`, `TaskCard` (con `Card`, `Column`, `Row` y un `Switch` de solo lectura) y el botón flotante con el icono <Dudoso nota="Casi todas las capturas leen `add_24px`; otra lectura es `add_24dp`.">`add_24px`</Dudoso>.

  </Step>
  <Step>

#### El parche y la navegación (09/10)

  El botón de crear se probó primero con un estado local y un `if`. Después llegaron `Routes.kt`, `ToDoNavHost.kt`, los callbacks `toCreate` y `toDetail`, la tarjeta pulsable y una `TaskDetailScreen(id)` de prueba. Ver [Navegación](/docs/2-dam/kotlin/arquitectura/navegacion).

  </Step>
  <Step>

#### ViewModel con Hilt (09/10)

  `TaskListViewModel` con `@HiltViewModel` e `@Inject constructor`, `hilt-navigation-compose` en Gradle y `viewModel: TaskListViewModel = hiltViewModel()` en la pantalla. El repositorio dejó de ser un parámetro de la pantalla. Ver [Inyección con Hilt](/docs/2-dam/kotlin/arquitectura/hilt).

  </Step>
  <Step>

#### StateFlow y el formulario (16/10)

  `MutableStateFlow` en el ViewModel, `collectAsStateWithLifecycle()` en la pantalla, y `TaskCreateViewModel` con dos `TextFieldState` y `onCreate()`. Se depuró con *breakpoints*, Step Into y *Recomposition State*. Ver [ViewModel y StateFlow](/docs/2-dam/kotlin/arquitectura/viewmodel-y-stateflow).

  </Step>
  <Step>

#### Corrutinas y estados sellados (23/10)

  El repositorio pasó a funciones `suspend` con `delay(5_000L)`, y las pantallas a estados sellados: `TaskListScreenState` y `TaskCreateScreenState`, con `load()`, `when` exhaustivo y pantalla con estado y sin estado. Ver [Estados de pantalla](/docs/2-dam/kotlin/arquitectura/estados-de-pantalla).

  </Step>
  <Step>

#### Detalle y textos traducidos (capturas del documento)

  En las capturas del documento de la ToDoApp aparecen además el paquete por pantalla (`tasklist`, `taskcreate`, `taskdetail`), `TaskDetailViewModel` leyendo el id con `savedStateHandle.toRoute()` y el botón con `stringResource(R.string.save)`, con `values/strings.xml` y `values-es/strings.xml`.

  </Step>
</Steps>

<Callout title="Por qué @Singleton importa tanto aquí">
  Todos los ViewModels reciben **la misma** instancia de `TaskRepositoryInMemory`, así que una tarea creada en una pantalla existe para las demás. Como solo vive en memoria, **se pierde al cerrar la app**: para guardarla de verdad hace falta Room, que se vio el 13/11 en otro proyecto.

<Ejercicio titulo="Marcar una tarea como completada" dificultad="media">
  En las capturas no se ven `complete(id)` ni `uncomplete(id)` del repositorio en memoria con `suspend`. Escríbelas para que cambien `isCompleted` de la tarea y **publiquen la lista nueva** en el `StateFlow`, de forma que quien observe `tasks` se entere. Supón que `_taskFlow` ya es `MutableStateFlow<List<Task>>` (la versión arreglada de [ViewModel y StateFlow](/docs/2-dam/kotlin/arquitectura/viewmodel-y-stateflow#la-lista-que-no-se-actualiza)).

  <Pista>Las dos funciones hacen lo mismo con un `Boolean` distinto: sácalo a una función privada.</Pista>
  <Pista>Busca la posición con `indexOfFirst { it.id == id }`, sustituye la tarea por una copia con `copy(isCompleted = ...)` y publica `_taskList.toList()`.</Pista>

  <Solucion>

```kotlin title="TaskRepositoryInMemory.kt (añadido)"
override suspend fun complete(id: Int) {
    changeCompleted(id, isCompleted = true)
}

override suspend fun uncomplete(id: Int) {
    changeCompleted(id, isCompleted = false)
}

private fun changeCompleted(id: Int, isCompleted: Boolean) {
    val index = _taskList.indexOfFirst { it.id == id }
    if (index != -1) {
        _taskList[index] = _taskList[index].copy(isCompleted = isCompleted)
        _taskFlow.value = _taskList.toList()
    }
}
```

`indexOfFirst` devuelve `-1` si no hay ninguna tarea con ese id, así que no se rompe. En la depuración del 16/10 se ve un `changeCompleted` de clase que hacía `taskToChange.isCompleted = isCompleted` sobre la propia tarea (por eso `isCompleted` era `var`). Funciona igual en memoria, pero no publica nada en el `StateFlow`, así que nadie se entera del cambio.

  </Solucion>
</Ejercicio>

<Ejercicio titulo="Tu propia app, de punta a punta" dificultad="dificil">
  Monta una app de notas mínima con toda la arquitectura del bloque: un repositorio en memoria que exponga `val notes: Flow<List<Note>>`, su módulo de Hilt, un `NoteListViewModel` que construya su estado (`Loading` o `Success(notes)`) a partir de ese `Flow`, un `NoteCreateViewModel` con un `TextFieldState`, las dos pantallas (la lista con un botón + y el formulario) y el `NavHost` con sus rutas. Al guardar una nota se vuelve a la lista y la nota tiene que aparecer.

  <Pista>Para que la lista se entere de las notas nuevas, el repositorio tiene que publicar una lista nueva en un `MutableStateFlow<List<Note>>` cada vez que crea una.</Pista>
  <Pista>En el ViewModel de la lista, usa `map` y `stateIn` sobre `repository.notes`, como en `SettingsViewModel` del 18/11.</Pista>
  <Pista>Las pantallas reciben callbacks: `toCreate` en la lista y `onBack` en el formulario. El `NavHost` les pasa `navigate` y `popBackStack()`.</Pista>

  <Solucion>

```kotlin title="data/NoteRepository.kt"
data class Note(val id: Int, val text: String)

interface NoteRepository {
    val notes: Flow<List<Note>>
    suspend fun create(text: String): Note
}

class NoteRepositoryInMemory @Inject constructor() : NoteRepository {
    private val _notes = MutableStateFlow<List<Note>>(emptyList())
    override val notes: Flow<List<Note>> = _notes.asStateFlow()
    private var nextId = 1

    override suspend fun create(text: String): Note {
        val note = Note(id = nextId, text = text)
        nextId++
        _notes.value = _notes.value + note
        return note
    }
}
```

```kotlin title="di/AppModule.kt"
@Module

    @Binds
    @Singleton
    fun bindNoteRepository(repository: NoteRepositoryInMemory): NoteRepository
```

```kotlin title="ui/notelist/NoteListViewModel.kt"
sealed class NoteListScreenState {
    object Loading : NoteListScreenState()
    class Success(val notes: List<Note>) : NoteListScreenState()
}

@HiltViewModel
class NoteListViewModel @Inject constructor(
    repository: NoteRepository
) : ViewModel() {
    val state: StateFlow<NoteListScreenState> = repository.notes
        .map<List<Note>, NoteListScreenState> { NoteListScreenState.Success(it) }
        .stateIn(
            scope = viewModelScope,
            started = SharingStarted.WhileSubscribed(stopTimeoutMillis = 5_000L),
            initialValue = NoteListScreenState.Loading
        )
}
```

```kotlin title="ui/notelist/NoteListScreen.kt"
@Composable
fun NoteListScreen(
    toCreate: () -> Unit,
    modifier: Modifier = Modifier,
    viewModel: NoteListViewModel = hiltViewModel(),
) {
    val state by viewModel.state.collectAsStateWithLifecycle()
    when (state) {
        NoteListScreenState.Loading -> NoteListContent(toCreate = toCreate, modifier = modifier, isLoading = true)
        is NoteListScreenState.Success -> NoteListContent(
            toCreate = toCreate,
            modifier = modifier,
            isLoading = false,
            notes = (state as NoteListScreenState.Success).notes
        )
    }
}
```

Detalles que conviene entender:

- La lista se actualiza sola porque el repositorio publica una lista **nueva** (`_notes.value + note`) y el ViewModel de la lista está suscrito con `stateIn`. El `NoteListViewModel` sigue vivo mientras la lista está en la pila, así que no hace falta volver a cargar.
- La función sin estado se llama `NoteListContent` en vez de repetir el nombre como en clase. Así ninguna llamada puede encajar con las dos a la vez.
- Volver justo después de `onCreate()` funciona aquí porque `create` no espera nada: la corrutina termina antes de salir. Si guardar tardara (una API, Room), al salir de la pantalla su ViewModel se destruye y la corrutina se cancela. Entonces habría que volver cuando el estado pasara a `Created`, con `LaunchedEffect`, que no se dio en clase.
