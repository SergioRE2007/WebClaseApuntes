## 2. Conceptos y patrones

### Teoría de Room (diagrama de la documentación)
- **Clase de base de datos** (`@Database`): es el punto de acceso. La app le pide los DAO.
- **DAO** (`@Dao`): una interfaz con los métodos que leen y escriben en la base de datos.
- **Entidades** (`@Entity`): cada objeto es una fila de una tabla. La app lee y cambia sus campos, y el DAO guarda los cambios.
- Flujo: *App → Get DAO → DAO → Get Entities from db / Persist changes back to db*.

### Gradle
- **Catálogo de versiones** (`gradle/libs.versions.toml`). En `[versions]` van los números, en `[libraries]` las librerías con `group`/`name` o `module` más `version.ref`, y en `[plugins]` el `id` con su `version.ref`. Desde los `.gradle.kts` se usan con `libs.xxx` y `alias(libs.plugins.xxx)`.
- **Build raíz**: los plugins se declaran con `apply false`. **Build del módulo app**: se aplican sin `apply false`.
- **KSP** (Kotlin Symbol Processing) es el procesador de anotaciones. Room 3 y Hilt lo usan para generar código: `ksp(...)` para el compilador e `implementation(...)` para el runtime.
- Plugin y dependencia van por separado. Si aplicas el plugin de Hilt sin `hilt-android`, el sync falla.
- Diferencias entre los tres SDK:
  - `compileSdk`: con qué API se compila.
  - `targetSdk`: qué comportamiento de ejecución se adopta.
  - `minSdk`: en qué dispositivos se puede instalar.
  - Si una librería pide un `compileSdk` más nuevo, falla `checkDebugAarMetadata`.
- Sintaxis nueva de AGP 9: `compileSdk { version = release(37) { minorApiLevel = 1 } }`.
- Después de tocar el catálogo, Gradle no puede reutilizar la *configuration cache*. Hay que hacer **Sync Now**.

### Room 3
- Los paquetes son **`androidx.room3.*`**, no `androidx.room.*`.
- Entidad = `data class` anotada con `@Entity`:
  - `tableName` fija el nombre de la tabla.
  - `@PrimaryKey` marca la clave primaria.
  - `@ColumnInfo(name = ...)` cambia el nombre de la columna en SQL.
  - Los tipos nullables (`String?`) son columnas que admiten NULL.
- Parámetros de `@Entity` que enseñó el tooltip: `tableName`, `indices`, `inheritSuperIndices`, `primaryKeys`, `foreignKeys`, `ignoredColumns` y `withoutRowId`.
- El DAO es una `interface` con `@Dao`, y sus métodos son `suspend fun`, porque el acceso a la base de datos se hace con corrutinas, fuera del hilo principal.
- Con `@Insert` puedes **sobrecargar** el método: una entidad, `vararg` o `List<Entity>` para meter varias de golpe.
- `@Update` actualiza una entidad por su clave primaria.
- `@Query(value = "SQL")`: los parámetros de la función se usan en el SQL con `:nombre`.
- Convención de nombres: la entidad se llama `PokemonEntity`, para separarla del modelo de dominio.
- La base de datos es una `abstract class` con `@Database(entities, version, ...)`.

### Hilt
- Módulo: `@Module` + `@InstallIn(SingletonComponent::class)`. Vive mientras vive la app.
- `@Provides` le dice a Hilt cómo construir un objeto, en este caso la base de datos de Room.
- Organización por capas: `data` (entidades, DAO y base de datos) y `di` (módulos de Hilt).

### Cómo buscar un error
- Leer el panel **Build Output** o **Sync**, que dice el archivo, la línea y el mensaje.
- Comentar líneas con `//` hasta que compile y así ver cuál falla.
- El error *"Syntax error: Expecting qualified name"* (`PokemonDAO.kt:5:7`) salía por un `import a…` a medio escribir.
