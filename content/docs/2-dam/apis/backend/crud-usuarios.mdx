| Fichero | Qué hace | Sabe de `req` y `res` |
| --- | --- | --- |
| `users.routes.ts` | Qué método y qué URL van a qué controlador, y qué middlewares van delante. | No (solo los conecta) |
| `users.controller.ts` | Lee la petición, llama al servicio y elige el **código HTTP**. | Sí |
| `users.service.ts` | La lógica y las consultas a **Prisma**. | **No** |
| `users.schema.ts` | Los schemas de **Zod** que validan lo que llega ([Validación con Zod 4](/docs/2-dam/apis/backend/validacion-zod)). | No |

Si vienes de Spring, es el mismo reparto de siempre: el `@RestController` (rutas + controlador), el `@Service` y el repositorio, que aquí es directamente el cliente de Prisma.

## Las rutas

<DeClase fecha="27/10" nota="v0.4.0" />

```ts title="src/modules/users/users.routes.ts"
import { Router } from 'express';
import { validate } from '../../middleware/validate.js';
import { updateUserSchema } from './users.schema.js';
import { listUsersCtrl, getUserCtrl, updateUserCtrl, deleteUserCtrl } from './users.controller.js';

const router = Router();
router.get('/', listUsersCtrl);
router.get('/:id', getUserCtrl);
router.patch('/:id', validate(updateUserSchema), updateUserCtrl);
router.delete('/:id', deleteUserCtrl);
export default router;
```

Y en `app.ts` se monta con un **prefijo**:

```ts title="src/app.ts"
app.use('/api/users', usersRoutes);
```

- `Router()` es como una mini app de Express con sus propias rutas. Al montarlo en `/api/users`, sus rutas se escriben **sin el prefijo**: `'/'` es `/api/users` y `'/:id'` es `/api/users/5`.
- **`:id`** es un parámetro de ruta. Llega en `req.params.id`, siempre como **texto**.
- En la ruta `patch` van dos funciones: primero el middleware `validate(updateUserSchema)` y luego el controlador. Puedes poner tantos middlewares como quieras entre la URL y el controlador.
- Es **`PATCH`** y no `PUT` porque la actualización es parcial: puedes mandar solo el nombre o solo el email.

<Callout type="info" title="No hay POST en /api/users">
  En la v0.4.0 los usuarios se crean con el registro (`POST /api/auth/register`, v0.5.0). Para enseñarlo, el profesor escribió `router.post('/', createUserCtrl)` y salió `Cannot find name 'createUserCtrl'`: ese controlador no existe. También escribió `app.use('api/users/', (req, resp) => ...)` para enseñar un manejador escrito en línea, y lo borró.
</Callout>

## El servicio

El servicio es el único que usa Prisma. No recibe `req` ni `res`: recibe datos normales (un id, un email) y devuelve lo que da la base.

<Recorrido
  titulo="src/modules/users/users.service.ts"
  lenguaje="ts"
  codigo={`import { prisma } from '../../config/db.js';

export async function createUser(email: string, name: string, passwordHash: string) {
  return prisma.user.create({
    data: { email, name, passwordHash },
    select: { id: true, email: true, name: true, createdAt: true }
  });
}

export async function findUserByEmail(email: string) {
  return prisma.user.findUnique({ where: { email } });
}

export async function findUserById(id: number) {
  return prisma.user.findUnique({
    where: { id },
    select: { id: true, email: true, name: true, createdAt: true }
  });
}

export async function listUsers() {
  return prisma.user.findMany({
    select: { id: true, email: true, name: true, createdAt: true },
    orderBy: { id: 'asc' }
  });
}

export async function updateUser(id: number, data: { name?: string; email?: string }) {
  return prisma.user.update({
    where: { id },
    data,
    select: { id: true, email: true, name: true, createdAt: true }
  });
}

export async function deleteUser(id: number) {
  return prisma.user.delete({ where: { id } });
}`}
>

    Importa el único `PrismaClient`, el de `config/db.ts`.
  </Paso>
  <Paso lineas="3-8" titulo="create con select">
    Inserta el usuario con el hash de la contraseña (lo usa el registro). `select` dice **qué campos devuelve**: todos menos `passwordHash`.
  </Paso>
  <Paso lineas="10-12" titulo="findUserByEmail, sin select">
    Es la única que devuelve el usuario **entero**, con `passwordHash`, porque el login lo necesita para comparar la contraseña. Nunca se manda tal cual al cliente.
  </Paso>
  <Paso lineas="14-19" titulo="findUnique por id">
    `findUnique` busca por un campo `@id` o `@unique`. Si no hay ninguno, **devuelve `null`** (no lanza error).
  </Paso>
  <Paso lineas="21-26" titulo="findMany con orderBy">
    La lista, sin `passwordHash` y ordenada por `id` de menor a mayor.
  </Paso>
  <Paso lineas="28-34" titulo="update">
    Actualiza por `where: { id }` solo los campos que vengan en `data`. Si no existe el usuario, **lanza P2025**; si el email ya lo usa otro, **P2002**.
  </Paso>

### El `select` que protege `passwordHash`

Sin `select`, Prisma devuelve **todas** las columnas, y con ellas el hash de la contraseña. Por eso todas las funciones que devuelven usuarios al cliente llevan `select: { id: true, email: true, name: true, createdAt: true }`. Los tests de la v0.9.0 lo comprueban: `expect(res.body).not.toHaveProperty('passwordHash')`.

El profesor **repite el `select` en cada función**. Si lo quieres escribir una sola vez:

### El choque de tipos con `exactOptionalPropertyTypes`

El 27/10 el profesor intentó tipar `data` con el tipo que saca Zod del schema, `UpdateUserInput`, y salió este error:

<Terminal titulo="Problems">
{`Type '{ name?: string | undefined; email?: string | undefined; }' is not assignable to type '(Without<UserUpdateInput, UserUncheckedUpdateInput> & UserUncheckedUpdateInput) | …' with 'exactOptionalPropertyTypes: true'.`}
</Terminal>

Con `exactOptionalPropertyTypes`, `name?: string` significa "puede no estar, pero si está es un `string`". El tipo de Zod dice `name?: string | undefined`, que deja poner `undefined` a mano, y los tipos de Prisma no lo aceptan. Se probaron una `interface` escrita a mano y un genérico, y al final se volvió al tipo **escrito en línea**: `data: { name?: string; email?: string }`.

## El controlador

El controlador traduce entre HTTP y el servicio: saca los datos de `req`, llama al servicio dentro de un `try/catch` y elige el código de la respuesta.

<Recorrido
  titulo="src/modules/users/users.controller.ts"
  lenguaje="ts"
  codigo={`import type { Request, Response } from 'express';
import { listUsers, findUserById, updateUser, deleteUser } from './users.service.js';

export async function listUsersCtrl(_req: Request, res: Response) {
  try {
    const users = await listUsers();
    res.json(users);
  } catch (error: any) {
    res.status(500).json({ message: error.message });
  }
}

export async function updateUserCtrl(req: Request, res: Response) {
  try {
    const id = Number(req.params.id);
    if (isNaN(id)) {
      return res.status(400).json({ message: 'ID inválido' });
    }
    const user = await updateUser(id, req.body);
    res.json(user);
  } catch (error: any) {
    if (error.code === 'P2025') {
      return res.status(404).json({ message: 'Usuario no encontrado' });
    }
    if (error.code === 'P2002') {
      return res.status(409).json({ message: 'El email ya está en uso' });
    }
    res.status(500).json({ message: error.message });
  }
}`}
>
  <Paso lineas="1" titulo="Solo tipos de Express">
    `Request` y `Response` son tipos, así que van con `import type`.
  </Paso>
  <Paso lineas="4-11" titulo="listUsersCtrl">
    `async` porque espera al servicio. Si todo va bien, `res.json(users)` (200). Si falla, 500 con el mensaje del error. `_req` lleva guion bajo porque no se usa.
  </Paso>
  <Paso lineas="15-18" titulo="Comprobar el id">
    `req.params.id` es texto. `Number('5')` da `5` y `Number('abc')` da `NaN`; con `isNaN` se responde **400** `ID inválido`. El `return` corta la función para no responder dos veces.
  </Paso>
  <Paso lineas="19-20" titulo="Llamar al servicio">
    `req.body` ya viene validado por `validate`. Si todo va bien, 200 con el usuario actualizado.
  </Paso>
  <Paso lineas="22-24" titulo="P2025 → 404">
    Prisma no encontró el registro que tenía que actualizar.
  </Paso>
  <Paso lineas="25-27" titulo="P2002 → 409">
    Se ha intentado repetir un valor `@unique` (el email). 409 *Conflict*: la petición choca con lo que ya hay.
  </Paso>
  <Paso lineas="28" titulo="Lo demás → 500">
    Cualquier otro error es un fallo del servidor.
  </Paso>
</Recorrido>

Con el ratón encima, el profesor enseñó los tipos de `Request` y `Response` (`ParamsDictionary`, `ParsedQs`…): `Request` es genérico y por defecto los parámetros y la *query* son diccionarios de texto.

## Errores de Prisma y códigos HTTP

Prisma pone un código a cada error conocido en `error.code`. Los dos que traduce el controlador de clase:

| Código de Prisma | Cuándo | Respuesta |
| --- | --- | --- |
| **P2025** | El registro que había que actualizar o borrar no existe. | **404** `Usuario no encontrado` |
| **P2002** | Se repite un valor de un campo `@unique`. | **409** `El email ya está en uso` |

<NoDadoEnClase inline /> Otros códigos útiles (como P2003, cuando se intenta borrar algo que todavía tiene datos relacionados) y cómo traducirlos todos en el `errorHandler` están en [Backend para el proyecto](/docs/2-dam/apis/backend-proyecto).

Ojo con la diferencia: `findUnique` **devuelve `null`** si no encuentra nada, mientras que `update` y `delete` **lanzan P2025**. Por eso en `getUserCtrl` hay que comprobar el `null` a mano y en `updateUserCtrl` se mira el código del error.

Los códigos HTTP que usa la API de clase:

| Código | Cuándo | Ejemplo de clase |
| --- | --- | --- |
| 200 | Bien | `res.json(...)` |
| 201 | Creado | Registro (`res.status(201).json(data)`) |
| 400 | Datos mal | Falla Zod, o el id no es un número |
| 401 | Credenciales o token | Login fallido, ruta protegida sin token |
| 404 | No existe | P2025, o una ruta que no existe (`Cannot GET /x`) |
| 409 | Choca con lo que hay | P2002, email ya registrado |
| 500 | Fallo del servidor | El `catch` |

Fíjate sobre todo en estos casos:

- **`GET /api/users/abc`**: el controlador responde 400 `ID inválido` sin llegar al servicio.
- **`PATCH /api/users/1` con un email mal escrito**: responde `validate` con 400 y el controlador ni se ejecuta.
- **`PATCH /api/users/abc` con un body válido**: primero pasa `validate` (va antes) y después el controlador responde 400 por el id.
- **`PATCH /api/users/99`**: P2025 → 404. **Email de otro usuario**: P2002 → 409.
- **Un campo de más en el body** (por ejemplo `"rol": "admin"`): `validate` lo quita, porque `req.body` pasa a ser lo que devuelve Zod y `z.object` descarta por defecto las claves que no conoce. <NoDadoEnClase inline />
- **`PUT /api/users/1`** y **`POST /api/users`**: no hay ruta para ese método, así que responde el 404 de Express.
- **`DELETE`**: el usuario se borra, pero la demo no inventa la respuesta, porque `deleteUserCtrl` no se vio.

  <Pista>Copia la estructura de `updateUserCtrl`: `try/catch`, `Number` + `isNaN` y `return res.status(...)`.</Pista>

  <Solucion>

<NoDadoEnClase>El final de `getUserCtrl` no se vio en clase: esta es una forma de hacerlo siguiendo el estilo del resto del controlador. El mensaje del 404 es inventado.</NoDadoEnClase>

```ts title="src/modules/users/users.controller.ts"
export async function getUserCtrl(req: Request, res: Response) {
  try {
    const id = Number(req.params.id);
    if (isNaN(id)) {
      return res.status(400).json({ message: 'ID inválido' });
    }
    const user = await findUserById(id);
    if (!user) {
      return res.status(404).json({ message: 'Usuario no encontrado' });
    }
    res.json(user);
  } catch (error: any) {
    res.status(500).json({ message: error.message });
  }
}
```

export async function deleteUserCtrl(req: Request, res: Response) {
  try {
    const id = Number(req.params.id);
    if (isNaN(id)) {
      return res.status(400).json({ message: 'ID inválido' });
    }
    await deleteUser(id);
    res.status(204).end();
  } catch (error: any) {
    if (error.code === 'P2025') {
      return res.status(404).json({ message: 'Usuario no encontrado' });
    }

}
