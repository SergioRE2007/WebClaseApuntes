Lo que llega en `req.body` lo manda el cliente, y puede ser cualquier cosa: un email mal escrito, un nombre vacío, campos de más o directamente nada. **Zod** describe cómo tienen que ser los datos y los comprueba antes de que lleguen al controlador. ## Qué es Zod

Un **schema** de Zod es un objeto que describe la forma de unos datos. Con él puedes validar cualquier valor y, además, sacar su tipo de TypeScript sin escribirlo dos veces. Si vienes de Java, es la idea de Bean Validation, pero sin anotaciones:

| Bean Validation (Java) | Zod |
| --- | --- |
| `@NotNull String name` | `name: z.string()` (obligatorio por defecto) |
| `@Size(min = 2)` | `z.string().min(2, 'mensaje')` |
| `@Email` | `z.email('mensaje')` |
| Campo que puede faltar | `.optional()` |
| `@Valid` en el controlador | El middleware `validate(schema)` en la ruta |

## Los schemas de `users.schema.ts`

Así quedó el fichero después de los cambios de la clase del 27/10:

```ts title="src/modules/users/users.schema.ts"
import { z } from 'zod';

export const registerSchema = z.object({
  email: z.string().email('Email inválido'),
  name: z.string().min(2, 'El nombre debe tener al menos 2 caracteres'),
  password: z.string().min(8, 'La contraseña debe tener al menos 8 caracteres'),
});

export const loginSchema = z.object({
  email: z.email('Email inválido'),
  password: z.string().min(8, 'La contraseña debe tener al menos 8 caracteres'),
});

export const updateUserSchema = z.object({
  name: z.string().min(2, 'El nombre debe tener al menos 2 caracteres').optional(),
  email: z.email('Email inválido').optional(),
});

export type RegisterInput = z.infer<typeof registerSchema>;
export type LoginInput = z.infer<typeof loginSchema>;
export type UpdateUserInput = z.infer<typeof updateUserSchema>;
```

- **`z.object({...})`**: un objeto con esas claves.
- **`z.string().min(n, 'mensaje')`**: texto de al menos `n` caracteres. El segundo argumento es el mensaje de error (en español, como los de clase).
- **`z.email('mensaje')`**: texto con formato de email.
- **`.optional()`**: el campo puede no venir. En `updateUserSchema` **todo** es opcional para que el `PATCH` sea parcial: puedes mandar solo el nombre, solo el email o los dos.
- Los tres schemas están en el módulo `users`, y el módulo `auth` los importa de ahí.

Ojo: `loginSchema` y `updateUserSchema` ya usan `z.email()`, pero `registerSchema` <Dudoso nota="No se sabe si se quedó sin cambiar o si no se llegó a ver. En el repositorio (v0.5.0 y v1.0.0) los tres siguen con z.string().email().">sigue con `z.string().email()`</Dudoso>. En Zod 4 funciona igual, pero está obsoleto.

## Tipos con `z.infer`

`z.infer<typeof schema>` saca el tipo de TypeScript del schema. Así el tipo y la validación no se pueden desincronizar:

```ts title="Lo que vale cada tipo"
type RegisterInput = { email: string; name: string; password: string };
type LoginInput = { email: string; password: string };
type UpdateUserInput = { name?: string | undefined; email?: string | undefined };
```

El último es el que salió en el tooltip el 27/10. Ese `| undefined` es el que choca con los tipos de Prisma por `exactOptionalPropertyTypes`, y por eso el servicio acaba con un tipo escrito a mano ([CRUD de usuarios](/docs/2-dam/apis/backend/crud-usuarios)).

## `parse` frente a `safeParse`

Los dos validan; la diferencia es qué hacen cuando los datos no valen:

| | Si vale | Si no vale | Dónde sale en clase |
| --- | --- | --- | --- |
| `schema.parse(datos)` | Devuelve los datos | **Lanza** un `ZodError` | El controlador de auth (v0.5.0), dentro de un `try` |
| `schema.safeParse(datos)` | `{ success: true, data }` | `{ success: false, error }`, **sin lanzar** | El middleware `validate` |

```ts title="Uso de los dos"
const r = updateUserSchema.safeParse(req.body);
if (!r.success) {
  // r.error es un ZodError con los fallos
} else {
  // r.data son los datos ya validados
}

const { email, password } = loginSchema.parse(req.body); // si falla, salta al catch
```

## El middleware `validate`

En vez de validar en cada controlador, la referencia tiene **un solo middleware** que sirve para cualquier ruta. Se le pasa el schema y devuelve el middleware que valida con ese schema: por eso se le llama middleware "fábrica".

<Recorrido
  titulo="src/middleware/validate.ts (versión de clase para Zod 4)"
  lenguaje="ts"
  codigo={`import type { Request, Response, NextFunction } from 'express';
import type { ZodType } from 'zod';
import { z } from 'zod';

export const validate = (schema: ZodType) => (req: Request, res: Response, next: NextFunction) => {
  const parsed = schema.safeParse(req.body);
  if (!parsed.success) {
    return res.status(400).json({ errors: z.treeifyError(parsed.error) });
  }
  req.body = parsed.data;
  next();
};`}
>
  <Paso lineas="1-2" titulo="Solo tipos">
    `Request`, `Response`, `NextFunction` y `ZodType` son tipos: van con `import type`.
  </Paso>
  <Paso lineas="3" titulo="z es un valor">
    `z.treeifyError` se **ejecuta**, así que `z` necesita un `import` normal. Con `import type { z }` sale el error `'z' cannot be used as a value because it was imported using 'import type'`.
  </Paso>
  <Paso lineas="5" titulo="Una función que devuelve un middleware">
    `validate(schema)` devuelve `(req, res, next) => ...`. La función de dentro "recuerda" el `schema` (es una *closure*). Por eso en la ruta se escribe `validate(updateUserSchema)`, con paréntesis.
  </Paso>
  <Paso lineas="6" titulo="safeParse">
    Valida el body sin lanzar excepciones.
  </Paso>
  <Paso lineas="7-9" titulo="Si no vale: 400">
    Responde 400 con los errores ordenados por campo (`z.treeifyError`). El `return` corta la cadena: el controlador no se ejecuta.
  </Paso>
  <Paso lineas="10-11" titulo="Si vale: datos limpios y next()">
    Cambia `req.body` por los datos que devuelve Zod y pasa al controlador. El controlador ya puede fiarse de `req.body`.
  </Paso>
</Recorrido>

En la ruta se pone delante del controlador:

```ts title="src/modules/users/users.routes.ts"
router.patch('/:id', validate(updateUserSchema), updateUserCtrl);
```

El tooltip del editor da su firma: `validate(schema: ZodType): (req, res, next) => Response | undefined`.

## Lo que cambió en Zod 4

| Zod 3 (obsoleto en Zod 4) | Zod 4 |
| --- | --- |
| `z.string().email('...')` | `z.email('...')` |
| `parsed.error.flatten()` | `z.treeifyError(parsed.error)` |
| `ZodSchema` | `ZodType` (en Zod 4, `ZodSchema` es solo un alias de compatibilidad) |
| `import ... from 'zod/v3'` | No se recomienda: es la capa de compatibilidad con Zod 3 |

Por el camino salieron varios intentos que fallaron. **No los copies**:

- `z.treeifyError(err)`: `err` no existe; el error está en `parsed.error`.
- `import type { z, ZodSchema }`: `z` no se puede usar como valor si se importa como tipo.
- `import type { ZodSchema } from 'zod/v3'`: da `No overload matches this call`, porque mezcla tipos de Zod 3 con funciones de Zod 4.
- Los *casts* `as $ZodError<unknown>` y `z.treeifyError(parsed.error.flatten().fieldErrors)`.

## Qué responde el 400 <NoDadoEnClase inline />

En clase no se llegó a enviar una petición mala, pero esto es lo que devuelve de verdad `validate` con Zod 4 si mandas `{ "name": "A", "email": "ana@" }` a `PATCH /api/users/1`:

```json title="Respuesta 400"
{
  "errors": {
    "errors": [],
    "properties": {
      "name": { "errors": ["El nombre debe tener al menos 2 caracteres"] },
      "email": { "errors": ["Email inválido"] }
    }
  }
}
```

`z.treeifyError` ordena los errores con la misma forma que el objeto: los del objeto entero en `errors` y los de cada campo dentro de `properties`. Y si `req.body` llega `undefined` (por ejemplo, porque falta `express.json()`), sale `{ "errors": { "errors": ["Invalid input: expected object, received undefined"] } }`.

Otra cosa que conviene saber: `z.object` **quita las claves que no están en el schema**. Como `validate` hace `req.body = parsed.data`, si alguien manda `{ "name": "Ana", "rol": "admin" }`, al controlador solo le llega `{ "name": "Ana" }`.
