Una app que mete todo en la `MainActivity` funciona para un ejercicio de diez líneas, pero en cuanto crece se vuelve imposible de tocar. En clase se trabajó desde el principio con **capas**: cada una tiene un trabajo y solo habla con la de debajo. Es la idea de la arquitectura en **N capas** del manual de arquitecturas de clase (presentación, negocio y datos), llevada a Android.

<Callout type="idea" title="Lo que vas a aprender">
  - Qué hace cada capa: <Concepto termino="UI" definicion="Las funciones `@Composable` que pintan la pantalla. No tienen lógica: leen el estado y avisan de los eventos.">UI</Concepto>, <Concepto termino="ViewModel" definicion="Clase que guarda el estado de una pantalla, sobrevive al giro del móvil y recibe los eventos de la UI.">ViewModel</Concepto>, <Concepto termino="Repositorio" definicion="Clase que decide de dónde salen los datos (memoria, API o Room). La UI y el ViewModel solo conocen su interfaz.">repositorio</Concepto> y <Concepto termino="DataSource" definicion="Clase que habla con una sola fuente de datos: la API, Room o DataStore. El repositorio usa uno o varios.">DataSource</Concepto>.
  - Por qué el repositorio es una **interfaz** con una **implementación** aparte.
  - Cómo se organizan los paquetes por pantalla y por feature, como en los proyectos de clase.
</Callout>

## Las capas, de arriba abajo

<Mermaid
  titulo="Capas de la ToDoApp"
  chart={`flowchart TD

    VM -->|"solo conoce la interfaz"| REPO["TaskRepository<br/>(interfaz)"]
    IMPL["TaskRepositoryInMemory"] -.->|"implementa"| REPO
    IMPL --> MEM[("Lista en memoria")]`}
/>

| Capa | Qué hace | Qué no hace |
| --- | --- | --- |
| **UI** (pantallas `@Composable`) | Pinta el estado que le da el ViewModel y le avisa de lo que hace el usuario (pulsar, escribir). | No guarda datos ni decide nada. No sabe de dónde salen las tareas. |
| **ViewModel** | Guarda el estado de **una** pantalla, lo expone para que la UI lo lea y tiene una función por cada evento (`onCreate()`, `load()`…). | No pinta nada. No sabe si los datos vienen de memoria, de una API o de Room. |
| **Repositorio** | Es la puerta a los datos: `readAll()`, `create(...)`, `update(...)`. Decide de qué fuente leer. | No sabe qué pantalla lo usa. |
| **DataSource** | Habla con una sola fuente: la API con Retrofit, la base de datos de Room o DataStore. | No mezcla fuentes. Eso lo hace el repositorio. |

Cada capa **solo conoce a la de debajo**, y además solo su interfaz. El ViewModel recibe un `TaskRepository`, no un `TaskRepositoryInMemory`. Así se puede cambiar una capa entera sin tocar las de arriba.

<Callout title="¿Y cómo llega el repositorio al ViewModel?">
  Ninguna capa crea a la de debajo con su constructor (lo que en Java sería un `new`). Las recibe en su constructor y las crea **Hilt**. Lo verás en [Inyección con Hilt](/docs/2-dam/kotlin/arquitectura/hilt). Por ahora quédate con que cada clase "pide" lo que necesita.
</Callout>

## El repositorio es una interfaz

<DeClase fecha="23/10" proyecto="ToDoApp" />

La interfaz dice **qué** se puede hacer con las tareas, sin decir **cómo**. Esta es la versión del 23/10, ya con funciones `suspend` (pueden esperar sin bloquear la pantalla) y con un `Flow` para observar los cambios:

```kotlin title="data/repository/TaskRepository.kt"
interface TaskRepository {
    val tasks: Flow<List<Task>>
    suspend fun readAll(): List<Task>
    suspend fun readOne(id: Int): Task
    suspend fun create(title: String, description: String, limitDate: String): Task
    suspend fun complete(id: Int)
    suspend fun uncomplete(id: Int)
    suspend fun update(id: Int, title: String? = null, description: String? = null)
}
```

Fíjate en dos cosas de Kotlin que en Java no existen:

- **Una interfaz puede declarar propiedades** (`val tasks`). La implementación la escribe con `override val`.
- **Parámetros con valor por defecto** (`title: String? = null`). En Java tendrías que escribir varias sobrecargas de `update`.

Las pantallas y los ViewModels solo conocen `TaskRepository`. Hoy los datos viven en memoria; mañana puedes escribir un `TaskRepositoryRoom` y, cambiando **una línea** del módulo de Hilt, toda la app pasa a usarlo sin tocar la UI.

<Callout type="error" title="Una interfaz no se instancia">
  El 09/10, para salir del paso, el profesor intentó darle a la pantalla un valor por defecto con `TaskRepository()` y no compiló: igual que en Java, **no se puede crear un objeto de una interfaz**. Tuvo que usar `TaskRepositoryInMemory()`. Después ese apaño desapareció al llegar el ViewModel y Hilt.
</Callout>

### La implementación en memoria

<DeClase fecha="23/10" proyecto="ToDoApp" nota="fragmento" />

Recórrela paso a paso con los botones (o con las flechas del teclado):

<Recorrido
  titulo="data/repository/TaskRepositoryInMemory.kt"
  lenguaje="kotlin"
  codigo={`private const val delay = 5_000L

class TaskRepositoryInMemory @Inject constructor() : TaskRepository {
    private val _taskList = mutableListOf<Task>()
    private val _taskFlow = MutableStateFlow(_taskList)
    override val tasks: Flow<List<Task>>
        get() = _taskFlow.asStateFlow()

    override suspend fun readAll(): List<Task> {
        delay(timeMillis = delay)
        return _taskList.toList()
    }

    override suspend fun create(title: String, description: String, limitDate: String): Task {
        delay(timeMillis = delay)
        val newTask = Task(id = nextId, title = title, description = description,
            createdAt = "", limitDate = limitDate)
        if (_taskList.add(newTask)) {
            nextId++
            _taskFlow.value = _taskList
        }
        return newTask
    }
}`}
>
  <Paso lineas="3" titulo="`: TaskRepository` es el `implements`">
    `: TaskRepository` es el `implements` de Java. Las funciones que vienen de la interfaz llevan `override` obligatorio (en Java, `@Override` es opcional). `@Inject constructor()` le dice a Hilt que sabe crear esta clase con ese constructor. Se explica en [Inyección con Hilt](/docs/2-dam/kotlin/arquitectura/hilt).
  </Paso>
  <Paso lineas="4-7" titulo="Lista privada, propiedad de la interfaz">
    `_taskList` es **privada y mutable**: solo el repositorio la toca. La propiedad `tasks` que pedía la interfaz se escribe con `override val`.
  </Paso>
  <Paso lineas="9-12" titulo="readAll() devuelve una copia">
    Hacia fuera, `readAll()` devuelve `_taskList.toList()`, que es **una copia**: así nadie de fuera puede modificar la lista interna.
  </Paso>
  <Paso lineas="1, 10, 15" titulo="Una red lenta de mentira">
    `delay(5_000L)` simula que los datos tardan 5 segundos en llegar, como si vinieran de la red. Así se ve en pantalla el estado de carga.
  </Paso>
  <Paso lineas="18-21" titulo="Crear y avisar">
    Si la tarea se añade, sube `nextId` y se asigna la lista al `StateFlow`. Esa asignación tiene trampa: lo ves justo debajo.
  </Paso>
</Recorrido>

Lo que no se ve o no está claro:

- Es un fragmento: no se ven `readOne`, `complete`, `uncomplete` ni `update`.
- <Dudoso nota="En las capturas no aparece la línea donde se declara.">`nextId`</Dudoso>: se usa, pero no se ve dónde se declara.
- <Dudoso nota="Asigna la misma lista mutable, así que el StateFlow no avisa de los cambios. Se explica en la página de ViewModel y StateFlow.">`_taskFlow.value = _taskList`</Dudoso>: asigna la misma lista. Tiene un problema que se explica (con una demo) en [ViewModel y StateFlow](/docs/2-dam/kotlin/arquitectura/viewmodel-y-stateflow#la-lista-que-no-se-actualiza).
- `createdAt` y `limitDate` son `String`. El propio profesor dejó un `TODO Buscar un tipo correcto para fecha`.

## El modelo de la app y el de la API

<DeClase fecha="26/10" proyecto="PokeApp2627" />

Cuando los datos vienen de una API, el JSON casi nunca tiene la forma que quiere la app. En la PokeApp2627 se separaron dos tipos de clases:

- Los **DTO**, en `PokemonApiModels.kt`: `data class` con la forma exacta del JSON (`PokemonResult`, `PokemonSprites`…). Solo los usa el DataSource remoto.
- El **modelo** de la app: `Pokemon(id, name, pokemonImageUrl)`. Es lo que viaja por el repositorio, el ViewModel y la UI.

Se pasa de uno a otro con una **función de extensión**, que en Java no existe: es como añadirle un método a una clase sin tocarla.

```kotlin title="PokemonApiModels.kt (versión del 09/11)"
fun PokemonResult.toModel(): Pokemon = Pokemon(
    id = this.id,
    name = this.name,
    pokemonImageUrl = this.sprites?.frontDefault,
)
```

Dentro de la función, `this` es el `PokemonResult` sobre el que la llamas: `body.toModel()`. Retrofit, Gson y los DTO se explican en [Retrofit 3 con Gson](/docs/2-dam/kotlin/datos/retrofit); aquí lo que importa es la idea: **la UI nunca ve un DTO**.

## Ejercicios

<Ejercicio titulo="Repositorio de notas" dificultad="facil">
  Vas a hacer una app de notas con la misma arquitectura que la ToDoApp. Escribe la `data class Note` (con `id` y `text`), la interfaz `NoteRepository` con `readAll()` y `create(text)`, ambas `suspend`, y una implementación en memoria `NoteRepositoryInMemory` que dé ids consecutivos empezando en 1 y que no deje modificar su lista desde fuera.

  <Pista>Copia la forma de `TaskRepositoryInMemory`: una `mutableListOf` privada y un contador `nextId`.</Pista>
  <Pista>Para no exponer la lista interna, devuelve una copia con `toList()`.</Pista>

  <Solucion>

```kotlin title="data/repository/NoteRepository.kt"
data class Note(val id: Int, val text: String)

interface NoteRepository {
    suspend fun readAll(): List<Note>
    suspend fun create(text: String): Note
}

class NoteRepositoryInMemory @Inject constructor() : NoteRepository {
    private val _notes = mutableListOf<Note>()
    private var nextId = 1

    override suspend fun readAll(): List<Note> = _notes.toList()

    override suspend fun create(text: String): Note {
        val newNote = Note(id = nextId, text = text)
        _notes.add(newNote)
        nextId++
        return newNote
    }
}
```

`nextId` se declara antes de usarlo. En Kotlin las propiedades se inicializan en el orden en que están escritas, así que si hubiera un bloque `init` que creara notas de prueba usando `nextId`, tendría que ir **después** de `nextId`. (Desde el `init` no se puede llamar a `create(...)` directamente, porque es `suspend`.)

  </Solucion>
</Ejercicio>

<Glosario titulo="Conceptos clave">
  <Termino nombre="Capa">Parte de la app con un solo trabajo. Solo conoce la interfaz de la capa de debajo.</Termino>
  <Termino nombre="Repositorio">Puerta a los datos. Decide de qué fuente leer. La UI y el ViewModel solo ven su interfaz.</Termino>
  <Termino nombre="DataSource">Habla con una sola fuente: API, Room o DataStore.</Termino>
  <Termino nombre="DTO">`data class` con la forma del JSON de la API. Se convierte al modelo con `toModel()`.</Termino>
  <Termino nombre="Feature">Paquete con todo lo de una funcionalidad (`data`, `ui`, `di`). Lo común va en `core`.</Termino>
