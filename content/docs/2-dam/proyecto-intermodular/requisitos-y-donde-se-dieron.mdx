### Planificación por hitos (Acceso a Datos)

El profesor de Acceso a Datos reparte el proyecto en **hitos semanales acumulativos**: cada semana se revisa una evidencia que funcione, y cada hito amplía el anterior. Los hitos son genéricos; cada equipo los adapta a su modelo.

| Hito | Semana | Foco | Qué tiene que haber |
| --- | --- | --- | --- |
| H1 | 29-30 oct. | Creación y estructura | Proyecto creado y **versionado**. Angular y Express separados, carpetas básicas y las dos apps arrancando. |
| H2 | 2-6 nov. | Layout y estilos | Layout general, Tailwind CSS y criterios visuales comunes (estructura, espaciado, tipografía y navegación). |
| H3 | 9-13 nov. | Componentes y navegación | Componentes principales y reutilizables, y Angular Router con navegación entre las vistas. |
| H4 | 16-20 nov. | Vistas, formularios e interacción | Listados, detalle y formularios, comunicación entre componentes y primeras validaciones. Puede ser con datos simulados. |
| H5 | 23-27 nov. | Servicios Angular | Servicios de acceso a datos e interfaces o tipos. Componentes separados de la comunicación con la futura API. |
| H6 | 30 nov.-4 dic. | Diseño de la API REST | Recursos, rutas, parámetros, cuerpos y respuestas. Express en rutas, controladores y servicios. Contrato entre frontend y backend. |
| H7 | 9-11 dic. | ORM y modelo | Modelo con Prisma o TypeORM, relaciones, restricciones y conexión con PostgreSQL. Primeras migraciones y preparación del seed. |
| H8 | 14-18 dic. | Endpoints y acceso a datos | Endpoints conectados a la base de datos, CRUD y consultas con el ORM, y el seed funcionando. |
| — | 21 dic.-10 ene. | Navidad | Sin hitos obligatorios. |
| H9 | 11-15 ene. | Integración | Datos reales en lugar de simulados: Angular consume la API y las operaciones atraviesan todas las capas. |
| H10 | 18-22 ene. | Consultas y negocio | Búsqueda, filtro, orden y paginación desde el backend. Consultas relacionales y la operación de negocio con transacción. |
| H11 | 25-29 ene. | Revisión final | Validaciones en los dos lados, errores HTTP, integridad, estados de carga y de "sin resultados". Migraciones, seed y configuración. |

En cada revisión semanal se mira: que el proyecto **arranca** y se puede enseñar el avance, que el hito nuevo **no rompe** lo anterior, que se mantiene la **separación por capas**, la **trazabilidad** (el repositorio refleja el avance con commits y una estructura comprensible), que el equipo sabe **explicar** sus decisiones y lo pendiente, y en algunos hitos una **rúbrica**. Para la trazabilidad te sirve lo de [Git: ramas, tags y Git Graph](/docs/2-dam/proyecto-intermodular/git-ramas-y-tags).

## Lo que te pueden pedir en la defensa

Los requisitos de la app dicen que "se pueden solicitar demostraciones prácticas", y en Acceso a Datos cada revisión pide que sepas explicar tus decisiones. Lo más probable, requisito por requisito:

| Requisito | Demostración probable |
| --- | --- |
| Room | Añadir un campo a una entidad. Si no subes `version` en `@Database` y das una migración, la app se cae al abrirla porque la base guardada en el móvil ya no coincide. En desarrollo basta con desinstalar la app. |
| Retrofit | Añadir un endpoint nuevo a la interfaz y llamarlo desde el repositorio. |
| Hilt | Explicar quién crea cada objeto. Por ejemplo, cómo llega el DAO al repositorio sin hacer `new`. |
| ViewModel y estado | Girar el móvil y ver que no se pierde nada. |
| Corrutinas | Quitar el wifi y enseñar que la app no se cae. |
| Localización <NoDadoEnClase inline /> | Cambiar el idioma del emulador. |
| Intent <NoDadoEnClase inline /> | Pulsar el botón y que se abra la otra app. |
| DataStore | Cambiar una preferencia, cerrar la app y volver a abrirla. |
| Prisma | Añadir un campo, crear la migración y enseñar el SQL que genera. |
| Seed <NoDadoEnClase inline /> | `npx prisma migrate reset` y ver que la base vuelve con datos. |
| Listado <NoDadoEnClase inline /> | Cambiar el filtro en Angular y enseñar la petición en la pestaña Red del navegador: los parámetros viajan en la URL. |
| Transacción <NoDadoEnClase inline /> | Forzar un error en mitad de la operación y comprobar que no se guardó nada. |
| Errores HTTP | Provocar un 400 (dato mal), un 404 (id que no existe) y un 409 (duplicado). |

Repasa con estas tarjetas: en el frente está lo que te pueden pedir y detrás, cómo responder.

<Flashcards titulo="Simulacro de defensa">
  <Tarjeta frente="Room: «añade un campo a esta entidad y arranca la app»">Sube `version` en `@Database` y añade una migración. Si no, Room ve que el esquema guardado en el móvil no coincide y la app se cae al abrirla. En desarrollo, desinstalar la app también vale.</Tarjeta>
  <Tarjeta frente="Retrofit: «añade un endpoint nuevo»">Un método nuevo en la interfaz de Retrofit (con `@GET`, `@POST`... y `@Path` o `@Body`), que devuelve `Response<T>`, y una llamada desde el DataSource o el repositorio.</Tarjeta>
  <Tarjeta frente="Hilt: «¿quién crea el DAO que usa tu repositorio?»">Hilt. El módulo de Room tiene un `@Provides` que crea la base de datos (mejor con `@Singleton`) y otro, `providesPokemonDao` en clase, que devuelve el DAO con `db.pokemonDao()`. El repositorio lo pide en su `@Inject constructor`; nadie hace `new`.</Tarjeta>
  <Tarjeta frente="ViewModel: «gira el móvil»">El estado vive en el ViewModel (`StateFlow`), que sobrevive al giro. La pantalla se vuelve a crear y recoge el mismo estado: no se pierde nada.</Tarjeta>
  <Tarjeta frente="Corrutinas: «quita el wifi»">Sin red, Retrofit lanza una excepción (`IOException`) y, si nadie la captura, la app se cierra. La llamada va en `viewModelScope.launch` dentro de un `try`/`catch`, y en el `catch` el ViewModel pasa a un estado de error que la pantalla enseña. Comprobar `isSuccessful` no basta: solo cubre las respuestas con error del servidor.</Tarjeta>
  <Tarjeta frente="DataStore: «cambia una preferencia y reinicia»">La preferencia se guarda en DataStore (por ejemplo, con `booleanPreferencesKey`) y se lee como `Flow` al arrancar, así que al volver a abrir la app sigue igual.</Tarjeta>
  <Tarjeta frente="Prisma: «añade un campo al modelo»">Cambias `schema.prisma`, `npx prisma migrate dev --name ...` crea la carpeta de la migración con su `migration.sql` (el SQL que se enseña) y la aplica. La migración se sube al repositorio.</Tarjeta>
  <Tarjeta frente="Seed: «deja la base como al principio»">`npx prisma migrate reset`: borra la base, aplica todas las migraciones y ejecuta el seed. No se dio en clase: di que lo has buscado tú.</Tarjeta>
  <Tarjeta frente="Listado: «¿dónde se filtra?»">En el backend. En la pestaña Red del navegador se ve que los criterios viajan en la URL como query params y que la respuesta solo trae una página, con el total. En el backend no se dio en clase.</Tarjeta>
  <Tarjeta frente="Errores HTTP: «provoca un 400, un 404 y un 409»">400: datos que no pasan la validación de Zod (o un id que no es número). 404: un id que no existe (P2025 de Prisma). 409: un valor `@unique` repetido (P2002).</Tarjeta>
  <Tarjeta frente="Transacción: «¿qué pasa si falla a la mitad?»">Con `prisma.$transaction` se deshace todo: no queda ninguna modificación a medias. Se demuestra forzando el error y mirando la base. No se dio en clase.</Tarjeta>
</Flashcards>
