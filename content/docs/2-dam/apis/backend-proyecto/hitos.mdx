La **"Planificación por hitos · PI · Acceso a Datos"** reparte el proyecto en **11 hitos semanales acumulativos**: cada semana se revisa una evidencia que funcione y cada hito amplía el anterior. Igual que con los requisitos, el documento se llama "de Acceso a Datos", pero los hitos H6 a H8 y buena parte de H9 a H11 son **backend y base de datos**, que es lo que se explica en este bloque.

<Callout type="info" title="Cómo funcionan los hitos">
  - Cada hito es una semana de trabajo y se revisa con algo que se pueda **ejecutar o comprobar**.
  - Son **genéricos**: no fijan el tema del proyecto, los adaptas a tu modelo.
  - En Navidad (del 21 de diciembre al 10 de enero) **no hay hitos obligatorios**.
  - La secuencia va de frontend a diseño visual, servicios, API, persistencia, integración y lógica de negocio.
</Callout>

## Los 11 hitos

| Hito | Semana | Foco | Qué se revisa |

## H6: el contrato de la API <NoDadoEnClase inline />

<NoDadoEnClase>
  En clase el contrato se documentó con **Swagger** en `/api-docs` (03/11), pero no se diseñó uno desde cero. Esta tabla es una forma sencilla de tenerlo escrito para el H6: qué rutas hay, qué reciben y qué códigos devuelven.
</NoDadoEnClase>

Para la tienda de ejemplo del bloque:

| Método y ruta | Recibe | Responde |
| --- | --- | --- |
| `GET /api/productos` | *Query*: `q`, `categoriaId`, `orden`, `dir`, `page`, `limit` | `200` con `items`, `total`, `page`, `limit` y `totalPages` · `400` si los parámetros están mal |
| `GET /api/productos/:id` | — | `200` con el producto · `404` |
| `POST /api/productos` | *Body*: `nombre`, `precio`, `stock`, `categoriaId` | `201` con el producto creado · `400` · `409` si la `categoriaId` no existe (P2003) |
| `PATCH /api/productos/:id` | *Body* parcial | `200` · `400` · `404` |
| `DELETE /api/productos/:id` | — | `204` · `404` · `409` si está en algún pedido |
| `GET /api/categorias` | — | `200` con cada categoría y su número de productos |
| `GET /api/categorias/:id` | — | `200` con la categoría y sus productos · `404` |
| `POST /api/pedidos/:id/confirmar` | Token en `Authorization` | `200` con el pedido confirmado · `401` · `404` · `409` sin stock |

Angular necesita saber exactamente esto para escribir sus servicios e interfaces en el H5, así que conviene tenerlo **antes** de programar el backend.

## La revisión de cada semana

La revisión **no exige** que cada bloque esté cerrado al 100 %: se mira que haya un avance que se pueda comprobar y que sepas explicarlo.

| Aspecto | Qué tienes que poder enseñar |
| --- | --- |
| Ejecución | El proyecto arranca y se ve el avance. |
| Integración | Lo nuevo no rompe de forma permanente lo anterior. |
| Arquitectura | Se mantiene la separación entre componentes, servicios, API, lógica y persistencia. |
| Trazabilidad | El repositorio refleja el avance con commits y una estructura comprensible. |
| Explicación técnica | Sabes justificar lo que has decidido y decir qué te falta. |
| Rúbrica | En algunos hitos se aplica una rúbrica con lo dado hasta ese momento. |

### Trazabilidad: cómo lo hacía el profesor

<DeClase fecha="27/10, 03/11" proyecto="node-server-26-27" />

El repositorio de referencia del profesor está hecho justo así: un **tag de Git por versión** (de v0.1.0 a v1.1.3), un `CHANGELOG.md` con lo que añade cada versión y commits con prefijo (`feat:`, `fix:`, `docs:`). En clase se recorrió versión a versión con Git Graph y se subieron los tags con `git push origin --tags`.

### Un tag por hito <NoDadoEnClase inline />

<NoDadoEnClase>
  En clase solo se vio cómo **subir** los tags, no cómo crearlos.
</NoDadoEnClase>

Puedes marcar el final de cada hito con un tag anotado, igual que las versiones del profesor:

<Terminal titulo="bash">
{`$ git add .

$ git tag -a h8 -m "H8: endpoints conectados y seed operativo"

$ git push origin --tags`}
</Terminal>

Así, en la revisión puedes enseñar qué había exactamente al cerrar cada hito.

## Ejercicios

<Ejercicio titulo="El contrato de tu API" dificultad="media">
  Escribe para tu proyecto una tabla como la del H6 con **todas** las rutas de tu API: método, ruta, qué reciben (parámetros de la URL, *query* o *body*) y qué códigos devuelven. Incluye al menos el listado principal con búsqueda y paginación y la ruta de tu operación de negocio.

  <Pista>Por cada entidad suelen salir cinco rutas: listar, ver una, crear, modificar y borrar.</Pista>
  <Pista>La operación de negocio no es un CRUD: suele ir como `POST` a una subruta con un verbo, por ejemplo `/api/reservas/:id/cancelar`.</Pista>

  <Solucion>

No hay una única respuesta. Comprueba que tu tabla cumple esto:

- Cada ruta que crea responde `201`; cada ruta que borra, `204`.
- Las rutas con `:id` pueden responder `404`.
- Las que reciben datos pueden responder `400`.
- Las que chocan con un único o con datos relacionados pueden responder `409`.
- Las protegidas pueden responder `401`.
- El listado principal recibe `q`, algún filtro, `orden`, `dir`, `page` y `limit`, y responde con el total.

</Solucion>
</Ejercicio>
