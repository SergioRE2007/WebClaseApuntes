## Las piezas de Git

Antes de los comandos, las cinco palabras que se usaron en clase:

<Glosario titulo="Vocabulario de Git">
  <Termino nombre="Commit">Una foto del proyecto con un mensaje. Tiene un identificador (el *hash*, como `325e9297`) y apunta a su **padre**, el commit anterior. El primero del repositorio no tiene padre: Git Graph lo muestra como `Parents: None`.</Termino>
  <Termino nombre="Rama">Una línea de trabajo que avanza: es un nombre que apunta al último commit de esa línea (`main`, `master`, `vercel-deployment`). Cada commit nuevo mueve la rama actual.</Termino>
  <Termino nombre="Rama remota">La copia que hay en GitHub de una rama, vista desde tu ordenador: `origin/main` es la `main` del remoto `origin`.</Termino>
  <Termino nombre="Tag">Una marca **fija** en un commit, como `v1.0.0`. A diferencia de una rama, no se mueve cuando haces más commits.</Termino>
  <Termino nombre="HEAD">Lo que estás viendo ahora mismo. Normalmente apunta a una rama; si haces checkout de un tag antiguo, queda **separado** (*detached*) en ese commit.</Termino>
</Glosario>

## Crear el repositorio

<DeClase fecha="26/10" proyecto="PokeApp (Android)" />

En la clase de Android se creó el repositorio de las dos formas:

- **Desde Android Studio:** el panel *Version Control*, con **Create Git repository** o **Share on GitHub** (que además lo sube).
- **Desde la terminal** (PowerShell): `git init` y el primer commit.

```bash title="Terminal"
git init
git status
git add .
git commit -m "..."
```

- `git init` crea el repositorio con la rama `main`.
- En Windows sale el aviso `LF will be replaced by CRLF`. **No es un error**: Git avisa de que cambiará los saltos de línea (por la opción `core.autocrlf`). Se puede ignorar.
- En Angular no hace falta: `ng new` inicializa Git solo (28/10, `proj-game`).

## Commits con prefijo

Los mensajes del profesor siguen la convención de **prefijos** (*Conventional Commits*): una palabra que dice qué tipo de cambio es, dos puntos y la descripción.

| Prefijo | Para qué | Dónde salió |
| --- | --- | --- |
| `feat:` | Funcionalidad nueva | Backend (20/10, 27/10, 03/11) y Android (26/10, 09/11) |
| `fix:` | Arreglo | Backend |
| `docs:` | Solo documentación | Backend |
| `chore:` | Configuración o tareas que no cambian el código de la app | Guía de la Act 11 (18/11) |
| `refactor:` | Cambiar el código sin cambiar lo que hace | Guía de la Act 11 (18/11) |

## Un tag por versión

<DeClase fecha="27/10, 03/11" proyecto="node-server-26-27" />

El repositorio de referencia del backend tiene **un tag por hito** (`v0.1.0` ... `v1.1.3`) y **un commit por versión**. Hacer checkout de un tag te enseña el código **exactamente como estaba** en esa versión. El profesor lo usa como una guía que se avanza versión a versión.

Pulsa cualquier versión de la demo para hacer su "checkout" (también con las flechas ↑ y ↓). Fíjate en lo que pasa con HEAD y con los commits de arriba:

<HistorialVersiones />

Lo que enseña la demo, que es lo que dijo el profesor con Git Graph delante:

- Al hacer checkout de un tag antiguo, **HEAD queda separado** (*detached*) en ese commit.
- Los commits posteriores siguen existiendo, pero **no están incluidos en HEAD**. Git Graph lo dice literalmente con un tooltip: "This commit is not included in HEAD".

Para volver a la última versión basta con hacer checkout de la rama `main` otra vez (en clase no se llega a ver ese paso).

### Qué significa vX.Y.Z <NoDadoEnClase inline />

<NoDadoEnClase>
  En clase se usaron los tags de versión semántica y se vieron los rangos `^` y `~` del `package.json` (20/10 y 28/10), pero no se explicó qué significa cada número de un tag. Es el convenio *Semantic Versioning*.
</NoDadoEnClase>

`vMAYOR.MENOR.PARCHE`:

- **MAYOR** (`v1.0.0`): cambios que rompen lo anterior. Por debajo de `1.0.0` se considera que el proyecto aún está en desarrollo, como el repositorio de clase hasta llegar a "Producción y documentación".
- **MENOR** (`v1.1.0`): algo nuevo que no rompe nada, como la subida de archivos con Cloudinary.
- **PARCHE** (`v1.1.2`): arreglos, como los errores de TypeScript del módulo media.

<DeClase fecha="27/10, 03/11" proyecto="node-server-26-27" nota="todo desde la interfaz de Cursor" />

| Opción | Qué hace |
| --- | --- |

### Lo mismo en la terminal <NoDadoEnClase inline />

<NoDadoEnClase />

```bash title="Terminal"
git tag                       # lista los tags
git switch --detach v0.4.0    # ir al tag v0.4.0 (HEAD separado)
git checkout v0.4.0           # lo mismo, con el comando antiguo
git switch main               # volver a la rama main
git log --oneline --graph --all --decorate   # el grafo en la terminal
```

<Callout type="warn" title="Cambios sin guardar">
  Si tienes archivos modificados sin commit, Git puede negarse a cambiar de versión (`Your local changes would be overwritten by checkout`). Haz commit antes, o guárdalos con `git stash`.
</Callout>

## Subir los tags

<DeClase fecha="03/11" proyecto="node-server-26-27" />

Un `git push` normal sube los commits de la rama, pero **no sube los tags**. Hay que pedirlo:

```bash title="Terminal"
git push origin --tags
```

El 03/11 ese comando estaba escrito en la terminal todo el rato.

<NoSeVio titulo="Crear un tag">
  En clase se explicó cómo subir los tags, pero no cómo crearlos.
</NoSeVio>

### Crear un tag <NoDadoEnClase inline />

<NoDadoEnClase />

```bash title="Terminal"
git tag -a v0.1.0 -m "v0.1.0 - Proyecto base"   # tag anotado en el commit actual
git push origin v0.1.0                           # sube solo ese tag
git push origin --tags                           # o todos (lo de clase)
```

- `-a` crea un tag **anotado**: guarda autor, fecha y mensaje, como un commit. Es el recomendado para marcar versiones.
- Sin `-a` ni `-m` (`git tag v0.1.0`) se crea un tag ligero, que es solo un nombre.
- Créalo **después** del commit que cierra la versión: el tag se pone en el commit en el que está HEAD.

## CHANGELOG y README por versiones

<DeClase fecha="27/10, 03/11" proyecto="node-server-26-27" />

Junto a cada tag, el repositorio de referencia tiene su documentación:

- **`CHANGELOG.md`**: un apartado por versión (por ejemplo, "v0.3.0 - PostgreSQL + Docker con Prisma"), con secciones como "Añadido" y "Seguridad en producción". Junto a cada versión hay un commit `docs: actualizar CHANGELOG con vX`.
- **`README.md`**: funciona como **manual completo**, con un índice enlazado por versiones (v0.1.0 ... v1.0.0). Cada versión tiene su **"Objetivo"** y sus pasos.
- **`docs/API_EXAMPLES.md`**: ejemplos de uso de la API, que crecen con cada versión.

Es lo mismo que el Changelog de Confluence del [proyecto real de Jira](/docs/2-dam/proyecto-intermodular/desarrollo-agil-y-jira), pero dentro del repositorio. Para tu proyecto es oro: la revisión semanal de Acceso a Datos mira la **trazabilidad** (que el repositorio refleje el avance con commits).

## Una rama por refactor

<DeClase fecha="12/11, 18/11" proyecto="proj-game" nota="Act 11, «Migración ReactiveForms, Git y Vercel»" />

En la actividad de Angular había que pasar el formulario de juegos a formularios reactivos **en una rama aparte**, sin tocar la rama estable. El patrón:

1. Desde la rama estable y actualizada, crear la rama con `git switch -c`.
2. Trabajar y hacer commits en ella.
3. Subirla con `git push origin <rama>` (o `git push -u`).
4. Abrir una **Pull Request de revisión** contra `main` y **dejarla abierta**.

El 12/11 se leyó el paso 3 de la guía, que empieza así:

```bash title="Guía de la Act 11, paso 3"
git status
git switch main
git pull --ff-only
git switch -c refactor/reactive-forms
git branch --show-current
```

- `git status`: comprobar que no hay nada a medias.
- `git pull --ff-only`: traer lo último de GitHub **solo si se puede avanzar sin mezclar** (*fast-forward*). Si tu rama y la remota se han separado, falla en vez de crear un *merge*.
- `git branch --show-current`: comprobar en qué rama estás antes de seguir.

El 18/11 el profesor lo hizo en directo con su proyecto. Recórrelo paso a paso:

<RamaDeTrabajo />

Los comandos de la demo, tal cual:

```bash title="Terminal (18/11)"
git branch
git switch master
git switch -c refactor/reactive-form2
git add -A .
git commit -m "."
git push origin refactor/reactive-form2
```

- `git switch -c` crea la rama en el commit actual y se cambia a ella ("Switched to a new branch").
- El commit dio `[refactor/reactive-form2 52bc022]`, "3 files changed, 63 insertions(+), 36 deletions(-)" y "create mode 100644 vercel.json". Un segundo `commit` dijo "nothing to commit, working tree clean" y otro `push`, "Everything up-to-date".
- Al subir la rama, GitHub responde con `[new branch]` y el enlace para crear la Pull Request.

<Callout type="warn" title="main o master">
  La guía usa `main` y `feature/reactive-forms`; el profesor trabajó con `master` (su rama principal) y `refactor/reactive-form2`. Ya tenía otra rama, `refactor/reactive-form`, con el refactor hecho, y creó la segunda para repetirlo desde cero. Usa los nombres de tu repositorio.
</Callout>

### La Pull Request de revisión

Es el paso E de la guía: en GitHub se abre la PR con **base `main`** y **compare `feature/reactive-forms`**, con el título "Refactorizar: formularios reactivos". En *Files changed* se comparan los cambios (en clase, `GameService` y la interfaz `Game`) y **la PR se deja abierta**: sirve para revisar, no se fusiona. Mientras, Vercel publica una Preview de la rama; eso está en [Despliegue en Vercel](/docs/2-dam/proyecto-intermodular/despliegue-en-vercel).

## Errores típicos

- **`LF will be replaced by CRLF`** (salió en clase): es un aviso de Windows sobre los saltos de línea, no un error. Se puede ignorar.

<NoDadoEnClase titulo="Otros errores habituales">
  Estos no salieron en clase, pero te los vas a encontrar trabajando en equipo.
</NoDadoEnClase>

- **`Your local changes would be overwritten by checkout`**: hay archivos cambiados sin commit. Muchas veces son archivos de `.idea` que Android Studio cambia solo. Haz commit, `git stash`, o descártalos con `git restore <archivo>` si no son tuyos.
- **No subas la configuración local de Android Studio** (`.idea/workspace.xml`, `.idea/appInsightsSettings.xml`, `local.properties`): ponla en el `.gitignore`.
- **`! [rejected] ... (fetch first)`** al hacer `push`: alguien subió antes que tú. Primero `git pull` y después `push`.
- **Has subido el `.env`**: añádelo al `.gitignore` y cambia las contraseñas y el `JWT_SECRET`. Aunque lo borres, sigue en el historial.
- **`&&` da error en PowerShell**: en la PowerShell de Windows 10 y 11 (la 5.1) no existe `&&`. Ejecuta los comandos de uno en uno o sepáralos con `;`.

## Ejercicios

<Ejercicio titulo="Versiona tu proyecto como el de clase" dificultad="media">
  En el repositorio de tu backend, cierra el hito en el que estés con un commit con prefijo, márcalo con un tag `vX.Y.Z`, añade su apartado al `CHANGELOG.md` y súbelo todo a GitHub, tags incluidos. Después, comprueba en Git Graph que el tag está en el commit correcto.

  <Pista>El tag se pone en el commit en el que está HEAD: primero el commit, después el tag.</Pista>
  <Pista>Recuerda que `git push` no sube los tags.</Pista>

  <Solucion>

```bash title="Terminal"
git add .
git commit -m "feat: CRUD de productos con Prisma"
# añade el apartado "v0.4.0 - CRUD de productos" al CHANGELOG.md
git add CHANGELOG.md
git commit -m "docs: actualizar CHANGELOG con v0.4.0"
git tag -a v0.4.0 -m "v0.4.0 - CRUD de productos"
git push origin main
git push origin --tags
```

Crear el tag con `git tag -a` no se dio en clase; subirlo con `--tags`, sí. En Git Graph el tag `v0.4.0` tiene que salir en el último commit (el del CHANGELOG), así la versión incluye su documentación. En el repositorio de referencia el tag está en el commit de la versión y el `docs: actualizar CHANGELOG con vX` va en un commit aparte: las dos formas valen si las usas siempre igual.

  </Solucion>
</Ejercicio>

<Ejercicio titulo="Lee un commit" dificultad="facil">
  Instala Git Graph, abre el repositorio de tu proyecto y elige un commit cualquiera. Apunta su hash, su padre, cuántos archivos cambió y cuántas líneas añadió y quitó en el más grande. Abre el *diff* de ese archivo y explica en una frase qué cambió.

  <Pista>Si el commit tiene `Parents: None`, has elegido el primero del repositorio.</Pista>

  <Solucion>

No hay una única respuesta. Lo importante es saber sacarlo: el hash y *Parents* están arriba del detalle del commit, la lista de archivos con su `+/-` debajo, y al pinchar un archivo se abre el *diff* (en verde lo añadido y en rojo lo quitado). Es lo que hacía el profesor para explicar qué añadía cada versión.

  </Solucion>
</Ejercicio>
