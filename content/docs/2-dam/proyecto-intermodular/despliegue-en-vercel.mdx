## Los pasos de la guía

<Steps>
  <Step>

#### A. Comprobar antes de subir

```bash title="Terminal"
git branch --show-current
npm ci
npm run build
```

- `git branch --show-current`: estás en la rama buena.
- `npm ci` instala **exactamente** lo que dice `package-lock.json` (es lo mismo que hará Vercel).
- `npm run build` no puede dar errores: si falla aquí, fallará en Vercel.

El build de Angular 19 sin SSR deja la web en **`dist/<proyecto>/browser`**. Esa es la carpeta que se publica:

<Files>
  <Folder name="dist" defaultOpen>
    <Folder name="proj-game" defaultOpen>
      <Folder name="browser" defaultOpen>
        <File name="index.html" />
        <File name="main-*.js" />
        <File name="polyfills-*.js" />
        <File name="styles-*.css" />
        <File name="3rdpartylicenses.txt" />
      </Folder>
      <File name="prerendered-routes.json" />
    </Folder>
  </Folder>
</Files>

Y en el `.gitignore` tienen que estar `/dist` y `/node_modules`: Vercel instala y compila por su cuenta.

</Step>
  <Step>

#### Añadir vercel.json

Se crea en la raíz del proyecto (junto a `package.json`) y se hace commit:

```json title="vercel.json"
{
  "rewrites": [
    { "source": "/(.*)", "destination": "/index.html" }
  ]
}
```

```bash title="Terminal"
git add vercel.json
git commit -m "chore: configure SPA navigation on Vercel"
npm run build
```

Para qué sirve lo tienes más abajo, en "Por qué hace falta el rewrite".

</Step>
  <Step>

#### B. Conectar GitHub con Vercel

En vercel.com: **Add New → Project → Import** y eliges el repositorio. En **Configure Project** revisas:

- **Root Directory**: la carpeta que tiene el `package.json` (la raíz, si el repositorio es solo la web).
- **Framework Preset**: Angular.
- **Build Command**: `npm run build`.
- **Output Directory**: la carpeta que contiene el `index.html` compilado, `dist/<proyecto>/browser`.

Pulsas **Deploy**. La rama `main` queda como **Production Branch**.

</Step>
  <Step>

#### C. Preview por rama

```bash title="Terminal"
git push -u origin feature/reactive-forms
```

Cada push de una rama crea una Preview con su URL. Si la Preview te pide iniciar sesión, es la **Deployment Protection** de Vercel, no un fallo.

</Step>
  <Step>

#### D. Qué funciona en la Preview

La Preview carga el frontend y las **validaciones** del formulario funcionan, pero **guardar no**: la app intenta llamar a JSON Server en `localhost:3000` y el navegador lo bloquea (lo tienes más abajo, en "El límite de la práctica"). Para comprobar las validaciones: al enviar un formulario **inválido**, en la pestaña Network **no debe salir ninguna petición**.

</Step>
  <Step>

#### E. PR de revisión

En GitHub, PR con base `main` y compare `feature/reactive-forms`, título "Refactorizar: formularios reactivos". Se revisa en *Files changed* y **se deja abierta**.

</Step>
  <Step>

#### F. Si algo falla

La tabla de diagnóstico está al final de la página.

</Step>
</Steps>

## Por qué hace falta el rewrite

Una SPA de Angular tiene **un solo** `index.html`. Rutas como `/aula/materiales` no son archivos: las conoce el **Router de Angular**, que corre en el navegador.

- Si entras por `/` y pulsas un enlace (`routerLink`), Angular cambia de pantalla **sin pedir nada al servidor**. Funciona siempre.
- Si **recargas** en `/aula/materiales` (o pegas esa URL), el navegador le pide a Vercel el archivo `/aula/materiales`, que no existe. Sin rewrite, Vercel responde **404**.
- Con el rewrite `/(.*)` → `/index.html`, Vercel sirve `index.html` para cualquier ruta que no sea un archivo real. Angular arranca, lee la URL y pinta la pantalla que toca.

<SimuladorVercel />

Lo que tienes que sacar de la demo:

- Con la Output Directory mal (`dist` en vez de `dist/<proyecto>/browser`) sale **404 incluso en `/`**: Vercel no encuentra ningún `index.html`. El rewrite no lo arregla.
- Con la Output Directory bien y **sin** rewrite, `/` funciona y los enlaces también, pero **recargar una ruta interna da 404**.
- Con las dos cosas bien, todo funciona.
- Vercel **primero busca un archivo real** (por eso `main-*.js` o `styles-*.css` se siguen sirviendo) y solo si no existe aplica el rewrite. <NoDadoEnClase inline /> Este detalle de Vercel no salió en clase.

<Callout type="warn" title="Solo para SPA">
  El rewrite a `index.html` es para una SPA sin SSR, como las de clase. Un proyecto de Angular con SSR se despliega de otra forma.
</Callout>

## Root Directory y Output Directory

Son los dos campos que más fallan:

| Campo | Qué es | En `proj-game` |
| --- | --- | --- |
| Root Directory | La carpeta del repositorio que tiene el `package.json` de la web. | La raíz del repositorio, que solo tenía la web. |
| Output Directory | La carpeta que contiene el `index.html` **compilado**. | `dist/proj-game/browser` |

<NoDadoEnClase titulo="Si tu repositorio tiene backend y frontend">
  Si en el mismo repositorio tienes, por ejemplo, `backend/` y `frontend/`, el Root Directory de Vercel es `frontend` (donde está su `package.json`) y la Output Directory se cuenta desde ahí: `dist/<proyecto>/browser`. En clase el repositorio era solo la web.
</NoDadoEnClase>

## El límite de la práctica: CORS contra localhost

La web publicada en Vercel sigue llamando a `http://localhost:3000/games`, donde estaba JSON Server en el ordenador del profesor. En la consola sale:

```txt title="Consola del navegador"
Access to XMLHttpRequest at 'http://localhost:3000/games?_page=1&_limit=5'
from origin 'https://proj-game-r6lu.vercel.app' has been blocked by CORS policy:
Permission was denied for this request to access the `loopback` address space.
```

- `localhost` es la dirección **de bucle local** (*loopback*): significa "este mismo ordenador". En la web publicada, `localhost` es el ordenador **de quien la visita**, no el tuyo.
- El navegador no deja que una página de un origen público acceda al *loopback*. Por eso la Preview **valida pero no guarda**.
- En la práctica era lo esperado: solo se pedía comprobar el frontend y las validaciones.

<NoSeVio titulo="La web publicada contra una API publicada">
  En clase no se llegó a publicar una API ni a conectar la web desplegada con ella. La rama `vercel-deployment` del backend de referencia no se abre, y se probó `environment.apiUrl` en Angular pero dio error y no se vio `environment.ts`.
</NoSeVio>

### Cómo se conecta con tu API <NoDadoEnClase inline />

<NoDadoEnClase>
  No se ha visto en clase. Es lo que necesitarás para tu proyecto cuando la web y la API estén publicadas.
</NoDadoEnClase>

1. **Publica la API** con `https` (si la web va por `https` y la API por `http`, el navegador da un error de *Mixed Content*).
2. **Permite el origen de tu web en el CORS de la API** (por ejemplo, `https://tu-proyecto.vercel.app`, sin `/` al final). Cómo hacerlo en Express está en [APIs: backend del proyecto](/docs/2-dam/apis/backend-proyecto).
3. **Saca la URL de la API a los *environments* de Angular**, para usar `localhost` en desarrollo y la URL publicada en el build:

```bash title="Terminal"
ng generate environments
```

```ts title="src/environments/environment.ts"
export const environment = {
  apiUrl: 'https://tu-api.example.com/api',
};
```

```ts title="src/environments/environment.development.ts"
export const environment = {
  apiUrl: 'http://localhost:3000/api',
};
```

```ts title="src/app/services/game.service.ts"
import { environment } from '../../environments/environment';

@Injectable({ providedIn: 'root' })
export class GameService {
  private readonly http = inject(HttpClient);
  private readonly apiUrl = `${environment.apiUrl}/games`;
}
```

`ng generate environments` crea los dos archivos y añade a `angular.json` el reemplazo de `environment.ts` por `environment.development.ts` en la configuración de desarrollo (`ng serve`). `npm run build` usa la de producción, así que coge la URL publicada. Importa siempre `environment.ts`, nunca el de desarrollo.
