Este bloque explica **cómo se monta una app de Android por dentro**, siguiendo lo que se hizo en clase de octubre a noviembre. No va de pintar botones (eso es Compose), sino de **dónde vive cada cosa**: quién guarda el estado, quién habla con los datos, quién crea los objetos y cómo se pasa de una pantalla a otra.

El hilo conductor es la **ToDoApp** de clase (paquete `com.alanturing.todoapp`, rama `dev`), una lista de tareas que el profesor fue construyendo entre el 09/10 y el 23/10. Cuando algo se vio en otro proyecto (TipCalculator, PokeApp2627, Room o ToDoOfflineFirst), se dice.

<Callout type="idea" title="Antes de empezar">
  Se da por hecho que sabes Java y lo básico de Kotlin y Compose (`@Composable`, `Scaffold`, `LazyColumn`, `remember`). Si vienes de Java, cada página compara con lo que ya conoces cuando ayuda.
</Callout>

## Qué clases cubre

| Fecha | Proyecto | Lo que sale en este bloque |

| 07/10 | TipCalculator | El estado pasa del composable a un `ViewModel` con una `data class`, `copy()` y backing property. |

Aquí solo se nombra cuando hace falta para entender una capa.

## Cómo leer las marcas

El material sale de las capturas de los vídeos de clase, así que cada página separa lo que se vio de lo que no:

- <DeClase fecha="09/10" proyecto="ToDoApp" /> dice cuándo y dónde se vio algo.
- <NoDadoEnClase inline /> marca lo que **no se dio en clase**. Si lo usas en tu proyecto, di que lo has buscado tú.
- <Dudoso>Así</Dudoso> se marca lo que no se leía bien en las capturas. No está corregido a propósito.
- Los recuadros "Esto no se llega a ver en clase" señalan huecos: código que no sale en las capturas. No se rellenan con código inventado.
- Los bloques con "Así se hizo en clase" y "Mejor así" son las **prácticas raras** del código de clase: cosas que se hicieron así en directo y que no conviene copiar.
