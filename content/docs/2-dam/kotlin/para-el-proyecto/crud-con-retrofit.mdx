## Lo que se vio en clase

<DeClase fecha="26/10" proyecto="PokeApp2627" nota="versión del 09/11" />

Una interfaz con funciones `suspend` que devuelven `Response<T>`, `@GET` con `@Path`, y DTO con `@SerializedName` para los nombres que no coinciden con el JSON:

```kotlin title="PokeApi.kt y PokemonApiModels.kt (09/11)"
interface PokeApi {
    @GET("pokemon")
    suspend fun readAllPokemon(): Response<PokemonListResult>
    @GET("pokemon/{name}")
    suspend fun readPokemonByName(@Path(value = "name") name: String): Response<PokemonResult>
    @GET("pokemon/{id}")
    suspend fun readPokemonById(@Path(value = "id") id: Int): Response<PokemonResult>
}

data class PokemonResult(val id: Int, val name: String, val sprites: PokemonSprites?)
data class PokemonSprites(@SerializedName("front_default") val frontDefault: String)
data class PokemonListResult(val results: List<PokemonListItemResult>)
data class PokemonListItemResult(val name: String, val url: String)
```

- `Response<T>` tiene `isSuccessful` (código 2xx) y `body()`, que es **nulable**.
- Antes de escribir las `data class` se miró el JSON real en **Postman** (`GET https://pokeapi.co/api/v2/pokemon/`).
- El listado de PokeAPI se pagina con `limit` y `offset`, y no trae la imagen: está en el detalle (`sprites.front_default`). Por eso se hacían N+1 peticiones.

Lo de clase lo tienes en [Retrofit 3 con Gson: la capa remota](/docs/2-dam/kotlin/datos/retrofit).

### Los DTO

Tu backend devuelve el listado **paginado**: un objeto con los `items` y los datos de la página (aquí, recortado al primer producto de tres).

```json title="GET api/productos (respuesta del backend)"
{
  "items": [
    { "id": 1, "nombre": "Ratón inalámbrico", "precio": "24.5", "stock": 30, "categoria": { "id": 1, "nombre": "Periféricos" } }
  ],
  "total": 3,
  "page": 1,
  "limit": 10,
  "totalPages": 1
}
```

Cada campo del JSON es una propiedad del DTO, con el **mismo nombre**:

```kotlin title="TiendaApiModels.kt"
data class PaginaDto<T>(
    val items: List<T>,
    val total: Int,
    val page: Int,
    val limit: Int,
    val totalPages: Int
)

data class CategoriaDto(val id: Int, val nombre: String)

data class ProductoDto(
    val id: Int,
    val nombre: String,
    val precio: String,
    val stock: Int,
    val categoria: CategoriaDto
)

data class NuevoProductoDto(
    val nombre: String,
    val precio: Double,
    val stock: Int,
    val categoriaId: Int
)
```

- `PaginaDto<T>` es **genérica**: vale para el listado de productos (`PaginaDto<ProductoDto>`) y para el de cualquier otro modelo. Como un `Pagina<T>` en Java.
- `precio` es `String` en `ProductoDto` porque Prisma manda los `Decimal` como texto (`"24.5"`).
- Cómo se hace ese listado en el backend está en [Listado con búsqueda, filtro, orden y paginación](/docs/2-dam/apis/backend-proyecto/listado-paginado).

### La interfaz

<Recorrido
  titulo="TiendaApi.kt"
  lenguaje="kotlin"
  codigo={`interface TiendaApi {
    @GET("api/productos")
    suspend fun getProductos(
        @Query("q") q: String? = null,
        @Query("page") page: Int = 1,
        @Query("limit") limit: Int = 50
    ): Response<PaginaDto<ProductoDto>>

    @GET("api/productos/{id}")
    suspend fun getProducto(@Path("id") id: Int): Response<ProductoDto>

    @POST("api/productos")
    suspend fun crearProducto(@Body producto: NuevoProductoDto): Response<ProductoDto>

    @PUT("api/productos/{id}")
    suspend fun actualizarProducto(
        @Path("id") id: Int,
        @Body producto: NuevoProductoDto
    ): Response<ProductoDto>

    @DELETE("api/productos/{id}")
    suspend fun borrarProducto(@Path("id") id: Int): Response<Unit>
}`}
>
  <Paso lineas="2-7" titulo="Listar con parámetros">
    `@Query("q")` añade `?q=...` a la URL. Si el valor es `null`, Retrofit no lo pone. Con los valores por defecto, `getProductos()` pide `api/productos?page=1&limit=50`.
  </Paso>
  <Paso lineas="7" titulo="El tipo tiene que cuadrar con el JSON">
    El backend devuelve un objeto con `items`, no una lista. Si pusieras `Response<List<ProductoDto>>`, Gson fallaría con `Expected BEGIN_ARRAY but was BEGIN_OBJECT`.
  </Paso>
  <Paso lineas="9-10" titulo="Leer uno">
    `@Path("id")` cambia `{id}` en la ruta por el valor del parámetro, como en clase.
  </Paso>
  <Paso lineas="12-13" titulo="Crear">
    `@POST` con `@Body`: Gson convierte el objeto en el JSON del cuerpo. La API devuelve el producto creado, ya con su `id`.
  </Paso>
  <Paso lineas="15-19" titulo="Editar">
    `@PUT` lleva las dos cosas: el `id` en la ruta y los datos nuevos en el cuerpo.
  </Paso>
  <Paso lineas="21-22" titulo="Borrar">
    `Response<Unit>` para cuando la API no devuelve nada (un `204 No Content` al borrar).
  </Paso>
</Recorrido>

| Anotación | Dónde va | Qué hace |
| --- | --- | --- |
| `@GET`, `@POST`, `@PUT`, `@DELETE` | En la función | El verbo HTTP y la ruta (sin `/` inicial) |
| `@Path("id")` | En un parámetro | Sustituye `{id}` en la ruta |
| `@Query("q")` | En un parámetro | Añade `?q=valor` a la URL; si es `null`, no lo pone |
| `@Body` | En un parámetro | Manda el objeto como JSON en el cuerpo |
| `@SerializedName("x")` | En una propiedad del DTO | Cuando el nombre en el JSON no es igual que en Kotlin |

<Callout type="warn" title="Hay dos @Query">
  El `@Query` de Retrofit (`retrofit2.http.Query`) no tiene nada que ver con el de Room (`androidx.room3.Query`). Si la interfaz de Retrofit y el DAO están en el mismo archivo, o Android Studio importa el que no es, salen errores muy raros. Ten cada uno en su archivo y mira el `import`.
</Callout>

- Los nombres de las propiedades tienen que ser **iguales** que los del JSON. Si no, `@SerializedName("nombre_en_json")` encima de la propiedad, como el `front_default` de clase.

### Después de cambiar algo en la API

Lo que hay en la pantalla sale de Room ([Room como fuente de verdad](/docs/2-dam/kotlin/para-el-proyecto/offline-first)). Así que después de crear, editar o borrar en la API, **hay que dejar Room igual**, y la pantalla se actualiza sola.

<Mermaid
  titulo="Crear un producto"
  chart={`sequenceDiagram
    participant VM as ViewModel
    participant R as Repositorio
    participant A as API
    participant DB as Room
    VM->>R: crear(nuevo)
    R->>A: POST api/productos
    A-->>R: 201 Created
    R->>A: GET api/productos (refresh)
    A-->>R: 200 OK con la lista
    R->>DB: upsert de categorías y productos
    DB-->>VM: el Flow emite la lista nueva`}
/>

Amplía la interfaz del repositorio con las tres operaciones:

```kotlin title="ProductoRepository.kt"
interface ProductoRepository {
    val productos: Flow<List<Producto>>
    suspend fun refresh()
    suspend fun crear(producto: NuevoProductoDto)
    suspend fun actualizar(id: Int, producto: NuevoProductoDto)
    suspend fun borrar(id: Int)
}

class ProductoRepositoryImpl @Inject constructor(
    private val dao: TiendaDao,
    private val api: TiendaApi
) : ProductoRepository {

    // productos y refresh(), como en la página anterior

    override suspend fun crear(producto: NuevoProductoDto) {
        val respuesta = api.crearProducto(producto)
        if (!respuesta.isSuccessful) {
            throw IOException("La API respondió ${respuesta.code()}")
        }
        refresh()
    }

    override suspend fun actualizar(id: Int, producto: NuevoProductoDto) {
        val respuesta = api.actualizarProducto(id, producto)
        if (!respuesta.isSuccessful) {
            throw IOException("La API respondió ${respuesta.code()}")
        }
        refresh()
    }

    override suspend fun borrar(id: Int) {
        val respuesta = api.borrarProducto(id)
        if (!respuesta.isSuccessful) {
            throw IOException("La API respondió ${respuesta.code()}")
        }
        dao.deleteProductoPorId(id)
    }
}
```

Y en el DAO, una consulta para borrar por id:

```kotlin title="TiendaDao.kt"
@Query("DELETE FROM producto WHERE id = :id")
suspend fun deleteProductoPorId(id: Int)
```

- Al crear y al editar basta con `refresh()`: trae la lista de la API y hace `@Upsert`, que inserta lo nuevo y actualiza lo cambiado.
- **Al borrar, `refresh()` no basta.** `@Upsert` nunca borra: el producto que ya no está en la API seguiría en Room. Por eso se borra a mano del DAO.
- Si la API responde un `400` por un dato mal escrito, el mensaje del backend está en `respuesta.errorBody()?.string()` (el JSON del error, como texto).
- `refresh()` pide solo la primera página (50 productos). Si tu app va a tener más, pide todas las páginas (`page = 2`, `3`… hasta `totalPages`). Subir el `limit` no sirve: el backend de ejemplo no admite más de 50 y responde un `400`.

<Flashcards titulo="Repaso: CRUD con Retrofit">
  <Tarjeta frente="`@Path` frente a `@Query`">`@Path("id")` cambia `{id}` dentro de la ruta. `@Query("q")` añade `?q=valor` al final.</Tarjeta>
  <Tarjeta frente="`@Body`">Manda un objeto como JSON en el cuerpo. Se usa en `POST` y `PUT`.</Tarjeta>
  <Tarjeta frente="`Response<Unit>`">Para respuestas sin cuerpo, como un `204` al borrar.</Tarjeta>
  <Tarjeta frente="DTO de recibir frente a DTO de mandar">El de recibir lleva `id` y los datos anidados. El de mandar, sin `id` y con los ids de las relaciones.</Tarjeta>
  <Tarjeta frente="`PaginaDto<T>`">DTO genérico para el listado paginado del backend: `items`, `total`, `page`, `limit` y `totalPages`.</Tarjeta>

<Ejercicio titulo="Borrar una categoría con productos" dificultad="dificil">
  Escribe `borrarCategoria(id)` en el repositorio. Ten en cuenta que en Room la clave ajena tiene `onDelete = ForeignKey.CASCADE`.

  <Pista>Necesitas en el DAO un `@Query("DELETE FROM categoria WHERE id = :id")`.</Pista>
  <Pista>¿Qué pasa con los productos de esa categoría en Room cuando la borras? ¿Y en el backend?</Pista>

  <Solucion>

```kotlin title="TiendaDao.kt"
@Query("DELETE FROM categoria WHERE id = :id")
suspend fun deleteCategoriaPorId(id: Int)
```

```kotlin title="ProductoRepositoryImpl.kt"
override suspend fun borrarCategoria(id: Int) {
    val respuesta = api.borrarCategoria(id)
    if (!respuesta.isSuccessful) {
        throw IOException("La API respondió ${respuesta.code()}")
    }
    dao.deleteCategoriaPorId(id)
}
```

  Con `CASCADE`, al borrar la categoría en Room se borran solos sus productos, así que no hace falta borrarlos uno a uno. Lo importante es que **el backend haga lo mismo** (en Prisma, `onDelete: Cascade` en la relación). Si el backend no deja borrar una categoría con productos, responderá un error y la función lanzará la excepción antes de tocar Room.

  </Solucion>
</Ejercicio>
