Una app **offline-first** enseña siempre lo que tiene guardado en el móvil y lo actualiza desde la red cuando puede. Si no hay internet, sigue funcionando con lo último que guardó. El 09/11 la PokeApp2627 empezó a funcionar así, primero con una fuente local en memoria, y el 16/11 se vio ya leyendo de Room.

<DeClase fecha="09/11, 16/11" proyecto="PokeApp2627" nota="el 16/11 es un fragmento de 3 minutos" />

<Callout type="idea" title="Lo que vas a aprender">
  - Qué es la fuente única de verdad y por qué la pantalla lee siempre de la fuente local.
  - Añadir una fuente local (`PokemonLocalDataSource`) junto a la remota y conectarlas con Hilt.
  - Escribir `refresh()`, que copia de la API a la fuente local.
  - Qué se vio de la PokeApp con Room y qué se quedó sin ver.
</Callout>

## La idea: una sola fuente de verdad

Hasta ahora el repositorio solo delegaba en la API. Ahora tiene **dos** fuentes de datos, y la pantalla **solo lee de la local**:

<Mermaid
  titulo="Repositorio offline-first"
  chart={`flowchart LR
    VM[ViewModel] -- "observa pokemons" --> R[PokemonRepositoryImpl]
    R -- "lee siempre de aquí" --> L[(PokemonLocalDataSource)]
    R -- "refresh(): descarga" --> RE[PokemonRemoteDataSource]
    RE --> API[(PokeAPI)]
    R -- "refresh(): guarda" --> L`}
/>

- La fuente **local** es la *fuente de verdad*: lo que la pantalla enseña sale de ahí.
- `refresh()` baja los datos de la **remota** y los guarda en la local.
- Si la fuente local avisa cuando cambia (un `Flow` que vuelve a emitir), la pantalla se actualiza sola en cuanto llegan los datos.

## Paso 2: la fuente local en memoria

```kotlin title="data/local/PokemonLocalDataSource.kt"
interface PokemonLocalDataSource {
    val pokemons: Flow<List<Pokemon>>
    suspend fun save(pokemons: List<Pokemon>)
}
```

```kotlin title="data/local/PokemonInMemoryDataSource.kt"
class PokemonInMemoryDataSource @Inject constructor() : PokemonLocalDataSource {
    private val _pokemons: MutableList<Pokemon> = mutableListOf()

    override val pokemons: Flow<List<Pokemon>> = flow {
        emit(_pokemons)
    }

    override suspend fun save(pokemons: List<Pokemon>) {
        _pokemons.clear()
        _pokemons.addAll(pokemons)
    }
}
```

Por el camino salieron varios errores que enseñan bien `val`, `var`, `List` y `MutableList`:

- Primero se escribió `save(List<Pokemon>)` en la interfaz, sin nombre de parámetro: en Kotlin cada parámetro lleva nombre y tipo.
- Con `val _pokemons` y `_pokemons = pokemons` dentro de `save()`: no se puede reasignar una `val`. Se probó con `var`.
- Al final queda `val` de tipo **`MutableList`**: la referencia no cambia, pero su **contenido sí** (`clear()` y `addAll()`). Es como un `final List` de Java, al que sí puedes añadir elementos.
- `listOf()` crea una lista **inmutable**; para poder llamar a `clear()` hace falta `mutableListOf()`.
- La implementación necesita `@Inject constructor()` (import `javax.inject.Inject`) para que Hilt sepa crearla.

## Paso 3: atar las tres interfaces con Hilt

```kotlin title="core/di/AppModule.kt"
@Module
@InstallIn(SingletonComponent::class)
interface AppModule {
    @Binds @Singleton
    fun bindsPokemonRemoteDataSource(ds: PokemonRemoteDataSourceImpl): PokemonRemoteDataSource

    @Binds @Singleton
    fun bindPokemonLocalDataSource(ds: PokemonInMemoryDataSource): PokemonLocalDataSource

    @Binds @Singleton
    fun bindsPokemonRepository(r: PokemonRepositoryImpl): PokemonRepository
}
```

Aquí `@Singleton` importa de verdad: la fuente en memoria guarda la lista en un atributo, así que tiene que haber **una sola** para toda la app. Que los nombres no sigan el mismo patrón (`binds...` y `bind...`) no afecta.

- La carga del `init` tiene su propia historia (`withContext`, `runBlocking`, `CoroutineScope(Dispatchers.IO)` y la pantalla en blanco): está en [Corrutinas](/docs/2-dam/kotlin/datos/corrutinas#cargar-datos-al-crear-el-repositorio).
- Con la fuente en memoria hay una trampa: `flow { emit(_pokemons) }` emite **una sola vez**, cuando alguien lo recoge. Si `refresh()` termina después, nadie se entera. Por eso con `runBlocking` (que garantiza que los datos ya están guardados antes de que se recoja nada) la lista sale, y con `launch` sale en blanco <Dudoso nota="Es la interpretación del resumen de clase; no se ve la explicación del profesor." />.

## La pantalla de detalle

La lista ya se explicó en [Flow y stateIn](/docs/2-dam/kotlin/datos/flow-y-statein). El detalle sigue la misma receta, pero necesita saber **qué pokémon** enseñar. Lo lee de la ruta de navegación con `SavedStateHandle`:

```kotlin title="ui/PokemonDetailViewModel.kt"
@HiltViewModel
class PokemonDetailViewModel @Inject constructor(
    private val _repository: PokemonRepository,
    savedStateHandle: SavedStateHandle,
) : ViewModel() {
    private val _route = savedStateHandle.toRoute<Routes.Detail>()
    private val _id = _route.id

    val state: StateFlow<PokemonDetailScreenState> = _repository.observePokemon(_id)
        .map { pokemon ->
            if (pokemon != null) PokemonDetailScreenState.Loaded(pokemon)
            else PokemonDetailScreenState.Initial
        }.stateIn(
            scope = viewModelScope,
            initialValue = PokemonDetailScreenState.Initial,
            started = SharingStarted.WhileSubscribed(5_000L)
        )
}
```

- `@HiltViewModel` no se ve en las capturas <Dudoso nota="Se ha puesto porque es obligatorio: el 18/11 el propio profesor enseña que sin él la app se cae." />.
- `savedStateHandle.toRoute<Routes.Detail>()` reconstruye la ruta tipada con la que se navegó y de ella sale el `id`. Hilt rellena el `SavedStateHandle` solo. La navegación está en [Navegación con rutas tipadas](/docs/2-dam/kotlin/arquitectura/navegacion).
- Aquí el `map` usa un `if`/`else` como expresión y una lambda con el parámetro con nombre (`pokemon ->`) en vez de `it`. Primero se escribió con genéricos explícitos, `map<Pokemon?, PokemonDetailScreenState>`, y al final se quitaron: Kotlin deduce el tipo común de las dos ramas.
- Al principio el ViewModel tenía además un `init` con `_state.value = ...`, pero `_state` estaba comentado y daba error. No se ve si al final se borró.

## Cómo se suele terminar <NoDadoEnClase inline />

<NoDadoEnClase>
  Esto no se vio en clase: es la forma más estándar de rematar lo que se empezó el 09/11 y el 16/11. Los nombres (`observeAll`, `upsert`…) son inventados, no del profesor. La versión completa, con dos tablas relacionadas, manejo de errores y estado `Error`, está en [Room como fuente de verdad](/docs/2-dam/kotlin/para-el-proyecto/offline-first).
</NoDadoEnClase>

**1. El DAO devuelve `Flow`.** Las consultas que devuelven `Flow` **no** llevan `suspend`: el `Flow` ya avisa cada vez que cambia la tabla. Las que escriben, sí.

```kotlin title="PokemonDao.kt"
@Dao
interface PokemonDao {
    @Query("SELECT * FROM pokemon")
    fun observeAll(): Flow<List<PokemonEntity>>

    @Query("SELECT * FROM pokemon WHERE id = :id")
    fun observeById(id: Int): Flow<PokemonEntity?>

    @Upsert
    suspend fun upsert(pokemons: List<PokemonEntity>)
}
```

`@Upsert` inserta si la fila no existe y la actualiza si ya existe, así que `refresh()` se puede llamar muchas veces sin errores de clave duplicada.

**2. La fuente local pasa entidades a modelo y al revés.**

```kotlin title="PokemonLocalDBDatasource.kt"
fun PokemonEntity.toModel() = Pokemon(id = id, name = name, pokemonImageUrl = imageUrl)
fun Pokemon.toEntity() = PokemonEntity(id = id, name = name, imageUrl = pokemonImageUrl)

class PokemonLocalDBDatasource @Inject constructor(
    private val _dao: PokemonDao
) : PokemonLocalDataSource {
    override val pokemons: Flow<List<Pokemon>> =
        _dao.observeAll().map { lista -> lista.map { it.toModel() } }

    override fun observePokemon(id: Int): Flow<Pokemon?> =
        _dao.observeById(id).map { it?.toModel() }

    override suspend fun save(pokemons: List<Pokemon>) {
        _dao.upsert(pokemons.map { it.toEntity() })
    }
}
```

Para esto `PokemonLocalDataSource` declara también `fun observePokemon(id: Int): Flow<Pokemon?>`, y el modelo `Pokemon` tiene `pokemonImageUrl: String?`.

**3. `refresh()` lo lanza el ViewModel**, con `viewModelScope.launch`, en vez del `runBlocking` del repositorio (ver [Corrutinas](/docs/2-dam/kotlin/datos/corrutinas#cargar-datos-al-crear-el-repositorio)). Para eso `refresh()` pasa a la interfaz `PokemonRepository`.

<Ejercicio titulo="Una fuente en memoria que sí avisa" dificultad="dificil">
  La `PokemonInMemoryDataSource` de clase usa `flow { emit(_pokemons) }`, que emite una sola vez. Reescríbela para que **vuelva a emitir** cada vez que se llama a `save()`, de modo que la lista se actualice aunque `refresh()` termine después de que la pantalla empiece a recoger.

  <Pista>Necesitas un `Flow` que guarde un valor actual y emita cuando cambia: un `MutableStateFlow`.</Pista>
  <Pista>Un `StateFlow` no emite si el valor nuevo es igual al anterior. Asigna una lista **nueva**, no la misma lista cambiada por dentro.</Pista>

  <Solucion>

```kotlin
class PokemonInMemoryDataSource @Inject constructor() : PokemonLocalDataSource {
    private val _pokemons = MutableStateFlow<List<Pokemon>>(emptyList())

    override val pokemons: Flow<List<Pokemon>> = _pokemons.asStateFlow()

    override suspend fun save(pokemons: List<Pokemon>) {
        _pokemons.value = pokemons.toList()
    }
}
```

  Cada `save()` pone una lista nueva en el `MutableStateFlow` y este emite. Si se hiciera `clear()` + `addAll()` sobre una misma `MutableList` y se volviera a asignar esa lista, el `StateFlow` no emitiría, porque el valor "nuevo" sería el mismo objeto. Esto no es de clase: es un ejercicio para entender el problema de la pantalla en blanco.

  </Solucion>
</Ejercicio>
