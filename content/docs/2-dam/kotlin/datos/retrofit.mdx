**Retrofit** convierte una **interfaz de Kotlin** en llamadas HTTP: tú escribes las funciones con anotaciones (`@GET`, `@Path`…) y Retrofit genera el código que monta la URL, hace la petición y convierte el JSON en objetos con **Gson**. Es lo que se usó el 26/10 para que la PokeApp2627 leyera de [PokeAPI](/docs/2-dam/kotlin/datos/pokeapi-y-postman).

## 1. La interfaz de la API

Cada función es un endpoint. La anotación dice el verbo y la ruta, y los parámetros con `@Path` rellenan los huecos `{...}` de la ruta.

```kotlin title="features/pokemon/data/remote/PokeApi.kt"
interface PokeApi {
    @GET("pokemon")
    suspend fun readAllPokemon(): Response<PokemonListResult>

    @GET("pokemon/{name}")
    suspend fun readPokemonByName(@Path(value = "name") name: String): Response<PokemonResult>

    @GET("pokemon/{id}")
    suspend fun readPokemonById(@Path(value = "id") id: Int): Response<PokemonResult>
}
```

- Es una `interface`: **no la implementas tú**. Retrofit crea la implementación con `retrofit.create(PokeApi::class.java)`.
- Las funciones son `suspend`: Retrofit hace la petición sin bloquear el hilo principal, así que se pueden llamar desde `viewModelScope.launch` (ver [Corrutinas](/docs/2-dam/kotlin/datos/corrutinas)).
- `@Path(value = "name")` sustituye `{name}` por el valor del parámetro: `readPokemonByName("pikachu")` pide `pokemon/pikachu`.
- `readPokemonById` está en la interfaz, pero en lo que se ve en clase no se llega a usar.

### `Response<T>`

El 26/10 el tipo de retorno pasa de `PokemonListResult` a **`Response<PokemonListResult>`**. Con `Response` no solo tienes el cuerpo, también la información de la respuesta HTTP:

| Miembro | Qué da |
| --- | --- |
| `isSuccessful` | `true` si el código es 2xx. |
| `body()` | El cuerpo ya convertido por Gson. Es **nulable**: si la respuesta no fue bien, es `null`. |
| `code()` | El código HTTP (200, 404…). <NoDadoEnClase inline /> |

El tooltip del IDE avisa de que `body()` es `@Nullable`, y por eso en clase se escribe `body()!!`. Más abajo verás por qué eso no conviene copiarlo.

## 2. DTO, modelo y `toModel()`

La forma del JSON y la forma que quiere la app no tienen por qué coincidir. En clase se separan:

- Los **DTO** (*Data Transfer Object*): las `data class` con la misma forma que el JSON. Van en `PokemonApiModels.kt`.
- El **modelo**: `Pokemon`, la clase que usa el resto de la app. No sabe nada de JSON.

```kotlin title="features/pokemon/data/remote/PokemonApiModels.kt (versión del 09/11)"
data class PokemonResult(val id: Int, val name: String, val sprites: PokemonSprites?)
data class PokemonSprites(@SerializedName("front_default") val frontDefault: String)
data class PokemonListResult(val results: List<PokemonListItemResult>)
data class PokemonListItemResult(val name: String, val url: String)

fun PokemonResult.toModel(): Pokemon = Pokemon(
    id = this.id,
    name = this.name,
    pokemonImageUrl = this.sprites?.frontDefault,
)
```

- La línea `name = this.name` de `toModel()` sale tapada por un tooltip en las capturas del 09/11 <Dudoso />.
- Una `data class` por cada objeto JSON y una `List` por cada array. Los campos del JSON que no están en la clase (`count`, `next`…) se ignoran.
- **`@SerializedName("front_default")`**: el JSON trae `front_default` y la propiedad se llama `frontDefault`. Gson empareja por nombre, así que sin la anotación esa propiedad se quedaría a `null`. El 26/10 aún no estaba, y la anotación aparece el 09/11.
- El 26/10 `sprites` era `PokemonSprites` (no nulable). El 09/11 pasa a `PokemonSprites?` y en `toModel()` se lee con `?.`.

### La función de extensión `toModel()`

`fun PokemonResult.toModel(): Pokemon` es una **función de extensión**: se "añade" a `PokemonResult` sin tocar la clase, y se llama como si fuera suya, `body.toModel()`. Dentro, `this` es el objeto que la llama.

<Comparar columnas titulo="Lo mismo en Java y en Kotlin">

```java
    return new Pokemon(r.id, r.name,
        r.sprites != null
            ? r.sprites.frontDefault
            : null);
}
// Uso: toModel(body)
```

  </Lado>
  <Lado titulo="Kotlin">

```kotlin
fun PokemonResult.toModel() = Pokemon(
    id = this.id,
    name = this.name,
    pokemonImageUrl =
        this.sprites?.frontDefault,
)
// Uso: body.toModel()
```

  </Lado>
</Comparar>

El modelo del 26/10 es `data class Pokemon(val id: Int, val name: String, val pokemonImageUrl: String)`. Para que compile el `toModel()` del 09/11, `pokemonImageUrl` tiene que ser `String?`, pero esa versión del modelo no se ve en las capturas.

## 3. El DataSource

El DataSource es la clase que habla con **una sola fuente** de datos, aquí la API. Hay una interfaz y una implementación que recibe `PokeApi` por el constructor:

```kotlin title="features/pokemon/data/remote/PokemonRemoteDataSource.kt"
interface PokemonRemoteDataSource {
    val pokemons: Flow<List<Pokemon>>
    suspend fun readAllPokemon(): List<Pokemon>
    suspend fun readPokemonByName(name: String): Pokemon?
    suspend fun readPokemonById(id: Int): Pokemon?
}
```

`val pokemons: Flow<...>` se añadió el 09/11 y se explica en [Flow y stateIn](/docs/2-dam/kotlin/datos/flow-y-statein). Esta es la implementación, paso a paso:

<Recorrido
  titulo="features/pokemon/data/remote/PokemonRemoteDataSourceImpl.kt"
  lenguaje="kotlin"
  codigo={`class PokemonRemoteDataSourceImpl @Inject constructor(
    private val _api: PokeApi
) : PokemonRemoteDataSource {
    override val pokemons: Flow<List<Pokemon>> = flow { emit(readAllPokemon()) }

    override suspend fun readAllPokemon(): List<Pokemon> {
        val response = _api.readAllPokemon()
        val pokemons = mutableListOf<Pokemon>()
        if (response.isSuccessful) {
            val body = response.body()!!
            for (item in body.results) {
                val pokemon = readPokemonByName(item.name)
                pokemons.add(pokemon!!)
            }
        }
        return pokemons
    }

    override suspend fun readPokemonByName(name: String): Pokemon? {
        val response = _api.readPokemonByName(name)
        if (response.isSuccessful) {
            return response.body()!!.toModel()
        } else {
            return null
        }
    }
}`}
>
  <Paso lineas="1-3" titulo="Recibe la API por el constructor">
    `@Inject constructor(private val _api: PokeApi)`: Hilt le pasa la `PokeApi` que crea el `NetworkModule`. La clase no sabe cómo se construye Retrofit.
  </Paso>
  <Paso lineas="7" titulo="La petición del listado">
    `_api.readAllPokemon()` es `suspend`: aquí la corrutina espera la respuesta sin bloquear.
  </Paso>
  <Paso lineas="8" titulo="Una lista que se va llenando">
    `mutableListOf<Pokemon>()` es como un `new ArrayList<>()` de Java. Es `val`, pero su contenido sí cambia.
  </Paso>
  <Paso lineas="9-10" titulo="Comprobar la respuesta">
    Solo si el código es 2xx se lee el cuerpo. `body()` es nulable y aquí se fuerza con `!!`.
  </Paso>
  <Paso lineas="11-14" titulo="N+1 peticiones">
    El listado no trae la imagen, así que por cada elemento se pide el detalle con `readPokemonByName(item.name)`. Con 20 resultados son 21 peticiones, una detrás de otra.
  </Paso>
  <Paso lineas="16" titulo="Devuelve el modelo">
    Fuera del DataSource solo sale `List<Pokemon>`: ni `Response`, ni DTO. Si la API falla, la lista vuelve vacía.
  </Paso>
  <Paso lineas="19-25" titulo="El detalle">
    Pide un pokémon por nombre y lo pasa al modelo con `toModel()`. Si la respuesta no es 2xx, devuelve `null`; por eso el tipo es `Pokemon?`.
  </Paso>
</Recorrido>

- El 26/10 la rama `else` de `readAllPokemon()` solo tiene el comentario `// Mostrar un error!`: no se ve cómo se informa del error.
- Por el camino salió el error de tipos *expected Pokemon, actual PokemonListItemResult*: se intentaba meter en la lista el elemento del listado en vez del pokémon del detalle.

## 4. El repositorio

El repositorio es lo que ve el ViewModel. Recibe el DataSource por el constructor (con `javax.inject.Inject`, importado con Alt+Mayús+Intro) y, de momento, solo delega:

```kotlin title="features/pokemon/data/repository/PokemonRepositoryImpl.kt (09/11, bloque 1, con el nombre nuevo de la interfaz)"
class PokemonRepositoryImpl @Inject constructor(
    private val _remoteDataSource: PokemonRemoteDataSource
) : PokemonRepository {
    override val pokemons: Flow<List<Pokemon>> = _remoteDataSource.pokemons

    override suspend fun readAllPokemon(): List<Pokemon> {
        return _remoteDataSource.readAllPokemon()
    }

    override suspend fun readPokemonById(id: Int): Pokemon? {
        return _remoteDataSource.readPokemonById(id)
    }
}
```

El 26/10 el repositorio acaba la clase con sus funciones en `TODO("Not yet implemented")`, que compila (devuelve `Nothing`) pero lanza `NotImplementedError` si se llama. Por qué tener un repositorio que solo delega se ve en [Offline-first](/docs/2-dam/kotlin/datos/offline-first): ahí decide entre la fuente remota y la local.

## 5. Conectarlo todo con Hilt

### `NetworkModule`: construir Retrofit

Retrofit no se crea con `@Inject constructor`: hay que **construirlo** con su `Builder`. Para eso se usa un módulo con `@Provides`.

<Recorrido
  titulo="features/pokemon/di/NetworkModule.kt"
  lenguaje="kotlin"
  codigo={`@Module
@InstallIn(SingletonComponent::class)
class NetworkModule {
    @Provides
    @Singleton
    fun provideHttpClient(): PokeApi {
        val retrofit: Retrofit = Retrofit.Builder()
            .baseUrl("https://pokeapi.co/api/v2/")
            .addConverterFactory(GsonConverterFactory.create())
            .build()
        return retrofit.create(PokeApi::class.java)
    }
}`}
>
  <Paso lineas="1-3" titulo="Un módulo de Hilt">
    `@Module` + `@InstallIn(SingletonComponent::class)`: lo que da este módulo vive mientras vive la app. Es una `class` con `@Provides`, no una `interface` con `@Binds`.
  </Paso>
  <Paso lineas="4-6" titulo="@Provides y @Singleton">
    `@Provides` le dice a Hilt: "cuando alguien pida una `PokeApi`, ejecuta esta función". Con `@Singleton` solo se ejecuta una vez.
  </Paso>
  <Paso lineas="7-8" titulo="La baseUrl">
    El `Builder` empieza por la `baseUrl`, que tiene que acabar en `/`.
  </Paso>
  <Paso lineas="9" titulo="Gson">
    `GsonConverterFactory.create()` le dice a Retrofit que convierta el JSON con Gson.
  </Paso>
  <Paso lineas="11" titulo="Retrofit implementa la interfaz">
    `retrofit.create(PokeApi::class.java)` devuelve un objeto que implementa `PokeApi`. Eso es lo que recibe el DataSource.
  </Paso>
</Recorrido>

<Comparar titulo="El nombre de la función">
  <Lado tipo="evitar">

```kotlin
@Provides
@Singleton

```

Se llama `provideHttpClient`, pero no devuelve un cliente HTTP, sino la API. El nombre engaña.

```kotlin
@Module

object NetworkModule {
    @Provides
    @Singleton
    fun provideRetrofit(): Retrofit = Retrofit.Builder()
        .baseUrl("https://pokeapi.co/api/v2/")
        .addConverterFactory(GsonConverterFactory.create())
        .build()

    @Provides
    @Singleton
    fun providePokeApi(retrofit: Retrofit): PokeApi =
        retrofit.create(PokeApi::class.java)
}
```

Cada función crea una cosa y se llama como lo que crea. Con `object` no hace falta crear instancias del módulo.

  </Lado>

### `AppModule`: atar interfaces con `@Binds`

El DataSource y el repositorio sí tienen `@Inject constructor`, así que basta con decirle a Hilt qué implementación va con cada interfaz:

```kotlin title="core/di/AppModule.kt (09/11, fragmento)"
@Module
@InstallIn(SingletonComponent::class)
interface AppModule {
    @Binds @Singleton
    fun bindsPokemonRemoteDataSource(ds: PokemonRemoteDataSourceImpl): PokemonRemoteDataSource

    @Binds @Singleton
    fun bindsPokemonRepository(r: PokemonRepositoryImpl): PokemonRepository
}
```

- Son dos de los tres `@Binds` del final del 09/11. El tercero, el de la fuente local, está en [Offline-first](/docs/2-dam/kotlin/datos/offline-first). El 26/10 solo se ve el primero, con los nombres de entonces (`PokemonRemoteDataSource` atado a `PokemonDataSource`).
- El 26/10 se lee <Dudoso nota="Con el import jakarta.inject.Singleton, en 3 capturas. Lo correcto, y lo que sale en las clases siguientes, es SingletonComponent::class.">`@InstallIn(Singleton::class)`</Dudoso> en este módulo.
- Al compilar se ven las tareas de KSP y Hilt (`kspDebugKotlin`, `hiltJavaCompileDebug`) y, en `build/generated/ksp`, las clases `..._Factory.java` que genera Dagger para cada `@Inject constructor`.
- `@Provides` frente a `@Binds`, y Hilt en general, están en [Módulos de Hilt](/docs/2-dam/kotlin/arquitectura/hilt-modulos).

## 6. La `Application` y el manifest

Hilt necesita una clase `Application` propia con `@HiltAndroidApp`:

```kotlin title="core/PokeApplication.kt"
@HiltAndroidApp
class PokeApplication() : Application()
```

<Callout type="error" title="Salió en clase: @AndroidEntryPoint en la Application">
  El 26/10 a `PokeApplication` se le puso primero `@AndroidEntryPoint` por error. Esa anotación va en la **Activity** (`MainActivity`); la `Application` lleva `@HiltAndroidApp`. Si falta, sale *Hilt Activity must be attached to an @HiltAndroidApp Application*.
</Callout>

En el manifest hay que hacer dos cosas: registrar esa `Application` con `android:name` y **pedir permiso para usar internet**.

```xml title="AndroidManifest.xml (resumen)"
<uses-permission android:name="android.permission.INTERNET" />

<application android:name=".core.PokeApplication" ...>
    <activity android:name=".MainActivity" android:exported="true">
        ...
    </activity>
</application>
```

- `INTERNET` es un permiso **normal**: se concede solo al instalar la app, sin preguntar al usuario. Basta con declararlo.
- En clase se añadió `CAMERA` como ejemplo de otro permiso y luego se quitó: al final solo queda `INTERNET`.
- Sin el permiso, la petición falla con un error como `SecurityException: Permission denied (missing INTERNET permission?)`.

## Lo que no se dio de Retrofit <NoDadoEnClase inline />

En clase solo hubo `@GET` contra PokeAPI. Para el proyecto hacen falta más cosas, explicadas en [Para el proyecto](/docs/2-dam/kotlin/para-el-proyecto):

- `@POST`, `@PUT` y `@DELETE` con `@Body`, y `@Query` para los parámetros `?clave=valor`: [POST, PUT y DELETE con Retrofit](/docs/2-dam/kotlin/para-el-proyecto/crud-con-retrofit).
- Llamar a vuestra API desde el emulador (`10.0.2.2` en vez de `localhost`, y permitir `http`) y mandar el token en cada petición con un interceptor de OkHttp: [Conectar con tu API](/docs/2-dam/kotlin/para-el-proyecto/conectar-con-tu-api).
- Capturar los errores de red (`IOException`) para que la app no se caiga sin conexión: [Room como fuente de verdad](/docs/2-dam/kotlin/para-el-proyecto/offline-first).

  <Tarjeta frente="`Response<T>`">Envuelve la respuesta: `isSuccessful` (código 2xx), `body()` (nulable) y `code()`.</Tarjeta>
  <Tarjeta frente="`@Path(value = &quot;name&quot;)`">Sustituye el hueco `{name}` de la ruta por el valor del parámetro.</Tarjeta>

  <Tarjeta frente="`@SerializedName`">Le dice a Gson el nombre del campo en el JSON cuando no coincide con el de la propiedad.</Tarjeta>

## Ejercicios

<Ejercicio titulo="El detalle por id" dificultad="facil">
  Implementa `readPokemonById(id: Int): Pokemon?` en `PokemonRemoteDataSourceImpl`, igual que `readPokemonByName`, pero usando el endpoint por id de la interfaz.

  <Pista>Llama a `_api.readPokemonById(id)` y mira `isSuccessful`.</Pista>

  <Solucion>

```kotlin
override suspend fun readPokemonById(id: Int): Pokemon? {
    val response = _api.readPokemonById(id)
    if (response.isSuccessful) {
        return response.body()!!.toModel()
    } else {
        return null
    }
}
```

  Hace lo mismo que la versión de clase del 09/11, que guarda antes el cuerpo en `val body = response.body()!!`. Sin `!!` sería más seguro: `return response.body()?.toModel()`, que devuelve `null` también si el cuerpo es `null`.

  </Solucion>
</Ejercicio>

<Ejercicio titulo="Los tipos de un pokémon" dificultad="media">
  El detalle de PokeAPI trae también los tipos, con esta forma (recortada):

```json
{
  "id": 1,
  "name": "bulbasaur",
  "types": [
    { "slot": 1, "type": { "name": "grass", "url": "https://pokeapi.co/api/v2/type/12/" } },
    { "slot": 2, "type": { "name": "poison", "url": "https://pokeapi.co/api/v2/type/4/" } }
  ]
}
```

  Añade al DTO lo necesario para leer los tipos y haz que `toModel()` rellene una propiedad `types: List<String>` del modelo con los nombres (`["grass", "poison"]`).

  <Pista>Cada objeto JSON es una `data class`: hacen falta dos nuevas, una para cada elemento de `types` y otra para el objeto `type` de dentro.</Pista>
  <Pista>Para quedarte con los nombres, recorre la lista con `map { it.type.name }`.</Pista>

  <Solucion>

```kotlin
data class PokemonResult(
    val id: Int,
    val name: String,
    val sprites: PokemonSprites?,
    val types: List<PokemonTypeSlot>,
)
data class PokemonTypeSlot(val slot: Int, val type: PokemonTypeName)
data class PokemonTypeName(val name: String, val url: String)

data class Pokemon(
    val id: Int,
    val name: String,
    val pokemonImageUrl: String?,
    val types: List<String>,
)

fun PokemonResult.toModel(): Pokemon = Pokemon(
    id = this.id,
    name = this.name,
    pokemonImageUrl = this.sprites?.frontDefault,
    types = this.types.map { it.type.name },
)
```

  Los nombres del JSON (`types`, `slot`, `type`, `name`) coinciden con los de las propiedades, así que no hace falta `@SerializedName`. Esto ya no es código de clase: es un ejercicio sobre el mismo patrón.

  </Solucion>
</Ejercicio>

## Resumen

<Glosario titulo="Conceptos clave">
  <Termino nombre="Retrofit">Librería que convierte una interfaz con `@GET`, `@Path`… en llamadas HTTP.</Termino>
  <Termino nombre="Gson">Librería que convierte JSON en objetos y al revés. En Retrofit se añade con `GsonConverterFactory`.</Termino>
  <Termino nombre="Response">Envoltorio de la respuesta con `isSuccessful`, `body()` y `code()`.</Termino>
  <Termino nombre="DTO">`data class` con la forma del JSON de la API.</Termino>
  <Termino nombre="toModel()">Función de extensión que pasa un DTO al modelo de la app.</Termino>
  <Termino nombre="DataSource">Clase que habla con una sola fuente de datos (aquí, la API).</Termino>
  <Termino nombre="NetworkModule">Módulo de Hilt con `@Provides` que construye Retrofit y la API.</Termino>
  <Termino nombre="INTERNET">Permiso que hay que declarar en el manifest para usar la red.</Termino>
</Glosario>
