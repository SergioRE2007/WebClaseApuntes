En la v0.5.0 la referencia añade el **módulo `auth`**: registrarse y entrar. Al registrarse, la contraseña se guarda como un *hash* de **bcrypt**; al entrar, se compara y, si es correcta, la API devuelve un **JWT**, un token firmado que el cliente mandará en las siguientes peticiones.

## La contraseña: hash, no cifrado

En la tabla `User` no hay columna `password`: hay **`passwordHash`**. Un <Concepto termino="Hash" definicion="Resultado de pasar un texto por una función de un solo sentido: de la contraseña se saca el hash, pero del hash no se puede sacar la contraseña.">hash</Concepto> se calcula a partir de la contraseña, pero no se puede deshacer. Si alguien roba la base de datos, no tiene las contraseñas.

- **`bcrypt.hash(password, rondas)`** calcula el hash al registrarse. Las rondas dicen cuánto trabajo cuesta calcularlo (más rondas, más lento y más difícil de atacar a fuerza bruta). Salen de `env.BCRYPT_SALT_ROUNDS`, que por defecto es **10**.
- **`bcrypt.compare(password, hash)`** comprueba al entrar si la contraseña que llega corresponde a ese hash. Devuelve `true` o `false`.

Nunca se compara a mano ni se "descifra" nada: siempre `bcrypt.compare`.

## El token: JWT

Un <Concepto termino="JWT" definicion="JSON Web Token: un token firmado que el servidor da al iniciar sesión. El cliente lo manda en cada petición (Authorization: Bearer ...) y el servidor comprueba la firma sin guardar nada.">JWT</Concepto> son tres trozos en Base64 separados por puntos: `cabecera.datos.firma`. Los datos (el *payload*) los puede leer cualquiera; lo que no se puede es **cambiarlos sin que la firma deje de valer**, porque la firma se calcula con un secreto que solo tiene el servidor.

```ts title="Lo que firma la API"
jwt.sign({ sub: user.id, email: user.email }, env.JWT_SECRET, { expiresIn: '7d' });
```

| Parte | Qué es |
| --- | --- |
| `sub` | *Subject*: el id del usuario. Es el nombre estándar de ese dato en un JWT. |
| `email` | El email, para no tener que buscarlo. |
| `env.JWT_SECRET` | El secreto con el que se firma. Sale del `.env` y es obligatorio (`required()`). |
| `expiresIn: '7d'` | El token caduca a los 7 días. |

El tooltip del editor sobre `sub` enseñaba `String.sub()` (obsoleto). Es un falso positivo: en el JWT, `sub` es solo una clave del objeto.

## El servicio

<Recorrido
  titulo="src/modules/auth/auth.service.ts"
  lenguaje="ts"
  codigo={`import bcrypt from 'bcrypt';
import jwt from 'jsonwebtoken';
import { env } from '../../config/env.js';
import { createUser, findUserByEmail } from '../users/users.service.js';

export async function register(email: string, name: string, password: string) {
  const existing = await findUserByEmail(email);
  if (existing) {
    throw new Error('Email ya registrado');
  }
  const hash = await bcrypt.hash(password, env.BCRYPT_SALT_ROUNDS);
  const user = await createUser(email, name, hash);
  const token = jwt.sign({ sub: user.id, email: user.email }, env.JWT_SECRET, { expiresIn: '7d' });
  return { user, token };
}

export async function login(email: string, password: string) {
  const user = await findUserByEmail(email);
  if (!user) {
    throw new Error('Credenciales inválidas');
  }
  const ok = await bcrypt.compare(password, user.passwordHash);
  if (!ok) {
    throw new Error('Credenciales inválidas');
  }
  const token = jwt.sign({ sub: user.id, email: user.email }, env.JWT_SECRET, { expiresIn: '7d' });
  return {
    user: { id: user.id, email: user.email, name: user.name, createdAt: user.createdAt },
    token
  };
}`}
>
  <Paso lineas="1-4" titulo="Reutiliza el servicio de usuarios">
    El módulo `auth` no habla con Prisma directamente: usa `createUser` y `findUserByEmail` del servicio de `users`.
  </Paso>
  <Paso lineas="7-10" titulo="¿Ya existe?">
    Si hay un usuario con ese email, **lanza** un `Error` con un mensaje concreto. El servicio no sabe de códigos HTTP: eso lo decide el controlador.
  </Paso>
  <Paso lineas="11" titulo="bcrypt.hash">
    Calcula el hash con las rondas de `env` (10 por defecto). `await`, porque bcrypt es lento a propósito.
  </Paso>
  <Paso lineas="12" titulo="Guardar">
    `createUser` inserta con `passwordHash` y devuelve el usuario **sin** él (lleva `select`).
  </Paso>
  <Paso lineas="13-14" titulo="Firmar el token">
    `jwt.sign` con `sub` y `email`, el secreto y 7 días de caducidad. El registro ya deja la sesión iniciada: devuelve `{ user, token }`.
  </Paso>
  <Paso lineas="18-21" titulo="Login: buscar por email">
    `findUserByEmail` devuelve el usuario entero, con `passwordHash`, o `null`.
  </Paso>
  <Paso lineas="22-25" titulo="Comparar la contraseña">
    `bcrypt.compare` con lo que llega y el hash guardado. Si no coincide, el **mismo** error que si el email no existiera.
  </Paso>
  <Paso lineas="26-30" titulo="Responder sin passwordHash">
    Aquí el usuario sí trae `passwordHash` (no tenía `select`), así que se monta el objeto a mano con solo los campos públicos.
  </Paso>
</Recorrido>

El tooltip de `register` enseña el tipo que devuelve: `Promise<{ user: { id: number; email: string; name: string; createdAt: Date }; token: string }>`.

## El controlador

<Recorrido
  titulo="src/modules/auth/auth.controller.ts (v0.5.0)"
  lenguaje="ts"
  codigo={`import type { Request, Response } from 'express';
import { register, login } from './auth.service.js';
import { registerSchema, loginSchema } from '../users/users.schema.js';

export async function registerCtrl(req: Request, res: Response) {
  try {
    const { email, name, password } = registerSchema.parse(req.body);
    const data = await register(email, name, password);
    res.status(201).json(data);
  } catch (e: any) {
    if (e.message === 'Email ya registrado') {
      return res.status(409).json({ message: e.message });
    }
    res.status(400).json({ message: e.message });
  }
}

export async function loginCtrl(req: Request, res: Response) {
  try {
    const { email, password } = loginSchema.parse(req.body);
    const data = await login(email, password);
    res.json(data);
  } catch (e: any) {
    if (e.message === 'Credenciales inválidas') {
      return res.status(401).json({ message: e.message });
    }
    res.status(400).json({ message: e.message });
  }
}`}
>
  <Paso lineas="7" titulo="Validar con parse">
    En la v0.5.0 la ruta no lleva `validate`: el controlador valida con `parse`, que **lanza** si los datos no valen, y el error cae en el `catch`.
  </Paso>
  <Paso lineas="8-9" titulo="201 Created">
    El registro crea un recurso, así que responde **201** con `{ user, token }`.
  </Paso>
  <Paso lineas="11-13" titulo="Del mensaje al código">
    El servicio lanzó `new Error('Email ya registrado')`: el controlador lo reconoce por el mensaje y responde **409**.
  </Paso>
  <Paso lineas="14" titulo="Lo demás: 400">
    Cualquier otro error (sobre todo el de Zod) responde 400 con `e.message`. Con un `ZodError`, ese mensaje es la lista de errores convertida en texto.
  </Paso>
  <Paso lineas="21-22" titulo="Login correcto: 200">
    `res.json(data)` con `{ user, token }`.
  </Paso>
  <Paso lineas="24-26" titulo="Credenciales inválidas: 401">
    401 *Unauthorized*: no te has identificado bien.
  </Paso>
</Recorrido>

El reparto es siempre el mismo: **el servicio lanza `throw new Error('...')` y el controlador traduce el mensaje a un código HTTP**.

| Petición | Cuándo | Respuesta |
| --- | --- | --- |
| `POST /api/auth/register` | Todo bien | **201** `{ user, token }` |
| | Email ya registrado | **409** `{ message: 'Email ya registrado' }` |
| | Datos que no pasan Zod | **400** `{ message }` (v0.5.0) |
| `POST /api/auth/login` | Todo bien | **200** `{ user, token }` |
| | Email que no existe o contraseña mal | **401** `{ message: 'Credenciales inválidas' }` |
| | Datos que no pasan Zod | **400** `{ message }` (v0.5.0) |

<Callout type="info" title="En la v1.0.0">
  Con `validate(schema)` en las rutas, los datos mal formados se cortan antes y el 400 sale de `validate` (con `{ errors }`). <Dudoso nota="No se ve el controlador de auth de la v1.0.0.">No se sabe si el `parse` del controlador se quitó</Dudoso>.
</Callout>

## Seguridad

- **El mismo mensaje en los dos fallos.** Si el login dijera "ese email no existe" o "contraseña incorrecta", un atacante podría averiguar qué emails están registrados. Con "Credenciales inválidas" para los dos casos, no da pistas.
- **Nunca se devuelve `passwordHash`**: `createUser` lleva `select` y `login` monta el usuario a mano. Los tests lo comprueban (`not.toHaveProperty('passwordHash')`).
- **El ejemplo de lo que no hay que hacer**: el 28/10, la Fake Store API devolvía el campo `password` de cada usuario en `GET /users` ([Probar APIs](/docs/2-dam/apis/backend/probar-apis)).
- **`JWT_SECRET` fuera del código**: sale del `.env` y, en producción, se pasa desde el entorno, sin escribirlo en el `docker-compose` ([Docker y Swagger](/docs/2-dam/apis/backend/docker-swagger)).

## Lo que vino después: v0.6.0 y v0.7.0

Según los tags, la **v0.6.0** añade el middleware de autenticación (JWT, rutas protegidas y `/me`) y la **v0.7.0**, actualizar el perfil y cambiar la contraseña.

<NoSeVio titulo="Middleware auth, /me y /me/password">
  El código del middleware `auth` (v0.6.0), de las rutas `/me` y `/me/password` y del servicio de cambiar la contraseña no se llegó a ver. Solo se conocen por los tests de la v0.9.0, el README de la v0.7.0 y los mensajes de error.
</NoSeVio>

Lo que sí se sabe por los tests y el README:

| Petición | Qué se espera |
| --- | --- |
| `GET /api/users` sin cabecera `Authorization` | **401** `No autorizado` |
| `GET /api/users` con `Bearer invalid_token` | **401** `Token inválido` |
| `GET /api/users/me` con token | **200** con el usuario, sin `passwordHash` |
| `PATCH /api/users/me` con `{ name }` | **200** con el nombre cambiado |
| `PATCH /api/users/me` con un email mal escrito | **400** |
| `PATCH /api/users/me/password` con `{ currentPassword, newPassword }` | **200** `Contraseña actualizada correctamente`, y después el login funciona con la nueva |
| Lo mismo con la contraseña actual mal | **400** `Contraseña actual incorrecta` |

El README de la v0.7.0 describe así el cambio de contraseña:

<Steps>
  <Step>

#### El middleware `auth` valida el JWT

Lee la cabecera `Authorization: Bearer <token>` y comprueba la firma.

  </Step>
  <Step>

#### El middleware `validate` valida el body

Con el schema de la contraseña.

  </Step>
  <Step>

#### El controlador saca el id del token

De `req.user.sub`, no del body ni de la URL.

  </Step>
  <Step>

#### El servicio comprueba la contraseña actual

Con `bcrypt.compare`.

  </Step>
  <Step>

#### Se guarda la nueva

Hasheada con bcrypt.

  </Step>
</Steps>

Como el id sale del token, **cada usuario solo puede modificar su propio perfil**: aunque cambie la URL o el body, el token dice quién es.

<NoDadoEnClase titulo="Cómo se protege una ruta con el token">
  Un middleware estándar que hace lo de la v0.6.0 (leer `Authorization: Bearer`, `jwt.verify` y pasar el id al controlador) está en [CORS y rutas protegidas](/docs/2-dam/apis/backend-proyecto/cors-y-token), con lo que no se ha dado en clase.
</NoDadoEnClase>

  <Pista>Compara los mensajes de error con los de clase.</Pista>
  <Pista>¿Qué campos trae `user` si `findUserByEmail` no lleva `select`?</Pista>

export async function login(email: string, password: string) {
  const user = await findUserByEmail(email);
  if (!user) {
    throw new Error('Credenciales inválidas');
  }
  const ok = await bcrypt.compare(password, user.passwordHash);
  if (!ok) {
    throw new Error('Credenciales inválidas');
  }
  const token = jwt.sign({ sub: user.id, email: user.email }, env.JWT_SECRET, { expiresIn: '7d' });
  return {
    user: { id: user.id, email: user.email, name: user.name, createdAt: user.createdAt },
    token
  };
}
