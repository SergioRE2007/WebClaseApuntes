## Express en una idea

<Concepto termino="Express" definicion="El framework de Node más usado para hacer servidores HTTP. Se le dicen las rutas y qué función responde a cada una.">Express</Concepto> crea un servidor HTTP al que le dices "cuando llegue un `GET` a esta ruta, ejecuta esta función". La función recibe la petición (`req`) y la respuesta (`res`):

```ts title="Lo mínimo"
import express from 'express';

const app = express();

app.get('/', (req, res) => {
  res.send('Hello World');
});

app.listen(3000);
```

Si vienes de Spring, `app.get('/', ...)` es un `@GetMapping("/")` y la función es el método del `@RestController`. La diferencia es que aquí no hay anotaciones ni escaneo de clases: cada ruta se registra a mano. Se usa **Express 5** (`^5.1.0` en la referencia, `^5.3.0` en directo).

## `app.ts` e `index.ts` por separado

Los dos proyectos de clase separan el servidor en dos ficheros:

- **`app.ts`** crea la app con `express()`, le pone los middlewares y las rutas, y la **exporta** con `export default app`.
- **`index.ts`** solo la **importa** y llama a `listen`. No exporta nada.

Así se puede importar la app sin arrancar el servidor. Es lo que hacen los tests con Supertest (`request(app)`), que verás en [Logs, rate limiting y tests](/docs/2-dam/apis/backend/logs-rate-limiting-tests).

## Variables de entorno: `env.ts`

La configuración (el puerto, la URL de la base de datos, los secretos) no se escribe en el código: va en un fichero **`.env`** en la raíz, que **no se sube a Git**. La librería **dotenv** lo lee al arrancar y mete cada línea en `process.env`.

```bash title=".env (en directo)"
NODE_PORT=3000
NODE_ENV=development
```

Y todo el código lee la configuración de **un único objeto `env`**, exportado desde `src/config/env.ts`. El resto del proyecto nunca toca `process.env` directamente.

## Rutas y respuestas

Una ruta se registra con el método HTTP (`app.get`, `app.post`, `app.patch`, `app.delete`…), la URL y una función `(req, res)`:

```ts title="src/app.ts (referencia)"
app.get('/health', (_req, res) => res.json({ ok: true }));
```

- **`res.json(obj)`** responde con JSON y código 200.
- **`res.status(código).json(obj)`** elige el código: `res.status(404).json({ message: 'No existe' })`.
- **`res.send(texto)`** responde con texto.
- **`_req`**: si un parámetro no se usa, se escribe con guion bajo delante. Lo mismo con `_next`.

La ruta **`/health`** sirve para comprobar que el servidor está vivo sin tocar la base de datos. En clase, con el autocompletado, el profesor también exploró lo que trae `req`: `headers`, `hostname`, `ip`, `method`…

### Lo que pasa si no hay ruta

Con el servidor recién arrancado y sin rutas, `localhost:3010` en el navegador respondía **`Cannot GET /`**: es el 404 que da Express por defecto. Con `morgan('dev')` se ve cada petición en la consola:

## Middlewares

Un middleware es una función `(req, res, next)` que se ejecuta **antes** de que la petición llegue a su ruta. Puede hacer algo y llamar a `next()` para pasar a la siguiente pieza, o responder y cortar la cadena. Se registran con `app.use()` y **se ejecutan en el orden en que los escribes**.

| Middleware | Qué hace |
| --- | --- |
| `helmet()` | Añade cabeceras de seguridad a todas las respuestas. |
| `cors()` | Añade las cabeceras <Concepto termino="CORS" definicion="Regla de los navegadores que impide que una web lea respuestas de otro origen (otro dominio o puerto) si el servidor no le da permiso con una cabecera. No afecta a Postman ni a Android.">CORS</Concepto> para que una web de otro origen (Angular en el puerto 4200) pueda leer las respuestas. Sin opciones, deja pasar a cualquiera. |
| `express.json()` | Lee el cuerpo de las peticiones con JSON y lo deja en `req.body`. Desde la v0.8.0, con `{ limit: '10mb' }`. |
| `express.urlencoded({ extended: true })` | Lee los formularios HTML clásicos. Solo en el proyecto en directo. |
| `morgan('dev')` | Una línea de log por petición. Desde la v0.8.0 se cambia por un `requestLogger` propio. |
| `errorHandler` | El manejador de errores. **Siempre el último.** |

El profesor insistió en el orden: primero seguridad y lectura del cuerpo, luego el log, luego las rutas, y el manejador de errores al final. Este es el orden definitivo de la referencia (v1.0.0):

1. `helmet` y `cors`
2. `express.json({ limit: '10mb' })`
3. `requestLogger` (antes `morgan('dev')`)
4. `generalLimiter` (rate limiting)
5. `/health` y `/api-docs`
6. Las rutas (`/api/auth`, `/api/users`)
7. `errorHandler`

El 20/10 también probó `helmet({ contentSecurityPolicy: false })` y lo dejó otra vez en `helmet()`. En la v1.0.0 se queda sin CSP para que se vea Swagger ([Docker y Swagger](/docs/2-dam/apis/backend/docker-swagger)).

| `errorHandler` antes de las rutas | Los errores de las rutas no le llegan y responde el manejador por defecto de Express, con HTML. |

## El manejador de errores

Express reconoce un middleware de errores porque tiene **cuatro parámetros**: `(err, req, res, next)`. Si algo llama a `next(err)` (o lanza un error en una ruta), Express se salta los middlewares normales y va al siguiente de cuatro parámetros.

```ts title="src/middleware/error.ts (v0.2.0)"
import type { Request, Response, NextFunction } from 'express';

export function errorHandler(err: any, _req: Request, res: Response, _next: NextFunction) {
  console.error(err);
  const status = err.status || 500;
  res.status(status).json({ message: err.message || 'Error interno' });
}
```

- Usa el `status` del error si lo trae (por ejemplo, `express.json()` pone 400 cuando el JSON está mal escrito) y, si no, 500.
- Responde siempre JSON con `{ message }`, y `'Error interno'` si el error no trae mensaje.
- `_next` no se usa, pero **tiene que estar**: sin el cuarto parámetro Express lo trataría como un middleware normal.

En la v0.8.0 `console.error` se cambia por el logger de Winston y el parámetro `_req` pasa a `req`, para apuntar el método y la ruta ([Logs, rate limiting y tests](/docs/2-dam/apis/backend/logs-rate-limiting-tests)).

<NoDadoEnClase titulo="Errores en funciones async con Express 5">
  En Express 5, si una ruta `async` lanza un error (o una promesa se rechaza), Express lo pasa solo al manejador de errores. En Express 4 había que hacer `try/catch` y llamar a `next(err)`. Los controladores de clase llevan su propio `try/catch` y responden ellos, así que no dependen de esto.
</NoDadoEnClase>

## Cierre ordenado del servidor

Cuando paras el servidor con **Ctrl+C** (señal `SIGINT`) o cuando Docker para el contenedor (señal `SIGTERM`), conviene dejar que terminen las peticiones que están a medias. Para eso se guarda lo que devuelve `app.listen` y se cierra al recibir la señal:

<Recorrido
  titulo="src/index.ts (v0.8.0 en adelante)"
  lenguaje="ts"
  codigo={`import app from './app.js';
import { env } from './config/env.js';
import { logger } from './utils/logger.js';

const server = app.listen(env.PORT, () => {
  logger.info(\`API escuchando en http://localhost:\${env.PORT}\`);
  logger.info(\`Entorno: \${env.NODE_ENV}\`);
});

process.on('SIGTERM', () => {
  logger.info('SIGTERM recibido, cerrando servidor...');
  server.close(() => {
    logger.info('Servidor cerrado');
    process.exit(0);
  });
});

process.on('SIGINT', () => {
  logger.info('SIGINT recibido, cerrando servidor...');
  server.close(() => {
    logger.info('Servidor cerrado');
    process.exit(0);
  });
});`}
>
  <Paso lineas="5-8" titulo="Guardar el servidor">
    `app.listen` devuelve el servidor HTTP. Se guarda en `server` para poder cerrarlo después.
  </Paso>
  <Paso lineas="10" titulo="Escuchar la señal">
    `process.on('SIGTERM', ...)` se ejecuta cuando el sistema (o Docker) pide al proceso que termine.
  </Paso>
  <Paso lineas="12-15" titulo="server.close(callback)">
    Deja de aceptar conexiones nuevas, espera a que acaben las que hay y entonces ejecuta el *callback*, que sale con `process.exit(0)` (0 = sin error).
  </Paso>
  <Paso lineas="18-24" titulo="Lo mismo con Ctrl+C">
    `SIGINT` es la señal de Ctrl+C. Se trata igual.
  </Paso>
</Recorrido>

Hasta la v0.7 era más corto: `process.on('SIGTERM', () => server.close())`, con `console.log` en vez del logger. El 20/10 el profesor lo reescribió con llaves (con algún error de sintaxis por el camino) y lo dejó en una línea.

  <Tarjeta frente="`app.ts` frente a `index.ts`">`app.ts` crea y configura Express (middlewares y rutas) y lo exporta. `index.ts` solo hace `listen` y el cierre ordenado.</Tarjeta>
  <Tarjeta frente="¿Para qué sirve `env.ts`?">Centraliza la configuración: lee `process.env` una vez, con valores por defecto y `required()` para las obligatorias. El resto del código usa `env.X`.</Tarjeta>
  <Tarjeta frente="`import 'dotenv/config'`">Carga el `.env` en `process.env`. Equivale a `import dotenv from 'dotenv'` + `dotenv.config()`.</Tarjeta>
  <Tarjeta frente="Orden de los middlewares de la referencia">helmet → cors → express.json → requestLogger → generalLimiter → /health y /api-docs → rutas → errorHandler.</Tarjeta>

  <Tarjeta frente="Firma del manejador de errores">`(err, req, res, next)`, con cuatro parámetros. Responde `err.status || 500` y `{ message }`.</Tarjeta>

<Ejercicio titulo="Un env.ts con variables obligatorias" dificultad="facil">
  Escribe un `src/config/env.ts` que cargue el `.env` y exporte un objeto `env` con `PORT` (número, por defecto 3000), `NODE_ENV` (por defecto `development`) y `DATABASE_URL`, que es obligatoria: si falta, la app no debe arrancar.

  <Pista>Para cargar el fichero basta con `import 'dotenv/config'` en la primera línea.</Pista>
  <Pista>Haz una función que reciba el valor y el nombre y lance un error si el valor no existe.</Pista>

  <Solucion>

Es el `env.ts` de la referencia, sin las variables de auth y Cloudinary:

```ts title="src/config/env.ts"
import 'dotenv/config';

const required = (v: string | undefined, k: string) => {
  if (!v) throw new Error(`Falta variable de entorno: ${k}`);
  return v;
};

export const env = {
  PORT: Number(process.env.PORT ?? 3000),
  NODE_ENV: process.env.NODE_ENV ?? 'development',
  DATABASE_URL: required(process.env.DATABASE_URL, 'DATABASE_URL'),
};
```

<Ejercicio titulo="Ordena este app.ts" dificultad="media">
  Este `app.ts` tiene el orden mal. Di qué falla al hacer `PATCH /api/users/1` con un JSON y reescríbelo bien.

```ts title="src/app.ts"
const app = express();
app.use(errorHandler);
app.use('/api/users', usersRoutes);
app.use(express.json());
app.use(helmet());
app.use(cors());
app.get('/health', (_req, res) => res.json({ ok: true }));
export default app;
```

  <Pista>Piensa qué se ha ejecutado ya cuando la petición llega a `usersRoutes`.</Pista>
  <Pista>¿Le llegaría al `errorHandler` un error de la ruta?</Pista>

  <Solucion>

- `express.json()` va después de las rutas: `req.body` llega `undefined` y `validate` responde 400.
- `helmet` y `cors` también van detrás: las respuestas de `/api/users` salen sin sus cabeceras (Angular no podría leerlas por CORS).
- `errorHandler` va el primero: los errores de las rutas no le llegan y responde el manejador por defecto de Express.

```ts title="src/app.ts"
const app = express();
app.use(helmet());
app.use(cors());
app.use(express.json());
app.get('/health', (_req, res) => res.json({ ok: true }));
app.use('/api/users', usersRoutes);
app.use(errorHandler);
export default app;
```

  </Solucion>
</Ejercicio>
