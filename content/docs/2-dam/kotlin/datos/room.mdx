**Room** es la base de datos local de Android: por debajo es SQLite, pero en vez de escribir el SQL de las tablas y leer cursores a mano, escribes clases y anotaciones y Room genera el código al compilar. El 13/11 se montó desde cero en un proyecto nuevo, **Room**, con Room 3, KSP y Hilt.

<DeClase fecha="13/11" proyecto="Room" />

El paquete del proyecto es <Dudoso nota="En algunas capturas se lee com.turinglan.room; seguramente es un error de lectura.">`com.turingalan.room`</Dudoso>.

<Callout type="warn" title="Room 3 no se escribe igual que Room 2">
  En clase se usa **Room 3**: los artefactos son `androidx.room3:room3-runtime` y `room3-compiler`, y los imports, `androidx.room3.*` (no `androidx.room.*`). Casi todo lo que hay en internet es de Room 2, y algunas cosas, como `@Relation`, cambian.
</Callout>

<Callout type="idea" title="Lo que vas a aprender">
  - Las tres piezas de Room: entidades, DAO y base de datos.
  - Preparar Gradle con el catálogo de versiones, KSP y Hilt.
  - Escribir una entidad, un DAO con `@Insert`, `@Update` y `@Query`, y la clase `@Database`.
  - Crear la base de datos con un módulo de Hilt y entender los errores de KSP.
</Callout>

| Pieza | Qué es | En clase |
| --- | --- | --- |
| **Entidad** (`@Entity`) | Una `data class` que es una **tabla**. Cada objeto es una fila. | `PokemonEntity` |

## Preparar Gradle

Room 3 y Hilt generan código al compilar con **KSP** (*Kotlin Symbol Processing*), el procesador de anotaciones. En clase se añadió todo a mano y salieron varios errores de sincronización por el camino.

<Steps>
  <Step>

#### Versiones y plugins en el catálogo

  En `gradle/libs.versions.toml` van los números en `[versions]`, las librerías en `[libraries]` y los plugins en `[plugins]`, unidos con `version.ref`.

  </Step>
  <Step>

#### Plugins en el build raíz, con `apply false`

  El `build.gradle.kts` de la raíz **declara** los plugins sin aplicarlos.

  </Step>
  <Step>

#### Plugins y dependencias en `app`

  El `app/build.gradle.kts` aplica los plugins (sin `apply false`) y añade las dependencias: `implementation(...)` para lo que va dentro de la app y `ksp(...)` para los compiladores que generan código.

  </Step>
  <Step>

#### Sync Now

  Después de tocar el catálogo, Gradle no puede reutilizar su caché de configuración: hay que pulsar **Sync Now**.

  </Step>
</Steps>

## La entidad

Una entidad es una `data class` con `@Entity`. Cada propiedad es una columna.

```kotlin title="data/Pokemon.kt (versión final)"
@Entity(tableName = "pokemon")
data class PokemonEntity(
    @PrimaryKey
    val id: Int,
    val name: String,
    val imageUrl: String?,
)
```

- `tableName` fija el nombre de la tabla. Sin él, la tabla se llamaría como la clase. En unas capturas sale <Dudoso nota="En otras capturas aparece @Entity sin tableName.">`@Entity(tableName = "pokemon")`</Dudoso> y en otras no.
- `@PrimaryKey` marca la clave primaria.
- Un tipo **nulable** (`String?`) es una columna que admite `NULL`. Los no nulables son `NOT NULL`.
- La entidad se llama `PokemonEntity` para no confundirla con el modelo `Pokemon` del resto de la app.

La primera versión (minutos 19 a 24) enseñaba `@ColumnInfo`, que cambia el nombre de la columna en SQL:

```kotlin title="data/Pokemon.kt (primera versión)"
@Entity
data class Pokemon(
    @PrimaryKey
    val id: Int,
    val name: String,
    @ColumnInfo(name = "image_url")
    val imageUrl: String?,
)
```

En la versión final `imageUrl` aparece sin `@ColumnInfo` y su import sale como no usado: no se sabe si se quitó a propósito. El tooltip de `@Entity` enseñó también sus otros parámetros: `indices`, `inheritSuperIndices`, `primaryKeys`, `foreignKeys`, `ignoredColumns` y `withoutRowId`.

## El DAO

El DAO es una `interface` con `@Dao`. Tú escribes la firma y la anotación, y Room genera la implementación.

<Recorrido
  titulo="data/Pokemon.kt (el DAO)"
  lenguaje="kotlin"
  codigo={`@Dao
interface PokeDao {
    @Insert
    suspend fun insert(vararg p: PokemonEntity)
    @Insert
    suspend fun insert(p: List<PokemonEntity>)
    @Update
    suspend fun update(p: PokemonEntity)
    @Query(value = "SELECT * FROM pokemon")
    suspend fun getAllPokemon(): List<PokemonEntity>
    @Query(value = "SELECT * FROM pokemon WHERE id = :id")
    suspend fun getPokemonById(id: Int): PokemonEntity
}`}
>
  <Paso lineas="1-2" titulo="Una interfaz con @Dao">
    No se implementa a mano: KSP genera la clase que hace el SQL.
  </Paso>
  <Paso lineas="3-6" titulo="@Insert sobrecargado">
    La misma función con `vararg` (uno o varios sueltos: `insert(a, b, c)`) y con `List`. Room genera el `INSERT` a partir de la entidad.
  </Paso>
  <Paso lineas="7-8" titulo="@Update">
    Actualiza la fila que tenga la misma clave primaria que la entidad que le pasas.
  </Paso>
  <Paso lineas="9-10" titulo="@Query">
    Para leer se escribe el SQL. `FROM pokemon` es el `tableName` de la entidad.
  </Paso>
  <Paso lineas="11-12" titulo="Parámetros con :nombre">
    `:id` se sustituye por el parámetro `id` de la función. Solo sirve para **valores**, no para nombres de tabla ni de columna.
  </Paso>
  <Paso titulo="Todo suspend">
    Todas las funciones son `suspend`: el acceso a la base se hace con corrutinas, fuera del hilo principal. Se llaman desde `viewModelScope.launch` o desde otra `suspend`.
  </Paso>
</Recorrido>

- El DAO se escribió primero como `PokemonDAO` con un `create(pokemon: Pokemon)`, se rehízo como `PokeDao` y acabó en el mismo archivo que la entidad, `Pokemon.kt`. No se sabe si el archivo `PokeDao.kt` se borró o se quedó vacío <Dudoso />.
- Había también un `insert(p: PokemonEntity)` de una sola entidad, que acaba comentado.

## La base de datos

```kotlin title="data/PokemonDatabase.kt"
@Database(entities = [PokemonEntity::class], version = 1)
abstract class PokemonDatabase(): RoomDatabase() {
    abstract fun pokemonDao(): PokeDao
}
```

- Es una `abstract class` que **hereda de `RoomDatabase()`**, con una función abstracta por cada DAO. Room genera la implementación.
- `entities` es la lista de tablas y `version` el número de versión del esquema. El tooltip enseñó también `views`, `exportSchema` (por defecto `true`) y `autoMigrations`.
- En clase la clase se escribió primero sin heredar de nada. Se vio el fallo al intentar tipar `val db: RoomDatabase` en el módulo de Hilt, y se corrigió.

### El aviso del esquema

Al compilar salió el aviso *Schema export directory was not provided*: con `exportSchema = true` (el valor por defecto), Room quiere guardar el esquema en una carpeta que no se le ha dicho. En clase solo se vio el aviso.

<NoDadoEnClase titulo="Quitar el aviso">

```kotlin
@Database(entities = [PokemonEntity::class], version = 1, exportSchema = false)
abstract class PokemonDatabase : RoomDatabase() {
    abstract fun pokemonDao(): PokeDao
}
```

  Con `exportSchema = false` Room no intenta exportar el esquema y el aviso desaparece.

</NoDadoEnClase>

## Crear la base de datos con Hilt

La base de datos no tiene `@Inject constructor`: se **construye** con `Room.databaseBuilder`. Por eso va en un módulo con `@Provides`, igual que Retrofit en el `NetworkModule`.

<Recorrido
  titulo="di/AppModule.kt"
  lenguaje="kotlin"
  codigo={`@Module
@InstallIn(SingletonComponent::class)
class AppModule {
    @Provides
    fun providesDatabase(@ApplicationContext context: Context): PokemonDatabase {
        val db = Room.databaseBuilder<PokemonDatabase>(
            context = context,
            name = "pokemon_db"
        ).build()
        return db
    }

    @Provides
    fun providesPokemonDao(db: PokemonDatabase): PokeDao {
        return db.pokemonDao()
    }
}`}
>
  <Paso lineas="1-3" titulo="Un módulo con @Provides">
    `@Module` + `@InstallIn(SingletonComponent::class)`, como `class`. `@Provides` se usa porque hay que construir el objeto; `@Binds` solo ata una interfaz a su implementación.
  </Paso>
  <Paso lineas="5" titulo="@ApplicationContext">
    Room necesita un `Context`. Con `@ApplicationContext context: Context` Hilt pasa el de la aplicación (import de `dagger.hilt.android.qualifiers.ApplicationContext`).
  </Paso>
  <Paso lineas="6-9" titulo="Room.databaseBuilder">
    Crea la base de datos con su nombre de archivo. Se reescribió con argumentos con nombre, y el nombre pasó de `pokemon.db` a `pokemon_db`. El popup enseñaba otras sobrecargas del builder (con `klass` y con `factory`).
  </Paso>
  <Paso lineas="13-16" titulo="Provides encadenados">
    Para dar el DAO, la función recibe la `PokemonDatabase`, que Hilt ya sabe crear con el otro `@Provides`, y le pide `pokemonDao()`. Así el repositorio puede pedir directamente un `PokeDao`.
  </Paso>
</Recorrido>

<Comparar titulo="Una sola base de datos">
  <Lado tipo="evitar">

```kotlin
@Provides
fun providesDatabase(@ApplicationContext context: Context): PokemonDatabase {
    val db = Room.databaseBuilder<PokemonDatabase>(
        context = context,
        name = "pokemon_db"
    ).build()
    return db
}
```

Sin `@Singleton`, Hilt ejecuta la función cada vez que alguien pide la base de datos o el DAO: se crearía una base nueva en cada inyección.

  </Lado>
  <Lado tipo="bien">

<NoDadoEnClase inline />

```kotlin
@Module
@InstallIn(SingletonComponent::class)
object DatabaseModule {
    @Provides
    @Singleton
    fun providesDatabase(@ApplicationContext context: Context): PokemonDatabase =
        Room.databaseBuilder<PokemonDatabase>(context = context, name = "pokemon_db").build()

    @Provides
    fun providesPokemonDao(db: PokemonDatabase): PokeDao = db.pokemonDao()
}
```

Con `@Singleton` hay una sola base de datos para toda la app. El DAO no lo necesita: sale siempre de esa misma base. Con `object` no hace falta crear instancias del módulo.

  </Lado>
</Comparar>

Para que Hilt funcione hacen falta además la `Application` con `@HiltAndroidApp` (aquí `RoomApplication`, en el paquete `di`, registrada con `android:name=".di.RoomApplication"`) y `@AndroidEntryPoint` en la Activity.

## Lo que no se dio de Room <NoDadoEnClase inline />

En clase solo hubo una tabla y funciones `suspend`. Para el proyecto hacen falta, y están explicadas en [Room con relaciones](/docs/2-dam/kotlin/para-el-proyecto/room-relaciones) y [Room como fuente de verdad](/docs/2-dam/kotlin/para-el-proyecto/offline-first):

- **Consultas que devuelven `Flow`**, para que la pantalla se actualice sola cuando cambia la tabla. Esas no llevan `suspend`.
- **Relaciones** entre tablas (no salieron en ninguna clase): `ForeignKey`, `@Embedded` y `@Relation`. En Room 3, `@Relation` se escribe con `parentColumns = ["id"]` y `entityColumns = ["categoriaId"]`, en plural y con corchetes; la forma de Room 2 (`parentColumn = "id"`) da el error *Cannot have empty 'parentColumns' in @Relation*.
- `@Upsert` (insertar o actualizar) y `@Delete`.
- **Migraciones**: si cambias una entidad, hay que subir `version`. En desarrollo basta con desinstalar la app.

  <Tarjeta frente="`@Database(entities, version)`">Sobre una `abstract class` que hereda de `RoomDatabase()`, con un `abstract fun` por DAO.</Tarjeta>
  <Tarjeta frente="`ksp(...)` frente a `implementation(...)`">`ksp` para los compiladores que generan código (Room, Hilt). `implementation` para lo que va dentro de la app.</Tarjeta>
  <Tarjeta frente="Database Inspector">View → Tool Windows → App Inspection. Enseña las tablas de Room con la app en marcha.</Tarjeta>
</Flashcards>

<Ejercicio titulo="Una tabla de tareas" dificultad="facil">
  Escribe la entidad de Room 3 para una tarea con `id` (clave primaria), `title`, `description` (que puede ser nula) e `isCompleted`. La tabla se tiene que llamar `task`.

  <Pista>Una `data class` con `@Entity(tableName = ...)` y `@PrimaryKey` en el `id`.</Pista>
  <Pista>Lo que puede ser nulo se declara con `?`.</Pista>

  <Solucion>

```kotlin
import androidx.room3.Entity
import androidx.room3.PrimaryKey

@Entity(tableName = "task")
data class TaskEntity(
    @PrimaryKey
    val id: Int,
    val title: String,
    val description: String?,
    val isCompleted: Boolean,
)
```

  `description` será una columna que admite `NULL`; el resto, `NOT NULL`.

  </Solucion>
</Ejercicio>

<Ejercicio titulo="DAO, base de datos y módulo" dificultad="media">
  Para la `TaskEntity` del ejercicio anterior, escribe:

  1. Un `TaskDao` con una función para insertar una lista, otra para actualizar una tarea y una consulta que devuelva las tareas completadas.
  2. La `TaskDatabase`.
  3. El módulo de Hilt que crea la base de datos (con el nombre `task_db`) y da el DAO, sin olvidar que solo debe haber una base de datos.

  <Pista>Para las completadas: `WHERE isCompleted = 1`. En SQLite los `Boolean` se guardan como 0 y 1.</Pista>
  <Pista>Es igual que el `AppModule` de clase, con `@Singleton` en la base de datos.</Pista>

  <Solucion>

```kotlin
@Dao
interface TaskDao {
    @Insert
    suspend fun insert(tasks: List<TaskEntity>)

    @Update
    suspend fun update(task: TaskEntity)

    @Query("SELECT * FROM task WHERE isCompleted = 1")
    suspend fun getCompleted(): List<TaskEntity>
}

@Database(entities = [TaskEntity::class], version = 1, exportSchema = false)
abstract class TaskDatabase : RoomDatabase() {
    abstract fun taskDao(): TaskDao
}

@Module
@InstallIn(SingletonComponent::class)
object DatabaseModule {
    @Provides
    @Singleton
    fun providesDatabase(@ApplicationContext context: Context): TaskDatabase =
        Room.databaseBuilder<TaskDatabase>(context = context, name = "task_db").build()

    @Provides
    fun providesTaskDao(db: TaskDatabase): TaskDao = db.taskDao()
}
```

  Los imports de Room son de `androidx.room3` (`Dao`, `Insert`, `Update`, `Query`, `Database`, `Room`, `RoomDatabase`). El `@Singleton` y el `exportSchema = false` no se pusieron en clase, pero conviene ponerlos.

  </Solucion>
</Ejercicio>

## Resumen

<Glosario titulo="Conceptos clave">
  <Termino nombre="Room">Base de datos local de Android sobre SQLite, con clases y anotaciones en vez de SQL a mano.</Termino>
  <Termino nombre="Entity">Una `data class` con `@Entity` que es una tabla.</Termino>
  <Termino nombre="DAO">La interfaz con `@Insert`, `@Update` y `@Query`. Room escribe su implementación.</Termino>
  <Termino nombre="@Database">La clase abstracta que hereda de `RoomDatabase` y da los DAO.</Termino>
  <Termino nombre="KSP">El procesador que lee las anotaciones y genera código al compilar. Lo usan Room y Hilt.</Termino>
  <Termino nombre="@ApplicationContext">Calificador de Hilt para recibir el `Context` de la aplicación.</Termino>
  <Termino nombre="Database Inspector">Herramienta de Android Studio para ver las tablas de Room en tiempo real.</Termino>
</Glosario>
