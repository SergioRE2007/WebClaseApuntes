Un **servicio** es una clase que guarda la lógica que no es de la pantalla: pedir datos a una API, guardar el estado que comparten varios componentes, hacer cálculos… El componente se queda con lo suyo, **pintar y responder al usuario**, y le pide el servicio a Angular en vez de crearlo con `new`. A eso se le llama **inyección de dependencias** (DI).

<DeClase fecha="27/10, 28/10" proyecto="angular-http y proj-fakestore" nota="Act 8, Catálogo de productos con un Service" />

<Callout type="idea" title="Lo que vas a aprender">
  - Por qué la petición HTTP va en un servicio y no en el componente.
  - Qué hace `@Injectable({ providedIn: 'root' })`.
  - Las dos formas de inyectar: `inject()` (la que más se usa en clase) y el constructor.
  - Por qué sin `private` en el constructor sale el error TS2339.
</Callout>

## Separar responsabilidades

El documento de la Act 8 lo resume con este reparto:

| Pieza | Se encarga de |
| --- | --- |
| `AppComponent` | Mostrar la información y gestionar la interfaz. |
| `ProductService` | Obtener los datos y hablar con la API por HTTP. |
| Fake Store API | Devolver los productos en JSON. |

Una de las preguntas finales de la actividad es justo esa: *¿por qué se crea `ProductService` en vez de hacer la petición desde `AppComponent`?* Porque así:

- El componente no sabe **de dónde** salen los datos. Si mañana cambias la Fake Store por vuestra API, solo tocas el servicio.
- Varios componentes pueden usar el mismo servicio sin repetir código.
- Es más fácil probar el componente con un servicio falso.

Si vienes de Java, es la misma idea que un `@Service` de Spring inyectado con `@Autowired`, o que Hilt en Android (ver [Kotlin](/docs/2-dam/kotlin)).

## Crear un servicio

```bash title="Terminal"
ng g s services/product
```

Crea `product.service.ts` (y su `.spec.ts`):

```ts title="src/app/services/product.service.ts (recién generado)"
import { Injectable } from '@angular/core';

@Injectable({
  providedIn: 'root'
})
export class ProductService {

  constructor() { }
}
```

- **`@Injectable`** marca la clase como algo que el sistema de inyección puede crear y entregar.
- **`providedIn: 'root'`** lo registra en el **inyector raíz**: hay **una sola instancia para toda la aplicación** (un *singleton*), y no hay que registrarlo en ningún otro sitio. Si nadie lo usa, el compilador lo quita del resultado final (*tree shaking*).

El cuerpo con `HttpClient` y `getProducts()` está en [HttpClient](/docs/2-dam/acceso-a-datos/angular/httpclient).

## Pedir el servicio: `inject()` o constructor

<DeClase fecha="28/10" proyecto="proj-fakestore" />

El 28/10 se probaron las dos formas en el mismo componente y se dejó escrito en comentarios:

```ts title="src/app/app.component.ts (proj-fakestore)"
import { Component, inject, OnInit } from '@angular/core';
import { RouterOutlet } from '@angular/router';
import { ProductService } from './services/product.service';
import { Product } from './models/product';

@Component({
  selector: 'app-root',
  imports: [RouterOutlet],
  templateUrl: './app.component.html',
  styleUrl: './app.component.css'
})
export class AppComponent implements OnInit {

  products?: Product[];

  //Inyección por función
  private productService = inject(ProductService);

  //Inyección por constructor, importante el scope de la propiedad en el constructor
  //constructor( private productService: ProductService ) {}

  ngOnInit(): void {
    this.productService.getProducts().subscribe( products => {
      console.log(products);
      this.products = products;
    });
  }

  title = 'proj-fakestore';
}
```

<Comparar titulo="Las dos formas de inyectar">
  <Lado tipo="bien" titulo="Con inject() (la de clase)">

```ts
export class AppComponent {
  private productService = inject(ProductService);
}
```

Una propiedad normal inicializada con `inject()`. Es la forma moderna y la que más se usa en clase, también dentro de los servicios (`inject(HttpClient)`). Ojo: el `AppComponent` de `proj-game` que se repasó el 05/11 pide `GameService` por constructor (`constructor(private gameService: GameService){}`), así que verás las dos.

  </Lado>
  <Lado titulo="Por constructor">

```ts
export class AppComponent {
  constructor(private productService: ProductService) {}
}
```

Angular ve el tipo del parámetro y le pasa la instancia. Funciona igual, pero **hace falta el `private`** (o `protected`, `public`, `readonly`).

  </Lado>
</Comparar>

### El error TS2339

Lo que se enseñó a propósito en clase: el constructor **sin** modificador.

```ts title="Así falla"
constructor( productService: ProductService ) {}

ngOnInit(): void {
  this.productService.getProducts();
  // Property 'productService' does not exist on type 'AppComponent'. ts(2339)
}
```

En TypeScript, un parámetro del constructor **con** `private` (o `public`, `protected`, `readonly`) es una *parameter property*: declara la propiedad y la asigna a la vez. **Sin** el modificador, es un parámetro normal que solo existe dentro del constructor, así que `this.productService` no existe. Eso es lo que quería decir el comentario "importante el scope de la propiedad en el constructor".

<Comparar titulo="Una parameter property es un atajo" columnas>
  <Lado titulo="TypeScript">

```ts
class AppComponent {
  constructor(
    private productService: ProductService
  ) {}
}
```

  </Lado>
  <Lado titulo="Lo mismo, al estilo Java">

```ts
class AppComponent {
  private productService: ProductService;
  constructor(productService: ProductService) {
    this.productService = productService;
  }
}
```

  </Lado>
</Comparar>

### `private readonly`

En `angular-http` (27/10) las dependencias se declaran `private readonly`:

```ts title="posts.component.ts"
private readonly postsService = inject(PostsService);
```

- `private`: solo la clase lo usa. La plantilla no lo necesita.
- `readonly`: nadie puede reasignarlo después (`this.postsService = ...` daría error). Es como un `final` de Java.

## Otros sitios donde dar un servicio <NoDadoEnClase inline />

<NoDadoEnClase>
  Viene en la unidad 5 de servicios e inyección de dependencias de las guías (la que se enseñó como teoría el 28/10), pero en clase solo se usó `providedIn: 'root'`.
</NoDadoEnClase>

| Dónde | Cómo | Resultado |
| --- | --- | --- |
| Inyector raíz | `@Injectable({ providedIn: 'root' })` | Una instancia para toda la aplicación. |
| Configuración de la aplicación | `providers: [ProductService]` en `app.config.ts` | También global, pero no se elimina aunque no se use. |
| Un componente | `providers: [ProductService]` en su `@Component` | Una instancia **por cada** componente de ese tipo, compartida con sus hijos. |

`provideHttpClient()` y `provideRouter(routes)` de `app.config.ts` son justo eso: *providers* globales que registran `HttpClient` y el router.

## Ejercicios

<Ejercicio titulo="Un servicio sin HTTP" dificultad="facil">
  Crea `CarritoService` con una lista privada de nombres de productos y los métodos `anadir(nombre: string)` y `total(): number`. Inyéctalo en dos componentes distintos, `TiendaComponent` (que añade) y `CabeceraComponent` (que enseña el total), y comprueba que los dos ven el mismo carrito.

  <Pista>Con `providedIn: 'root'` los dos componentes reciben la misma instancia.</Pista>
  <Pista>Para que la cabecera pinte el total, llama al método en la plantilla: `{{ carrito.total() }}`. Como la plantilla lo usa, el servicio no puede ser `private` en ese componente.</Pista>

  <Solucion>

```ts title="carrito.service.ts"
import { Injectable } from '@angular/core';

@Injectable({ providedIn: 'root' })
export class CarritoService {
  private productos: string[] = [];

  anadir(nombre: string): void {
    this.productos.push(nombre);
  }

  total(): number {
    return this.productos.length;
  }
}
```

```ts title="tienda.component.ts"
export class TiendaComponent {
  private readonly carrito = inject(CarritoService);

  protected comprar(nombre: string): void {
    this.carrito.anadir(nombre);
  }
}
```

```ts title="cabecera.component.ts"
export class CabeceraComponent {
  protected readonly carrito = inject(CarritoService);
}
```

```html title="cabecera.component.html"
<p>Carrito: {{ carrito.total() }} productos</p>
```

Al pulsar "comprar" en la tienda, el número de la cabecera sube, porque los dos componentes tienen el mismo `CarritoService`.

  </Solucion>
</Ejercicio>

<Ejercicio titulo="De constructor a inject()" dificultad="facil">
  Pasa este componente a `inject()` y explica por qué daba error:

```ts
export class ListaComponent implements OnInit {
  constructor(gameService: GameService) {}

  ngOnInit(): void {
    this.gameService.getAll().subscribe(games => console.log(games));
  }
}
```

  <Solucion>

```ts
export class ListaComponent implements OnInit {
  private readonly gameService = inject(GameService);

  ngOnInit(): void {
    this.gameService.getAll().subscribe(games => console.log(games));
  }
}
```

Sin `private` en el constructor, `gameService` era solo un parámetro y no una propiedad: `this.gameService` daba **TS2339**. Con `inject()` declaras la propiedad directamente. La otra solución es `constructor(private gameService: GameService) {}`.

  </Solucion>
</Ejercicio>
