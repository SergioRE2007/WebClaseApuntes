El documento **"Requisitos de Acceso a Datos del Proyecto Intermodular"** tiene 8 apartados. Aunque se llame "de Acceso a Datos", casi todo lo que pide es **backend y base de datos**, que en clase se ha dado en APIs con Node. Aquí tienes cada apartado resumido, de dónde sale cada requisito (§ es el número de apartado del documento) y si se dio en clase.

<Callout type="info" title="Leyenda">
  **Dado**: se vio entero en clase. **A medias**: se vio una parte (por ejemplo, solo con el modelo `User` del profesor). **No dado**: no salió; está explicado en este bloque y marcado como no dado en clase.
</Callout>

## §1. La arquitectura que piden

Una **aplicación web completa con persistencia**, por capas: **Angular** para la interfaz, **Node con Express (o Nest)** para el backend, **Prisma (o TypeORM)** como ORM, **PostgreSQL** como base de datos y una **API REST con JSON** entre medias. En clase se eligió Express y Prisma.

| Requisito | Estado | Dónde se dio |
| --- | --- | --- |
| Separar presentación, lógica y persistencia | Dado | 20/10 y 27/10: `app.ts`, rutas, controlador, servicio y `config/db.ts` |
| Angular como interfaz principal | Dado en Acceso a Datos | Ver [Angular avanzado](/docs/2-dam/acceso-a-datos/angular-avanzado) |

La interfaz "tendrá un peso relevante", pero tiene que estar respaldada por una capa de acceso a datos "suficientemente completa": no vale una web muy bonita sobre un backend de un solo modelo.

## §2. Interfaz Angular

Navegación con Router, componentes reutilizables, listados y detalle, formularios de crear y editar (se valoran los **reactivos**), borrar con confirmación, búsqueda, filtro, orden, paginación y los estados de carga, vacío, error y confirmación. El HTTP, siempre dentro de **servicios** de Angular.

Esta parte **no es de este bloque**: está en [Angular avanzado](/docs/2-dam/acceso-a-datos/angular-avanzado). Lo que sí toca al backend es que Angular **solo manda los criterios** (búsqueda, filtro, orden y página) y la consulta la hace el backend: eso se explica en [Listado con búsqueda y paginación](/docs/2-dam/apis/backend-proyecto/listado-paginado).

## §3. Modelo de datos y persistencia

Piden un modelo relacional "suficientemente completo":

- Varias entidades persistentes.
- Claves primarias y externas.
- Campos obligatorios y opcionales.
- Restricciones y valores únicos cuando proceda.
- Relaciones **1 y N**, que se usen de verdad en la aplicación.
- Prisma o TypeORM con modelos, relaciones, restricciones e integridad.
- **Migraciones** guardadas en el repositorio.
- Un **seed** con datos suficientes para probar sin meterlo todo a mano.

| Requisito | Estado | Dónde se dio | Dónde se explica |
| --- | --- | --- | --- |
| PostgreSQL | Dado | 20/10: Postgres 16 en `docker-compose.yml`. 03/11: Supabase | [PostgreSQL](/docs/2-dam/apis/backend/postgres-docker-supabase) |
| Prisma | Dado | 27/10: `schema.prisma` y migración `init`. 03/11: migraciones, *drift* y `db pull` | [Prisma 6](/docs/2-dam/apis/backend/prisma) |
| Varias entidades relacionadas | A medias | El repositorio del profesor solo tiene `User` (y `Media`, con su clave ajena a `User`, en la v1.1) | [Modelo y seed](/docs/2-dam/apis/backend-proyecto/modelo-y-seed) |
| Relaciones 1 y N | A medias | Igual: solo `User` → `Media` | [Modelo y seed](/docs/2-dam/apis/backend-proyecto/modelo-y-seed) |
| Migraciones | Dado | 27/10 y 03/11. Sube la carpeta `prisma/migrations` | [Prisma 6](/docs/2-dam/apis/backend/prisma#migraciones) |
| Seed de datos | No dado | Nunca (`db seed` solo salió en la ayuda de Prisma) | [Modelo y seed](/docs/2-dam/apis/backend-proyecto/modelo-y-seed) |

## §4. API REST y organización del backend

Una API REST con las operaciones equivalentes a `GET`, `GET` por id, `POST`, `PUT`/`PATCH` y `DELETE`, y una organización **modular**: rutas, controladores, servicios, ORM y base de datos separados. El documento dice expresamente que **no vale** concentrar rutas, lógica y acceso a datos en un único fichero.

| Requisito | Estado | Dónde se dio |
| --- | --- | --- |
| API REST | Dado | 20/10 a 03/11 |
| Organización por módulos | Dado | 27/10: `src/modules/users/` con `users.routes.ts`, `users.controller.ts`, `users.service.ts` y `users.schema.ts` |
| Operaciones CRUD | Dado | 27/10: `GET /`, `GET /:id`, `PATCH /:id` y `DELETE /:id` de usuarios, y el `POST` del registro. P2025 → 404 y P2002 → 409 |

Lo que te falta es repetir ese módulo para **tus** entidades.

## §5. Operaciones y consultas

El proyecto **no puede quedarse en el CRUD básico**. Con el ORM hay que usar también:

- Consultas por diferentes criterios.
- Información relacionada entre entidades.
- Filtros, ordenaciones, búsquedas y paginación.
- Selección de campos.

Y dos condiciones importantes:

1. **Al menos uno** de los listados principales tiene que tener **búsqueda, filtrado, ordenación y paginación** a la vez.
2. Esos criterios se **mandan desde Angular al backend** y se convierten en consultas del ORM. Si hay bastantes datos, **no vale** descargarlo todo y filtrar en Angular. La API tiene que dar lo necesario para paginar (el **total**).

| Requisito | Estado | Dónde se dio | Dónde se explica |
| --- | --- | --- | --- |
| Consultas relacionales y por criterios | A medias | Solo el `select` que quita `passwordHash` y el `orderBy: { id: 'asc' }` | [Consultas con datos relacionados](/docs/2-dam/apis/backend-proyecto/consultas-relacionadas) |
| Búsqueda y filtrado | No dado | En el backend, nunca. En Angular (12/11) solo con JSON Server (`_page`, `_limit`) | [Listado paginado](/docs/2-dam/apis/backend-proyecto/listado-paginado) |
| Ordenación y paginación | No dado | Igual que la fila anterior. Falta devolver el total | [Listado paginado](/docs/2-dam/apis/backend-proyecto/listado-paginado) |

## §6. Operación de negocio y transacción

Al menos **una operación de negocio** con varias acciones relacionadas, que no se reduzca a un CRUD: comprobaciones previas, crear o cambiar datos relacionados, actualizar estados, aplicar reglas de negocio y mantener la consistencia. Si hay riesgo de dejar los datos a medias, con **transacción**: o se hace todo o no se hace nada.

| Requisito | Estado | Dónde se dio | Dónde se explica |
| --- | --- | --- | --- |
| Operación de negocio | No dado | Nunca | [Transacciones](/docs/2-dam/apis/backend-proyecto/transacciones) |
| Uso de transacciones | No dado | Nunca | [Transacciones](/docs/2-dam/apis/backend-proyecto/transacciones) |

## §7. Validación, errores e integridad

- Validar **en Angular y en el backend**. El servidor comprueba campos obligatorios, tipos y formatos, rangos, que existan los datos relacionados, las restricciones del modelo y las reglas de negocio.
- Códigos HTTP que distingan **bien**, **petición incorrecta**, **no existe**, **conflicto** y **error interno**.
- Angular captura esos errores y se los explica al usuario.
- **Integridad**: claves ajenas, únicos, qué pasa al borrar datos relacionados y que no queden operaciones a medias.
- Cadenas de conexión y credenciales en **variables de entorno**, nunca en el código.

| Requisito | Estado | Dónde se dio | Dónde se explica |
| --- | --- | --- | --- |
| Validación en el backend | Dado | 27/10: Zod 4 y el middleware `validate` | Falta validar los *query params* del listado: [Listado paginado](/docs/2-dam/apis/backend-proyecto/listado-paginado) |
| Gestión de errores | Dado | 20/10: `errorHandler`. 27/10: códigos de Prisma. 03/11: Winston | Si quieres una clase de error propia: [Errores HTTP](/docs/2-dam/apis/backend-proyecto/errores-http) |
| Integridad (borrados relacionados) | A medias | `onDelete: Cascade` en `Media` | [Modelo y seed](/docs/2-dam/apis/backend-proyecto/modelo-y-seed) |
| Variables de entorno | Dado | 20/10: `env.ts` y dotenv, con `required()` | [Servidor con Express 5](/docs/2-dam/apis/backend/servidor-express#variables-de-entorno-envts) |

## Lo que te pueden pedir en la defensa

<Callout type="idea" title="Es una previsión">
  Esto no lo ha dicho el profesor: es lo más probable que te pidan demostrar de cada requisito.
</Callout>

- **Prisma:** añadir un campo, crear la migración y enseñar el SQL que genera.
- **Seed:** `npx prisma migrate reset` y ver que la base vuelve con datos.
- **Listado:** cambiar el filtro en Angular y enseñar la petición en la pestaña Red del navegador (los parámetros viajan en la URL y la respuesta trae solo una página).
- **Transacción:** forzar un error en mitad de la operación y comprobar que no se guardó nada.
- **Errores HTTP:** provocar un 400 (dato mal), un 404 (id que no existe) y un 409 (duplicado).

<Ejercicio titulo="Tu tabla de requisitos" dificultad="facil">
  Copia la tabla del §8 y, para tu proyecto, escribe al lado de cada requisito **con qué entidad o qué ruta lo cumples**. Por ejemplo, para "Relaciones 1 y N" escribe qué dos entidades están relacionadas y cuál es la clave ajena.

Un ejemplo para una app de reservas de pistas:

| Requisito | En mi proyecto |
| --- | --- |
| Varias entidades | `Usuario`, `Pista`, `Hueco` y `Reserva` |

| Consultas relacionales | La pista con sus huecos libres (`include` con `where`) |

</Solucion>
</Ejercicio>

<Ejercicio titulo="¿CRUD u operación de negocio?" dificultad="media">
  Di cuáles de estas acciones son una operación de negocio que necesita transacción y cuáles son un CRUD normal:

  1. Cambiar el nombre de una categoría.
  2. Confirmar un pedido restando el stock de cada producto.
  3. Borrar un comentario.
  4. Transferir puntos de un usuario a otro.
  5. Registrar un usuario creando también su perfil en otra tabla.

  <Pista>Pregúntate: si falla a mitad, ¿quedan los datos inconsistentes?</Pista>

  <Solucion>

- **CRUD normal:** 1 y 3. Son una sola sentencia: si falla, no se ha cambiado nada.
- **Operación de negocio con transacción:** 2, 4 y 5. Las tres cambian varias filas o tablas. Si en la 2 falta stock del tercer producto, hay que devolver el de los dos primeros. En la 4, si se restan los puntos a uno y falla el sumárselos al otro, se pierden puntos. En la 5, quedaría un usuario sin perfil.

</Solucion>
</Ejercicio>
