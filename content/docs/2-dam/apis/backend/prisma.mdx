**Prisma** es el ORM del proyecto: describes las tablas en un fichero, `schema.prisma`, y Prisma genera dos cosas a partir de él: el **SQL** de las migraciones y un **cliente con tipos** para hacer las consultas desde TypeScript. Se usa **Prisma 6** (`@prisma/client ^6.18.0`; el cliente generado es la 6.19.0).

## Qué es un ORM

Un <Concepto termino="ORM" definicion="Object-Relational Mapping: una librería que deja trabajar con la base de datos usando objetos y funciones en vez de escribir SQL a mano.">ORM</Concepto> traduce entre objetos y tablas. Si has usado JPA o Hibernate en Java, la idea es la misma con otras piezas:

| JPA / Hibernate | Prisma |
| --- | --- |
| Clases con `@Entity`, `@Id`, `@Column` | Bloques `model` en `schema.prisma` |
| `EntityManager` o un `JpaRepository` | El `PrismaClient`: `prisma.user.findMany()` |
| Flyway o Liquibase para las migraciones | `prisma migrate` |

La diferencia práctica: en Prisma **el modelo no son clases tuyas**. Escribes el `schema.prisma` y `npx prisma generate` crea el cliente con sus tipos en `node_modules`. Si cambias el schema, hay que volver a generar.

## `schema.prisma`

Está en `prisma/schema.prisma`. Esta es la versión con la tabla `Media` (la de la v1.1, la que había el 03/11):

  format       String

  bytes        Int
  width        Int?
  height       Int?
  originalName String?
  folder       String?

  @@index([userId])
  @@index([createdAt])

>
  <Paso lineas="1-3" titulo="generator">
    Qué se genera a partir del schema: el cliente de JavaScript/TypeScript (`prisma-client-js`), que acaba en `node_modules/@prisma/client`.
  </Paso>
  <Paso lineas="5-8" titulo="datasource">
    A qué base se conecta: PostgreSQL, con la cadena de la variable de entorno `DATABASE_URL`. Con Prisma 6, la `url` va aquí.
  </Paso>
  <Paso lineas="11" titulo="Clave primaria autoincremental">
    `@id` marca la clave primaria y `@default(autoincrement())` hace que la ponga la base (en SQL sale `SERIAL`).
  </Paso>
  <Paso lineas="12" titulo="@unique">
    No puede haber dos usuarios con el mismo email. Si se intenta, Prisma lanza el error **P2002**, que la API traduce a 409.
  </Paso>
  <Paso lineas="14" titulo="passwordHash, nunca la contraseña">
    En la base nunca se guarda la contraseña en claro, solo su hash de bcrypt. Por eso en las consultas se usa `select` para no devolver nunca este campo.
  </Paso>
  <Paso lineas="15" titulo="@default(now())">
    La fecha de creación la pone la base al insertar.
  </Paso>
  <Paso lineas="16" titulo="El lado 'muchos' de la relación">
    `media Media[]`: un usuario tiene muchos `Media`. Este campo no es una columna; solo existe en el cliente de Prisma.
  </Paso>
  <Paso lineas="21-22" titulo="La clave ajena">
    `userId` es la columna de verdad. `user` describe la relación: `fields` es la columna de esta tabla y `references` la de `User`. `onDelete: Cascade` borra los `Media` de un usuario cuando se borra el usuario.
  </Paso>
  <Paso lineas="28-31" titulo="Campos opcionales">
    `?` detrás del tipo: la columna admite `NULL`.
  </Paso>
  <Paso lineas="34-35" titulo="Índices">
    `@@index` (con dos arrobas, porque es del modelo entero) crea índices para buscar rápido por `userId` y por `createdAt`.
  </Paso>
</Recorrido>

- Los campos de `Media` (`publicId`, `secureUrl`, `format`, `resourceType`, `bytes`, `width`, `height`, `folder`) son los datos que devuelve Cloudinary al subir un archivo.
- El modelo `Media` está reconstruido a partir del diff que salió al hacer `db pull` <Dudoso nota="Dudoso en los detalles: no se vio el fichero completo en ninguna captura." />.
- Hasta la v1.1 el schema solo tenía `User`, sin la línea `media Media[]`.

## Un solo `PrismaClient`

El cliente se crea **una sola vez** para toda la app, en `src/config/db.ts`, y el resto de ficheros lo importan:

```ts title="src/config/db.ts"
import { PrismaClient } from '@prisma/client';

export const prisma = new PrismaClient();
```

Cada `PrismaClient` abre su propio grupo de conexiones con la base, así que crear uno en cada fichero (o en cada petición) gastaría conexiones de más. Con uno exportado, todos los servicios comparten las mismas.

Al pasar el ratón por `prisma.user`, el editor lista las operaciones que tiene cada modelo. Las que salen en clase:

| Operación | Qué hace | Ejemplo de clase |
| --- | --- | --- |
| `findMany` | Varias filas, con `select`, `orderBy`… | Listar usuarios |
| `findUnique` | Una fila por un campo `@id` o `@unique` | Buscar por `id` o por `email` |
| `create` | Insertar | Registrar un usuario |
| `update` | Modificar por `where` | `PATCH /api/users/:id` |
| `delete` | Borrar por `where` | `DELETE /api/users/:id` |

Cómo se usan en el servicio lo tienes en [CRUD de usuarios](/docs/2-dam/apis/backend/crud-usuarios).

## Migraciones

Una **migración** es un fichero SQL con un cambio de la base de datos. Cuando cambias `schema.prisma`, `npx prisma migrate dev --name nombre` compara el schema con la base, escribe el SQL necesario, lo aplica y vuelve a generar el cliente.

Las migraciones **se guardan en el repositorio**, en orden, una carpeta por migración:

<Files>
  <Folder name="prisma" defaultOpen>
    <Folder name="migrations" defaultOpen>
      <Folder name="20251104112830_init" defaultOpen>
        <File name="migration.sql" />
      </Folder>
      <Folder name="20251120090028_add_media_table">
        <File name="migration.sql" />
      </Folder>
      <File name="migration_lock.toml" />
    </Folder>
    <File name="schema.prisma" />
  </Folder>
</Files>

El nombre de la carpeta es la fecha y hora (`20251104112830` = 04/11/2025 a las 11:28:30) más el nombre que le diste. `migration_lock.toml` apunta el proveedor (PostgreSQL). Este es el SQL que generó la primera:

```sql title="prisma/migrations/20251104112830_init/migration.sql"
-- CreateTable
CREATE TABLE "User" (
    "id" SERIAL NOT NULL,
    "email" TEXT NOT NULL,
    "name" TEXT NOT NULL,
    "passwordHash" TEXT NOT NULL,
    "createdAt" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT "User_pkey" PRIMARY KEY ("id")
);
-- CreateIndex
CREATE UNIQUE INDEX "User_email_key" ON "User"("email");
```

Fíjate en cómo se traduce el modelo: `Int @id @default(autoincrement())` pasa a `SERIAL` con `PRIMARY KEY`, `String` a `TEXT`, `DateTime @default(now())` a `TIMESTAMP(3) ... DEFAULT CURRENT_TIMESTAMP` y `@unique` a un `UNIQUE INDEX`. Y todos los nombres van **entre comillas dobles**, por eso en el SQL Editor hay que escribir `"User"` ([PostgreSQL con Docker y Supabase](/docs/2-dam/apis/backend/postgres-docker-supabase)).

La segunda migración, `add_media_table`, crea la tabla `"Media"` con sus columnas.

<NoSeVio titulo="El resto de add_media_table">No se ven los índices ni la clave ajena de esa migración: solo el `CREATE TABLE`.</NoSeVio>

### La tabla `_prisma_migrations`

La base de datos apunta qué migraciones tiene aplicadas en una tabla que crea Prisma, `_prisma_migrations`. El 03/11, en Supabase:

```sql title="SQL Editor"
select * from _prisma_migrations;
```

Devolvía 2 filas, con `migration_name`, `checksum`, `started_at`, `finished_at` y `applied_steps_count = 1`. Así Prisma sabe qué carpetas de `prisma/migrations` faltan por aplicar en cada base.

## Los comandos

| Comando | Qué hace |
| --- | --- |
| `npx prisma generate` | Genera el cliente a partir de `schema.prisma`. Después de `npm install` y de cada cambio del schema. |
| `npx prisma migrate dev --name x` | Desarrollo: crea la migración del cambio, la aplica y genera el cliente. **Detecta el drift.** |
| `npx prisma migrate status` | Compara la carpeta de migraciones con `_prisma_migrations`. **No ve el drift.** |
| `npx prisma migrate reset` | Borra la base y la vuelve a crear con todas las migraciones. **Se pierden los datos**; pide confirmación. |
| `npx prisma migrate deploy` | Producción: aplica las migraciones pendientes sin crear ninguna nueva. |
| `npx prisma db pull` | Introspección: reescribe `schema.prisma` a partir de la base. Después, `generate`. |
| `npx prisma db push` | Lleva el schema a la base **sin crear migración** (para prototipos). |
| `npx prisma studio` | Abre una web para ver y editar los datos. |
| `npx prisma db seed`, `db execute` | Solo se vieron en la ayuda de la CLI. |

## El experimento del drift (03/11)

El <Concepto termino="Drift" definicion="Cuando la base de datos ya no coincide con lo que dicen las migraciones, porque alguien la cambió a mano fuera de Prisma.">drift</Concepto> es cuando la base ya no coincide con lo que dejarían las migraciones, porque alguien la ha cambiado a mano. El 03/11 el profesor lo provocó a propósito:

<Steps>
  <Step>

#### Cambiar la base a mano

En el Table Editor de Supabase renombró la tabla `Media` a `MediaElements`. `select * from "MediaElements"` funcionaba.

  </Step>
  <Step>

#### `migrate status` no se entera

Respondió `2 migrations found… Database schema is up to date!`. Solo mira si las carpetas de migraciones están apuntadas en `_prisma_migrations`, y lo estaban.

  </Step>
  <Step>

#### `migrate dev` sí lo detecta

Comparó la base real con la esperada, enseñó las diferencias (tabla `MediaElements` añadida, `Media` quitada, sus índices y la FK) y dijo *"We need to reset the public schema… All data will be lost"*.

  </Step>
  <Step>

#### `migrate reset` lo arregla

Se respondió `yes`: la base se borró y se recreó desde las migraciones. La tabla volvió a llamarse `Media`, sin datos.

  </Step>
  <Step>

#### Segunda prueba: `db pull`

Renombró otra vez la tabla, ahora a `MediaElement`, y ejecutó `npx prisma db pull`. Esta vez **manda la base**: Prisma reescribió `schema.prisma` con el modelo `MediaElement`. Luego otro `migrate reset` dejó la base otra vez con `Media`.

  </Step>
</Steps>

Repítelo tú en el simulador. Prueba el orden de clase (renombrar, `migrate status`, `migrate dev`, `migrate reset`) y después la segunda prueba con `db pull` y `generate`:

<SimuladorMigraciones />

Lo que enseña: **`migrate status` solo compara las migraciones con la tabla `_prisma_migrations`**, así que un cambio hecho a mano no lo ve. **`migrate dev` compara con la base real** y detecta el drift. **`migrate reset`** recrea la base desde las migraciones (y se pierden los datos). **`db pull`** hace lo contrario: cambia el schema para que se parezca a la base, y después hace falta `generate` para que el cliente cambie (con el modelo `MediaElement`, el cliente tendría `prisma.mediaElement` y no `prisma.media`).

### Lo que escribe `db pull`

En el diff de Git de `schema.prisma` se vio esto (resumido):

```prisma title="prisma/schema.prisma después de db pull"
model User {
  // ...
  MediaElement MediaElement[]
}

model MediaElement {
  id           Int      @id(map: "Media_pkey") @default(autoincrement())
  userId       Int
  publicId     String   @unique(map: "Media_publicId_key")
  // ...
  createdAt    DateTime @default(now())
  User         User     @relation(fields: [userId], references: [id], onDelete: Cascade, map: "Media_us...")

  @@index([createdAt], map: "Media_createdAt_idx")
  @@index([userId], map: "Media_userId_idx")
}
```

- La tabla se llama `MediaElement`, pero las restricciones (la clave primaria, el `UNIQUE`, los índices) se siguen llamando como antes (`Media_pkey`…). Como no coinciden con los nombres que Prisma pondría por defecto, `db pull` los apunta con **`map:`**.
- El campo de la relación pasa a llamarse `User` y, en `User`, `MediaElement`: `db pull` usa el nombre de la tabla.
- El `map:` de la clave ajena sale cortado: <Dudoso nota="Seguramente Media_userId_fkey.">`"Media_us…"`</Dudoso>.
- Antes del `db pull` se tecleó <Dudoso nota="No es un comando real de Prisma; después se escribió npx prisma db pull.">`npx prisma update`</Dudoso>.

<Callout type="error" title="No toques las tablas a mano">
  La moraleja del experimento: los cambios de la base se hacen **siempre** cambiando `schema.prisma` y creando una migración. Si alguien cambia la base desde el panel, las migraciones dejan de cuadrar y en desarrollo acabas con `migrate reset`, que borra los datos.
</Callout>

El 03/11 se enseñó un resumen de Google con el orden que hay que seguir cuando bajas cambios de un compañero:

<Steps>
  <Step>

#### `npm install`

Por si hay dependencias nuevas.

  </Step>
  <Step>

#### `npx prisma generate`

Para que el cliente tenga los modelos del `schema.prisma` que te has bajado.

  </Step>
  <Step>

En desarrollo, aplica las migraciones nuevas a tu base. En producción, `npx prisma migrate deploy`.

  </Step>

  El resumen ponía `npx prisma db migrate deploy`. Ese comando no existe: es **`npx prisma migrate deploy`**.

## Errores típicos <NoDadoEnClase inline />

- **`@prisma/client did not initialize yet. Please run "prisma generate"`**: después de `npm install` o `npm ci` hay que ejecutar `npx prisma generate`. También cada vez que cambias el schema.
- **`migrate dev` dice que hay drift y quiere borrar la base**: alguien cambió la base fuera de las migraciones. En desarrollo, `npx prisma migrate reset`.
