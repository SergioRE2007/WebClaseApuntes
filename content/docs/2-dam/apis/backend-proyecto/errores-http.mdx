Los requisitos piden que la API use **códigos HTTP adecuados** para distinguir "operaciones correctas, peticiones incorrectas, recursos inexistentes, conflictos y errores internos", y que Angular los capture y se los explique al usuario (§7). La gestión de errores **sí se dio en clase**; aquí está lo que se vio y una mejora para lanzar errores con su código desde cualquier servicio.

<Callout type="idea" title="Lo que vas a aprender">
  - El `errorHandler` y la traducción de errores de Prisma de clase.
  - Una clase `HttpError` para lanzar errores con su código desde los servicios.
  - Qué código usar en cada caso, y `P2003`.
</Callout>

## Lo que se vio en clase

### El manejador de errores

```ts title="src/middleware/error.ts (v0.8.0, de clase)"
import type { Request, Response, NextFunction } from 'express';
import { logger } from '../utils/logger.js';

export function errorHandler(err: any, req: Request, res: Response, _next: NextFunction) {
  logger.error(`${req.method} ${req.path} - ${err.message}`);
  logger.error(err.stack);
  const status = err.status || 500;
  res.status(status).json({ message: err.message || 'Error interno' });
}
```

- Tiene **cuatro parámetros** `(err, req, res, next)`. Es lo que hace que Express lo trate como manejador de errores, aunque no use `next` (por eso lleva `_` delante).
- Usa `err.status` si el error lo trae y, si no, `500`.
- Va con `app.use(errorHandler)` **al final** de `app.ts`, después de todas las rutas. En clase se vio que el orden de los middlewares importa y que el `errorHandler` va siempre el último.
- La versión anterior a la v0.8.0 tenía `_req` y usaba `console.error(err)` en vez del logger de Winston.

### Errores de Prisma en el controlador

```ts title="users.controller.ts (fragmento de clase)"
} catch (error: any) {
  if (error.code === 'P2025') {
    return res.status(404).json({ message: 'Usuario no encontrado' });

  if (error.code === 'P2002') {
    return res.status(409).json({ message: 'El email ya está en uso' });

  res.status(500).json({ message: error.message });

```

| Código de Prisma | Cuándo salta | HTTP en clase |
| --- | --- | --- |
| `P2025` | `update` o `delete` de una fila que no existe | `404` |
| `P2002` | Se repite un valor `@unique` | `409` |

### Errores de negocio con un mensaje

En el módulo de auth, el servicio lanza `throw new Error('Email ya registrado')` y el controlador **compara el texto** para elegir el código: `409` si es ese mensaje, `401` con "Credenciales inválidas" y `400` con el resto.

Los códigos que salieron en clase: `200` (`res.json`), `201` (crear), `400` (validación o id que no es número), `401` (credenciales o falta de token), `404` (no existe), `409` (único repetido) y `500`.

## Lanzar errores con su código: HttpError <NoDadoEnClase inline />

<NoDadoEnClase>
  La clase `HttpError`, traducir `P2003` y el `errorHandler` que distingue los tipos de error no se han dado en clase.
</NoDadoEnClase>

Comparar el texto del mensaje funciona, pero si cambias una coma del mensaje en el servicio, el controlador deja de reconocerlo. Es más cómodo que el propio error lleve el código. Una clase pequeña en `src/utils/httpError.ts`:

```ts title="src/utils/httpError.ts"
export class HttpError extends Error {
  constructor(public status: number, message: string) {
    super(message);
  }
}
```

`public status` en el constructor crea la propiedad y la rellena a la vez, como un `val` en el constructor de Kotlin. En Java sería un atributo `status` y un `this.status = status` en el constructor.

### El errorHandler que lo entiende

El de clase ya traduce `P2002` y `P2025` en los controladores. Este los centraliza en el `errorHandler` y añade `HttpError` y `P2003`:

<Recorrido
  titulo="src/middleware/error.ts"
  lenguaje="ts"
  codigo={`import type { NextFunction, Request, Response } from 'express';
import { Prisma } from '@prisma/client';
import { HttpError } from '../utils/httpError.js';

export function errorHandler(err: unknown, _req: Request, res: Response, _next: NextFunction) {
  if (err instanceof HttpError) {
    return res.status(err.status).json({ error: err.message });
  }
  if (err instanceof Prisma.PrismaClientKnownRequestError) {
    if (err.code === 'P2002') return res.status(409).json({ error: 'Ya existe' });
    if (err.code === 'P2025') return res.status(404).json({ error: 'No encontrado' });
    if (err.code === 'P2003') return res.status(409).json({ error: 'Tiene datos relacionados' });
  }
  res.status(500).json({ error: 'Error interno' });
}`}
>
  <Paso lineas="5" titulo="Cuatro parámetros y err: unknown">
    Los cuatro parámetros, como el de clase. `unknown` en vez de `any` obliga a comprobar qué es el error antes de usarlo.
  </Paso>
  <Paso lineas="6-8" titulo="Errores propios">
    Si es un `HttpError`, ya trae su código y su mensaje: se responde con ellos.
  </Paso>
  <Paso lineas="9-13" titulo="Errores conocidos de Prisma">
    `PrismaClientKnownRequestError` es la clase de los errores con código `P20xx`. `P2003` salta cuando falla una clave ajena: al borrar un padre con `onDelete: Restrict` que tiene hijos, o al crear un hijo con un `categoriaId` que no existe.
  </Paso>
  <Paso lineas="14" titulo="Todo lo demás: 500 sin detalles">
    Cualquier otro error es culpa del servidor. Se responde `500` con un mensaje genérico: el detalle (el SQL, la ruta de un archivo…) no se manda al cliente.
  </Paso>
</Recorrido>

- Igual que en clase, va con `app.use(errorHandler)` al final de `app.ts`.
- Si usas el logger de Winston de clase, escribe el error con `logger.error` antes del `500`, para que quede en `logs/error.log`.
- El de clase responde con la clave `message`; este, con `error`. **Elige una** y úsala en toda tu API (y en Angular, que es quien la lee). Si mantienes los tests de clase, que comprueban `res.body.message`, usa `message`.
- El `errorHandler` de clase ya lee `err.status`, así que un `HttpError` también funcionaría con él. La diferencia es que el de clase manda `err.message` incluso en los `500`.

## Qué código usar

La mayoría salieron en clase (los de la lista de arriba). `204`, `403` y `P2003` <NoDadoEnClase inline /> no.

| Código | Cuándo | Ejemplo |
| --- | --- | --- |
| `200` | Bien, y devuelve algo | `GET` y `PUT` o `PATCH` |
| `201` | Creado | `POST`: `res.status(201).json(nuevo)` |
| `204` | Bien, sin nada que devolver | `DELETE`: `res.status(204).end()` |
| `400` | Datos mal | Falla Zod, o el id no es un número |
| `401` | Sin token o token malo | `requireAuth`, credenciales incorrectas en el login |
| `403` | Con token, pero sin permiso | Tocar algo de otro usuario |
| `404` | No existe | `P2025`, o `findUnique` devuelve `null` |
| `409` | Choca con lo que hay | `P2002` (duplicado), `P2003` (tiene hijos), sin stock |
| `500` | Fallo del servidor | Cualquier otra cosa. No se manda el detalle al cliente |

<Callout type="warn" title="401 no es lo mismo que 403">
  `401` es "no sé quién eres" (falta el token o no vale). `403` es "sé quién eres, pero esto no es tuyo". Y un `204` no lleva cuerpo: con `res.status(204).json(...)` el JSON no llega.
</Callout>

## Para la defensa: provocar cada error <NoDadoEnClase inline />

<Terminal titulo="bash">
{`$ curl -i "http://localhost:3000/api/productos?limit=500"
HTTP/1.1 400 Bad Request
$ curl -i http://localhost:3000/api/productos/99999
HTTP/1.1 404 Not Found
$ curl -i -X POST http://localhost:3000/api/categorias -H "Content-Type: application/json" -d '{"nombre":"Periféricos"}'

- `-i` enseña la línea de estado y las cabeceras, además del cuerpo (aquí solo se ve la primera línea).
- El `400`: un dato que Zod no deja pasar. El `404`: un id que no existe. El `409`: un nombre de categoría repetido (`P2002`).
- En PowerShell, `curl` es otro comando: usa `curl.exe` o prueba lo mismo con Postman, como en clase.

<Ejercicio titulo="Crear un producto de una categoría que no existe" dificultad="media">
  Escribe el servicio `crearProducto(datos)` para que, si la `categoriaId` no existe, la API responda con un error claro en vez de un `500`. Hazlo de dos formas: dejando que salte el error de Prisma, y comprobándolo tú antes.

  <Pista>Si no compruebas nada, Prisma lanza `P2003` (falla la clave ajena), y el `errorHandler` de esta página ya lo convierte en `409`.</Pista>
  <Pista>Para comprobarlo antes, busca la categoría con `findUnique` y lanza un `HttpError` si es `null`.</Pista>

  <Solucion>

```ts title="productos.service.ts"
// Forma 1: el errorHandler traduce P2003 a 409
export function crearProducto(datos: { nombre: string; precio: number; stock: number; categoriaId: number }) {
  return prisma.producto.create({ data: datos });
}

// Forma 2: comprobarlo antes, con un mensaje más claro
export async function crearProductoComprobando(datos: { nombre: string; precio: number; stock: number; categoriaId: number }) {
  const categoria = await prisma.categoria.findUnique({ where: { id: datos.categoriaId } });
  if (!categoria) {
    throw new HttpError(400, 'La categoría no existe');
  }
  return prisma.producto.create({ data: datos });
}
```

Las dos valen. Con la primera, el mensaje del `errorHandler` ("Tiene datos relacionados") está pensado para los borrados y confunde al crear; la segunda da un mensaje que Angular puede enseñar tal cual. Puedes usar `400` o `404`: lo importante es que no sea un `500` y que el mensaje se entienda.

</Solucion>
</Ejercicio>
