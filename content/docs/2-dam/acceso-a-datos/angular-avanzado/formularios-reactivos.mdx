## Plantilla o clase: dónde vive el formulario

<DeClase fecha="18/11" proyecto="proj-game" rama="refactor/reactive-form2" />

| | Template-driven (Act 10) | Reactivo (Act 11) |
| --- | --- | --- |
| Módulo | `FormsModule` | `ReactiveFormsModule` |
| Dónde se define | En la plantilla: `ngModel`, `name`, `#x="ngModel"` | En la clase: un `FormControl` por campo dentro de un `FormGroup` |
| Validadores | Atributos HTML: `required`, `minlength="3"` | Funciones: `Validators.required`, `Validators.minLength(3)` |
| Enlace en el HTML | `[(ngModel)]="game.title"` | `[formGroup]` en el `<form>` y `formControlName="title"` en cada campo |
| Referencia del formulario | `NgForm` | `FormGroupDirective` |
| Formularios grandes o dinámicos | Se complica | Más cómodo (`FormArray`, `FormBuilder`) |

La idea: en el reactivo, **el modelo del formulario es un objeto de TypeScript** que puedes leer, cambiar y probar sin tocar el HTML. La plantilla solo se engancha a él.

## El tipo de un FormControl

<DeClase fecha="18/11" proyecto="proj-game" nota="con los tooltips y abriendo node_modules/@angular/forms/index.d.ts" />

El profesor fue enseñando con el tooltip de VS Code qué tipo deduce TypeScript según cómo se crea el control:

| Cómo se crea | Tipo | Qué pasa con `reset()` |
| --- | --- | --- |
| `new FormControl()` | `FormControl<any>` | Vuelve a `null`, y TypeScript no te avisa de nada |
| `new FormControl('')` | `FormControl<string \| null>` | Vuelve a `null` |
| `new FormControl('', { nonNullable: true })` | `FormControl<string>` | Vuelve al valor inicial, `''` |

Sin `nonNullable`, Angular supone que el control puede quedarse en `null` (por ejemplo, después de un `reset()` sin valor), y el tipo lo refleja. Con `nonNullable: true`, el valor inicial es también el valor de reinicio y el `null` desaparece del tipo.

El **segundo argumento** del constructor admite tres formas: un validador suelto, un array de validadores o un objeto de opciones (`FormControlOptions`) con `nonNullable`, `validators`, `asyncValidators` y `updateOn`. En clase siempre se usa el objeto.

<Callout type="idea" title="Mira los tipos de la librería">
  Con el cursor sobre `FormControl` y *Ir a la definición*, VS Code abre `node_modules/@angular/forms/index.d.ts`. Ahí se ven las sobrecargas del constructor, `FormControlState<T>` (`{ value, disabled }`) y que `FormControlOptions` extiende `AbstractControlOptions`. Es lo que hizo el profesor para explicar `nonNullable`.
</Callout>

## Validators

Al escribir `Validators.` el autocompletado lista los que trae Angular: `compose`, `email`, `max`, `maxLength`, `min`, `minLength`, `nullValidator`, `pattern`, `required` y `requiredTrue`. Los que llevan parámetro (`minLength(3)`, `max(100)`…) son **funciones que devuelven un validador** (`ValidatorFn`); los que no, como `Validators.required`, se pasan sin paréntesis.

Cuando un validador falla, añade una clave al objeto `errors` del control. **El nombre de la clave no siempre es el del validador**:

| Validador | Clave en `errors` | Valor del error |
| --- | --- | --- |
| `Validators.required` | `required` | `true` |
| `Validators.minLength(3)` | `minlength` (en minúsculas) | `{ requiredLength: 3, actualLength: 2 }` |
| `Validators.maxLength(40)` | `maxlength` | `{ requiredLength: 40, actualLength: 41 }` |
| `Validators.min(0.01)` | `min` | `{ min: 0.01, actual: 0 }` |
| `Validators.max(100)` | `max` | `{ max: 100, actual: 150 }` |
| `Validators.pattern(/^\d+$/)` | `pattern` | `{ requiredPattern: '/^\d+$/', actualValue: 2.5 }` |
| `Validators.email` | `email` | `true` |

El tooltip de `Validators.max` lo enseña así: con `max(15)` y el valor 16, el error es `{ max: { max: 15, actual: 16 } }`.

`min`, `max`, `minLength` y `pattern` **no dan error con el campo vacío**: de eso se encarga `required`. Por eso casi siempre van juntos.

La tabla de controles que pide la Act 11 (en el documento):

| Control | Valor inicial | Validadores |
| --- | --- | --- |
| `title` | `''` | `required`, `minLength(3)` |
| `genre` | `''` | `required` |
| `platform` | `''` | `required` |
| `price` | `0` | `required`, `min(0.01)` |
| `stock` | `0` | `required`, `min(0)`, `pattern` de entero (`/^\d+$/`) |

El documento avisa de que `type="number"` y `step="1"` en el input **no sustituyen** a la validación de Angular: el navegador deja escribir decimales igualmente. En clase, el precio llevó además `max(100)` y el stock `max(999)` en vez del `pattern`.

## Mostrar los errores

```html title="crud.component.html (título y precio)"
@if (title.invalid && (title.touched || title.dirty)) {
  @if (title.hasError('required')) { <p>Título obligatorio...</p> }
  @if (title.errors?.['minlength']) { <p>Longitud minima 3...</p> }
}

@if (price.invalid && (price.touched || price.dirty || gameForm.submitted)) {
  @if (price.hasError('required')) { <p>Precio es obligatorio...</p> }
  @if (price.errors?.['min'] || price.errors?.['max']) { <p>Precio fuera de rango permitido [0.01-100]</p> }
}
```

- `control.hasError('clave')` y `control.errors?.['clave']` hacen lo mismo. `hasError` se lee mejor y no necesita los corchetes. En clase se mezclan las dos.
- La clave es la de la tabla de arriba: `hasError('minlength')`, no `hasError('minLength')`. Con el nombre mal no da error de compilación, simplemente el mensaje no sale nunca.
- Al precio se le añadió `gameForm.submitted` a la condición, para que los errores salgan también al pulsar Guardar. El título no lo lleva: si pulsas Guardar sin tocarlo, su error no aparece.

Pruébalo en el inspector. Escribe, sal de cada campo, borra, pulsa Guardar con el título sin tocar y activa después la barrera con `markAllAsTouched()`:

<InspectorFormControl />

Lo que enseña:

- `touched` pasa a `true` al **salir** del campo; `dirty`, al **cambiar** el valor.
- Con el campo vacío solo sale `required`; `min` y `max` no saltan hasta que hay un número.
- Con `"ab"` en el título, `errors` es `{ minlength: { requiredLength: 3, actualLength: 2 } }`.
- Al pulsar Guardar con todo vacío, salen los errores de precio y stock (su condición incluye `submitted`) pero no el del título. Con la barrera activada, `markAllAsTouched()` marca todos los campos como tocados y salen todos.
- Si el formulario es inválido, `onSaveGame` hace `return` y no se manda nada a JSON Server.

En la demo los mensajes de stock dicen "Stock…". En el código de clase dicen "Precio es obligatorio" y "Precio fuera de rango", copiados del precio.

## La clave tiene que coincidir

<DeClase fecha="18/11" proyecto="proj-game" nota="prueba con genre_" />

`formControlName` busca el control **por la clave dentro del `FormGroup`**, no por el nombre de la propiedad de la clase. El profesor lo demostró cambiando la clave a `genre_`: el formulario solo funciona si en el `FormGroup` y en el HTML pone lo mismo.

```ts
genre = new FormControl('', { nonNullable: true, validators: [Validators.required] });
formGroup = new FormGroup({ title: this.title, genre: this.genre });
//                                             ^ la clave que busca formControlName="genre"
```

Si no coinciden, en la consola sale *"Cannot find control with name: 'genre'"*. Y si queda algún `#platform="ngModel"` de la versión anterior, sin `FormsModule` sale **NG8003**: *No directive found with exportAs 'ngModel'*. Los dos estilos no se mezclan.

## gameForm pasa a ser un FormGroupDirective

```html
<form [formGroup]="formGroup" #gameForm="ngForm" (ngSubmit)="onSaveGame(gameForm)" novalidate>
```

La referencia `#gameForm="ngForm"` se queda, pero ya no es un `NgForm`: sobre un `<form>` con `[formGroup]`, `ngForm` es el nombre que exporta la directiva **`FormGroupDirective`** (el tooltip dice *"Binds an existing FormGroup or FormRecord to a DOM element"*). Sigue teniendo lo que se usaba antes: `submitted`, `valid`, `invalid`, `value` y `resetForm()`. Por eso el método cambia el tipo del parámetro:

```ts
onSaveGame(form: FormGroupDirective) { ... }   // antes: (form: NgForm)
```

En las capturas no se ve si al final se quita `#gameForm` del `<form>`.

  selector: 'app-crud',
  imports: [ReactiveFormsModule, JsonPipe],

  styleUrl: './crud.component.css'

export class CrudComponent implements OnChanges {
  private gameService = inject(GameService);

  title = new FormControl('', { nonNullable: true, validators: [Validators.required, Validators.minLength(3)] });
  genre = new FormControl('', { nonNullable: true, validators: [Validators.required] });
  platform = new FormControl('', { nonNullable: true, validators: [Validators.required] });
  price = new FormControl(0, { nonNullable: true, validators: [Validators.required, Validators.min(0.01), Validators.max(100)] });
  stock = new FormControl('', { nonNullable: true, validators: [Validators.required, Validators.min(0), Validators.max(999)] });

  formGroup = new FormGroup({
    title: this.title,
    genre: this.genre,
    platform: this.platform,
    price: this.price,
    stock: this.stock
  });

  edit = false;
  editGame = input.required<Game | undefined>();
  actualizaGames = output<Game>();

  ngOnChanges(changes: SimpleChanges): void {
    if (changes['editGame']?.currentValue) {
      this.formGroup.setValue(changes['editGame'].currentValue);
      this.edit = true;
    }
  }

  onSaveGame(form: FormGroupDirective) {
    if (form.invalid) return;
    if (this.edit) {
      this.gameService.update({ id: this.editGame()?.id, ...form.value }).subscribe(gameUpdated => {
        form.resetForm();
        this.edit = false;
        this.actualizaGames.emit(gameUpdated);
      });
    } else {
      this.gameService.create(form.value).subscribe(gameSaved => {
        form.resetForm();
        this.actualizaGames.emit(gameSaved);
      });
    }
  }
}`}

## Rellenar el formulario al editar

<DeClase fecha="18/11, 19/11" proyecto="proj-game" />

En directo, la línea de `ngOnChanges` salió mal un par de veces (`this.formGroup.value = ...`, `setValue() = ...`) antes de quedar como llamada. Al probarlo, el juego se cargaba en el formulario salvo el stock: al `<input>` de stock **le faltaba `formControlName="stock"`**. Se añadió y el formulario pasó a "Válido: true".

<Comparar titulo="Dos formas de meter el juego en el formulario">
  <Lado titulo="En directo (18/11): setValue">

```ts
ngOnChanges(changes: SimpleChanges): void {
  if (changes['editGame']?.currentValue) {
    this.formGroup.setValue(changes['editGame'].currentValue);
    this.edit = true;
  }
}
```

`setValue` exige un objeto con **exactamente** las claves del grupo: ni una más ni una menos.

  </Lado>
  <Lado titulo="Diapositiva y 19/11: patchValue">

```ts
ngOnChanges(changes: SimpleChanges): void {
  if (changes['editGame']?.currentValue) {
    let game = changes['editGame']?.currentValue;
    this.gameFormGroup.patchValue(game);
    this.edit = true;
  }
}
```

`patchValue` rellena las claves que coinciden y no se queja ni de las que faltan ni de las que sobran.

  </Lado>
</Comparar>

El `Game` que llega del padre trae además `id`, que no está en el grupo. Por cómo funciona `setValue`, eso debería dar el error *"Cannot find form control with name: 'id'"*, y por eso es más seguro `patchValue`. <Dudoso nota="El juego se carga en el formulario en la demo, pero no se ve la consola en ese momento.">En las capturas no se ve si dio error</Dudoso>.

Hay un segundo motivo en `proj-game`: el 05/11, los juegos 1 a 15 de `db.json` no tenían `stock` (no se ve que se corrigiera). Con uno de esos, `setValue` también fallaría, ahora por la clave que **falta** (*Must supply a value for form control with name: 'stock'*). `patchValue` lo carga sin problema y deja el stock como estaba.

| Método | Claves que faltan | Claves que sobran |
| --- | --- | --- |
| `setValue(obj)` | Error | Error |
| `patchValue(obj)` | Se dejan como estaban | Se ignoran |

## Barrera de validación (Tarea 5 de la guía)

<DeClase fecha="18/11" nota="en la guía de la actividad, Tarea 5" />

```ts title="Guía de la Act 11, Tarea 5"
guardar(form: FormGroupDirective): void {
  this.gameForm.markAllAsTouched();
  if (this.gameForm.invalid) {
    return; // no se contacta con JSON Server
  }
  const game = this.gameForm.getRawValue();
  // TODO: llamar a GameService con game
  // Tras confirmar el POST y actualizar el listado:
  // form.resetForm();
}
```

Aquí `this.gameForm` es el `FormGroup` (en el código del profesor, `formGroup`).

1. **`markAllAsTouched()`** marca todos los controles como tocados, así salen todos los mensajes aunque el usuario no haya pasado por los campos.
2. **`if (invalid) return`**: si algo falla, no se hace la petición. Para comprobarlo, la guía dice que abras la pestaña Network: al enviar un formulario inválido no debe salir ninguna.
3. **`getRawValue()`** devuelve los valores de **todos** los controles, también los deshabilitados (`.value` deja fuera los que tienen `disabled`). Con controles `nonNullable`, su tipo es exacto: `{ title: string; genre: string; ... }`.
4. La petición sigue en `GameService`, nunca en el componente. Después de que responda, `form.resetForm()`.

La guía deja pendiente llamar al servicio y el `resetForm()`.

## Tipos que no cuadran

Con `stock = new FormControl('', { nonNullable: true, ... })`, el control es un `FormControl<string>`, pero el input es `type="number"` y el modelo `Game` dice `stock: number`. En clase no se ve qué se hace con ese desajuste. En ejecución funciona porque, con `type="number"`, Angular escribe un número en el control, pero TypeScript cree que es un texto y `form.value` (de la `FormGroupDirective`) es `any`, así que no te avisa.

### Cómo dejarlo bien tipado <NoDadoEnClase inline />

<NoDadoEnClase>
  No se hizo en clase. Es una forma de que TypeScript compruebe que lo que mandas a `GameService` es un `Game`.
</NoDadoEnClase>

```ts title="crud.component.ts (tipado, no es la versión de clase)"
price = new FormControl(0, { nonNullable: true, validators: [Validators.required, Validators.min(0.01), Validators.max(100)] });
stock = new FormControl(0, { nonNullable: true, validators: [Validators.required, Validators.min(0), Validators.max(999), Validators.pattern(/^\d+$/)] });

onSaveGame(form: FormGroupDirective) {
  this.formGroup.markAllAsTouched();
  if (this.formGroup.invalid) return;

  const datos = this.formGroup.getRawValue();   // { title: string; ...; price: number; stock: number }
  const peticion = this.edit
    ? this.gameService.update({ id: this.editGame()?.id, ...datos })
    : this.gameService.create(datos);

  peticion.subscribe(game => {
    form.resetForm();
    this.edit = false;
    this.actualizaGames.emit(game);
  });
}
```

Con `0` como valor inicial, `price` y `stock` son `FormControl<number>`, y `getRawValue()` devuelve un objeto con los mismos tipos que `Game` (sin `id`). Si te equivocas en un campo, ahora sí falla al compilar.

## Más allá de clase: FormBuilder, FormArray y validadores propios <NoDadoEnClase inline />

<NoDadoEnClase>
  Esto está en la guía [10_Formularios](https://github.com/hokahey007/guides-angular) (con su proyecto en [codebase-angular/10_formularios](https://github.com/hokahey007/codebase-angular/tree/main/10_formularios)), pero no se dio en clase. Es un resumen con nuestras palabras.
</NoDadoEnClase>

<Tabs items={['FormBuilder', 'Validador propio', 'FormArray']}>
  <Tab value="FormBuilder">

`FormBuilder` ahorra escribir `new FormGroup` y `new FormControl`. Por dentro crea lo mismo. Con `nonNullable`, todos los controles son no nulos:

```ts
private fb = inject(FormBuilder);

formGroup = this.fb.nonNullable.group({
  title: ['', [Validators.required, Validators.minLength(3)]],
  genre: ['', Validators.required],
  platform: ['', Validators.required],
  price: [0, [Validators.required, Validators.min(0.01), Validators.max(100)]],
  stock: [0, [Validators.required, Validators.min(0), Validators.max(999)]],
});
```

Cada clave es `[valorInicial, validadores]`. Para leer un control en la plantilla: `formGroup.controls.title.invalid`, o guárdalo antes con `@let title = formGroup.controls.title;`.

  </Tab>
  <Tab value="Validador propio">

Un validador es una función que recibe el control y devuelve `null` si está bien o un objeto de error si está mal. La clave que devuelvas es la que luego consultas con `hasError`:

```ts title="validadores.ts"
import { AbstractControl, ValidationErrors, ValidatorFn } from '@angular/forms';

export function enteroValidator(): ValidatorFn {
  return (control: AbstractControl): ValidationErrors | null => {
    if (control.value === '' || control.value === null) return null; // de eso se encarga required
    return Number.isInteger(Number(control.value)) ? null : { entero: true };
  };
}
```

```ts
stock = new FormControl(0, { nonNullable: true, validators: [Validators.required, enteroValidator()] });
```

```html
@if (stock.hasError('entero')) { <p>El stock tiene que ser un número entero</p> }
```

  </Tab>
  <Tab value="FormArray">

Un `FormArray` es una lista de controles que puede crecer o encoger, por ejemplo, una lista de etiquetas o las líneas de un carrito:

```ts
etiquetas = new FormArray([new FormControl('', { nonNullable: true })]);
formGroup = new FormGroup({ title: this.title, etiquetas: this.etiquetas });

anadirEtiqueta(): void {
  this.etiquetas.push(new FormControl('', { nonNullable: true }));
}

quitarEtiqueta(i: number): void {
  this.etiquetas.removeAt(i);
}
```

```html
<div formArrayName="etiquetas">
  @for (control of etiquetas.controls; track $index) {
    <input [formControlName]="$index" />
    <button type="button" (click)="quitarEtiqueta($index)">Quitar</button>
  }
</div>
<button type="button" (click)="anadirEtiqueta()">Añadir etiqueta</button>
```

  </Tab>
</Tabs>
